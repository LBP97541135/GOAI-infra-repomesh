# 推理轨迹（Trace）实现方案

日期：2026-08-15
状态：待评审
关联：`docs/可观测性-赛题对照与实现方案-2026-08-14.md`、观测中心门户（`#/observe/trace`）

## 1. 目标

让观测中心的「推理轨迹」板块从占位页变成真实数据页，覆盖赛题点名的全链路推理轨迹：**Skill 调用、MCP 工具、RAG 检索、LLM 推理**。这些事件发生在 Agent 容器侧（Manager + 8 个 Worker），不经过 RepoMesh 进程，本方案的读取通道是 Agent 自动推入存储的 `.copaw` 会话文件。

交付物：一张会话元数据表、一张事件表、一个后台采集器、三个查询端点、一个时间线页面。

## 2. 数据通道（已核实）

会话文件的位置与格式已从 AgentTeams 源码与真实环境（Docker Desktop 已启动，embedded/hiclaw 部署）确认：

| Runtime | 路径（容器内） | 格式 |
|---|---|---|
| CoPaw Worker/Leader | `/root/hiclaw-fs/agents/{name}/.copaw/workspaces/{workspace}/sessions/` | `.json`，一个会话一个文件 |
| OpenClaw（如启用） | `/.openclaw/agents/main/sessions/` | `.jsonl`，每行一条消息 |

**workspace 名不固定**：真实环境同时存在 `default`（运行时会话，含真实会话文件）与 `CoPaw_QA_Agent_0.1beta1`（模板/配置，sessions 为空），解析器必须扫描 `.copaw/workspaces/*/sessions/`，不能硬编码 `default`。

CoPaw 的 `FileSync.push_loop`（`copaw/src/copaw_worker/sync.py`）把本地变更周期推入存储，`.copaw/sessions/` 属于 Worker 管理且会被推送。真实环境验证：MinIO `hiclaw-storage` bucket 下存在 `agents/{name}/.copaw/workspaces/default/sessions/*.json`，多个 leader 各有 2 个会话（最大 406 KiB）。

读取侧：

- **本地直读**：`REPOMESH_AGENTTEAMS_STORAGE_ROOT` 指向的目录，对象路径与 key 一一对应。当前宿主机可通过「docker exec/cp 或一次性容器挂 `agentteams-data` 卷」把 `minio/hiclaw-storage/agents` 预同步到本地目录后直读。
- **MinIO 客户端**：凭据已从 controller 环境变量取得（endpoint `127.0.0.1:9000`，bucket `hiclaw-storage`，user `kissie`）。当前宿主机无法直接访问容器内 9000（18001 是 Higress、18088 是 Element，S3 API 不可用）；给 controller 补 `-p 9000:9000` 端口映射（重建容器）或比赛部署同网络后即可直连。RepoMesh 已有先例：`integrations/agentteams/task_publishing.py` 按同套配置构造 `minio.Minio`。

OpenClaw `.jsonl` 与 CoPaw `.json` 格式不互通，本期先做 CoPaw；OpenClaw 会话作为同一解析器的第二个输入格式（路线 1b）预留接口，不在本期实现。

## 3. 架构

```
Agent 容器 (.copaw/sessions/*.json)
   │  push_loop 周期推送（已有）
   ▼
存储（MinIO 或 STORAGE_ROOT 本地目录，agents/{name}/.copaw/...）
   │  trace_ingest 后台轮询（新，observability 模块）
   ▼
observability.trace_sessions / trace_events（新表）
   │  GET /observe/trace/...（新端点）
   ▼
ObserveTrace 页面（时间线视图）
```

MinIO 是源，PostgreSQL 是查询投影。对象存储不适合按字段过滤、分页、聚合；`llm_usage` 已经是「采集 → append-only 投影」的既有模式，告警与后续评估也都需要 SQL 侧的数据，所以落库而不是每次全量扫对象。

## 4. 存储设计

新增迁移 `20260815_0030_observability_traces.py`，两张表都在 `observability` schema。

### trace_sessions（会话元数据）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | 会话在观测侧的主键 |
| `session_id` | text | CoPaw 会话原始 id（文件名的 stem） |
| `agent_name` | text | 从对象 key `agents/{name}/...` 解析出的 Worker/Manager 名 |
| `runtime` | text | `copaw` / `openclaw`（本期只有 copaw，列先留） |
| `source_key` | text | 存储对象 key，`unique` |
| `object_mtime` | timestamptz | 存储侧对象修改时间，增量判断依据 |
| `object_size` | bigint | 对象字节数，增量判断依据 |
| `first_seen_at` | timestamptz | 首次发现时间 |
| `parsed_at` | timestamptz | 最近一次成功解析时间 |
| `parsing_error` | text 可空 | 解析失败原因（记录而非崩溃，见 §6） |
| `event_count` | int | 已落库事件数 |

索引：`(agent_name, first_seen_at)`、`(source_key)` 唯一。

### trace_events（事件流水）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | |
| `session_id` | uuid FK → trace_sessions.id，CASCADE | |
| `seq` | int | 会话内事件序号（来自文件顺序） |
| `ts` | timestamptz | 事件时间 |
| `event_type` | text | `chat` / `tool` / `skill` / `mcp`（见 §6） |
| `name` | text | 事件名：模型名 / 工具名 / Skill 名 |
| `role` | text 可空 | `user` / `assistant` / `tool` / `thinking` |
| `summary` | text 可空 | 截断后的正文摘要（见 §6 截断策略） |
| `token_count` | int 可空 | LLM 事件 token 数（有则填） |
| `latency_ms` | int 可空 | 工具/Skill 执行耗时（有则填） |
| `status` | text | `ok` / `error` / `skipped`（工具结果为空或异常） |
| `payload` | jsonb 可空 | 原始事件片段（解析器认定的关键字段，防信息丢失） |

唯一约束 `(session_id, seq)`，`insert ... on conflict do nothing` 实现幂等——同一对象被重复轮询、或 mtime 变化后整文件重解析，都不会产生重复行。

## 5. 采集器

新文件 `observability/infrastructure/trace_ingest.py`，结构对齐 `alerting.py` 的后台循环模式：应用启动时随 `background_services` 挂一个轮询任务。

轮询逻辑：

1. 列出存储根下 `agents/*/.copaw/workspaces/default/sessions/*.json`（本地直读用 `rglob`；MinIO 用 `list_objects(prefix="agents/")` 过滤后缀）。
2. 对每个 key，读取对象 mtime + size，与 `trace_sessions` 中记录比对；相同则跳过。
3. 新 key 或已变化 → 拉取对象内容 → 解析 → 事务内写 session 行 + 事件行。
4. 解析失败：写/更新 session 行的 `parsing_error`，不中断轮询；同一对象在下次轮询重试（避免死循环：连续失败记录失败次数，超过阈值降级为只记录不再重拉，靠 mtime 变化触发重试）。

轮询间隔建议 30 秒（对齐前端摘要的观察习惯；push_loop 本身有周期，事件到达存在秒级到分钟级延迟，属预期）。

解析器 `parse_copaw_session(text: str) -> list[TraceEventDraft]` 是纯函数，单测友好。输入是 session JSON 的文本，输出是规范化的事件草稿列表，不碰数据库。

## 6. 解析规范与语义映射

会话 JSON 结构已在 M0 用真实文件确认到字段级（见 `docs/推理轨迹-M0-侦察记录-2026-08-15.md` §3）。解析器输入是会话文件文本，输出是规范化事件草稿，纯函数，不碰数据库。

真实结构要点（解析器依赖）：

- 顶层仅 `agent`；`agent` 含 `name` / `_sys_prompt` / `toolkit` / `memory`；`memory` 含 `content`（二元组 `[msg, []]` 列表）与 `_compressed_summary`。
- 消息六键：`id` / `name` / `role` / `content` / `metadata` / `timestamp`。`role` 取值 `user` / `assistant` / `system`；`metadata` 在本环境恒为 `{}`，不依赖；`timestamp` 形如 `2026-08-14 11:43:10.386`（无时区，本地时间）。
- 块三类型：`text`（`{type, text}`）、`tool_use`（`{type, id, name, input, raw_input}`，出现在 assistant 消息）、`tool_result`（`{type, id, name, output: [text块]}`，出现在 system 消息）。**tool_result 没有 content 字符串，结果是 `output` 块列表。**

事件映射（对应赛题覆盖项，识别规则按真实数据校准）：

| 赛题覆盖项 | event_type | 识别规则（真实数据验证） |
|---|---|---|
| LLM 推理 | `chat` | 消息 `role in (user, assistant)` 且 `content` 含 `text` 块（纯文本）；真实会话 assistant 多只发 tool_use，chat 事件主要来自 user 侧 |
| Skill 调用 | `skill` | `tool_use.name` 前缀 `skill_*`（真实数据未出现，规则保留待复核） |
| MCP 工具 | `mcp` | `tool_use.name` 前缀 `mcporter.*` / `repomesh-task-control.*`（真实数据未出现，规则保留待复核） |
| RAG 检索 | `rag` | 检索类工具调用 / memory 检索记录（真实数据未出现，规则可扩展） |
| 其他工具 | `tool` | 其余 `tool_use`（真实数据全部落此：`execute_shell_command` / `glob_search` / `read_file` / `grep_search` / `filesync`） |
| 任务关联 | `task` | user 消息文本解析出的 `repomesh.collaboration.v1` 负载（`kind: task_assignment` 等），携带 `task_id` / `repository_id` / `correlation_id`——trace 与 RepoMesh 任务的关联点 |

解析器防御策略（schema 版本漂移不中断）：

- 全程 `.get` 链取值，任何一层缺失落到「跳过该事件」而不是抛异常；整体解析失败才记 `parsing_error`。
- 工具结果正文取 `output` 内 text 块的拼接；`summary` 截断 500 字符（取首尾），原始 `input`/`raw_input` 进 `payload`。
- 每个文件解析的事件数上限 5000，超出记入 `parsing_error` 提示截断，防止巨型会话卡死轮询。
- 事件时间优先取消息 `timestamp`；缺失则回退会话文件 mtime。

## 7. API

三个端点挂到现有 observer router（`observability/api/router.py`，沿用 `_authorized_container` 鉴权），contract 模型放 `api/models.py`：

| 端点 | 说明 |
|---|---|
| `GET /observe/trace/sessions?agent=&cursor=&limit=` | 会话列表，按 `first_seen_at` 倒序，keyset 分页（cursor = 上一页末行 id），返回每会话的 agent / 事件数 / 解析状态 |
| `GET /observe/trace/sessions/{session_id}/events` | 单个会话的事件流水，按 `seq` 升序，上限 1000 条 |
| `GET /observe/trace/events?event_type=&agent=&q=&cursor=&limit=` | 跨会话过滤：按类型（skill/mcp/chat 等）、按 agent、按名称/正文模糊匹配 |

`summary` 端点不加——门户摘要已经只保留三个关键数字，trace 的统计由前端在页面内自行聚合会话列表得到，避免为「可能不用的统计」扩接口。

## 8. 前端

`ObserveTrace.tsx` 从占位页改为真实页面（`console` 的 `pages/observe/` 既有视觉 token 全部复用）：

- 顶部：ObserveCrumb 面包屑 + 汇总条（会话数 / 事件数 / 四类事件各自计数）。
- 类型筛选胶囊：全部 / LLM 推理 / Skill / MCP / RAG，切换触发 `events?event_type=` 请求。
- 会话列表：agent 名 + 时间 + 事件数 + 状态（`parsing_error` 有值时显示解析异常徽标），点击展开该会话的时间线。
- 时间线：每条事件一行——类型图标 + 名称 + 时间 + 状态；展开行显示 summary 与 payload 里的关键字段。
- 轮询 30 秒刷新会话列表（有活跃 Agent 时新会话自然出现）。

`api/client.ts` 增加 `traceSessions()` / `traceSessionEvents()` / `traceEvents()` 三个方法，contract 类型放 `api/contract.ts`。空态（无任何会话）沿用 `EmptyObserve` 组件，文案指向「配置存储并运行 Agent 后即有数据」。

## 11. 风险

| 风险 | 缓解 |
|---|---|
| CoPaw 升级导致 schema 漂移 | 结构已用真实数据校准；解析器防御式取值；`parsing_error` 可见；fixture 作为回归基线 |
| 长会话文件过大 | 事件数上限 + 正文截断 + `payload` 限量 |
| push_loop 周期导致事件延迟 | 文档标注「秒级到分钟级」；轮询 30s 与其匹配即可 |
| 宿主访问 MinIO 受限 | 预同步 + STORAGE_ROOT 本地直读先行；端口映射/同网络后切 S3，采集器读取源抽象为可切换 |
| 与 `llm_usage` 数据重叠 | 两者边界明确：llm_usage 是 RepoMesh 规划侧埋点，trace 是执行侧会话，互不替代 |
