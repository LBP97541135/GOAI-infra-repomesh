# 托管原生端到端验收（人话版）

> 这是原文 [`hosted-native-e2e-acceptance-script-20260902.md`](../hosted-native-e2e-acceptance-script-20260902.md) 的易读版。
>
> 它解释“为什么要拍这 30 幕、每一幕到底想证明什么”。执行验收时仍应回到原文复制准确命令、接口和数据库查询。

---

## 1. 这次验收到底要证明什么

页面显示 Running、房间里出现派单消息、任务状态变成进行中，都不能证明真的有人在写代码。

这次验收要用一条完整的 issue 路径证明：

1. 用户选择托管原生模式；
2. RepoMesh 真正创建了可以执行的任务包；
3. AgentTeams 原生 Worker 在自己的容器里改了代码；
4. Worker 交出了候选代码和自测证据；
5. Leader 真正审阅过候选结果；
6. 独立 verifier 在全新容器里重新跑过验证；
7. RepoMesh 获得了可信的候选提交；
8. 整条链没有启动本地 coding CLI；
9. 整条链没有向 GitHub 推送任何东西；
10. 重启、越界修改、假通过等坏情况都会被拦住。

验收的核心原则是：

> 每一张“看起来成功”的截图，都必须配一条机器探针。截图证明用户看得见，探针证明系统真的做了。

---

## 2. 为什么不能只看截图

9 月 2 日的演示里曾经同时出现这些现象：

- 团队页显示就绪；
- Worker 显示 Running；
- 房间里有派单消息；
- 日志里却一直报 Worker MCP 错误；
- 同一条派单还重复发送；
- 没有任何进程真正写代码。

所以本次每一幕都要保存四样东西：

| 内容 | 意义 |
|---|---|
| 命令 | 实际执行了什么机器检查 |
| 预期 | 正确系统应该返回什么 |
| 实际 | 这次环境真实返回了什么 |
| 退出码 | 命令本身有没有成功运行 |

如果为了过关而手工补文件、改命令、重启额外服务或绕开产品路径，只能记为 `WORKAROUND`，不能记为 `PASS`。

---

## 3. 两个验收版本

### 基线版

现在就能跑，不改代码。只执行幕表中标记为 `B` 的项目，目的是保存“改造前到底坏在哪里”的对照证据。

基线版预计会看到：

- 派单进入房间；
- Worker 最后返回 BLOCKED；
- MCP 调用报错；
- 验证 dispatch 一直没人领取。

基线版失败是预期结果，但必须如实留证。

### 托管原生版

波次 1 合并后执行全部 30 幕。它是新版是否真正闭环的正式验收。

---

## 4. 谁负责哪些操作

用户自己在浏览器里完成：

- 登录；
- 初始化管理员；
- 填写模型密钥；
- 操作档案开关。

AI 可以完成：

- 使用 action token 调 RepoMesh API；
- 查看容器、对象存储和数据库；
- 驱动测试流程；
- 保存不含秘密的截图和探针输出。

任何时候都不能要求 AI 读取、展示或代填用户密码和模型密钥。

全程保持：

```text
REPOMESH_DELIVERY_AUTO_ENABLED=false
```

验收最多到“候选分支就绪”，不得向四个 GitHub 夹具仓推送内容。

---

## 5. 证据怎么保存

- 正文放在 `docs/startup-records/<日期>-hosted-native-e2e.md`；
- 截图放在同名子目录；
- 原始命令输出放在 gitignored 的 `output/hosted-native-e2e/<日期>/`；
- 截图使用 1440×900、深色主题、带侧栏和页面时间；
- 含 token 的输入框必须先遮罩；
- 每幕判定只能是 `PASS`、`BLOCKED`、`WORKAROUND` 或 `SKIP`；
- 幂等检查比较整行内容哈希，不能只比较“行数有没有增加”。

## 6. 30 幕验收，用一条故事串起来

下面保留原来的幕次编号，便于和正式命令逐项对应。

### 第一段：确认平台和团队真的准备好了（01～06）

| 幕 | 要做什么 | 人在页面上看到什么 | 机器必须证明什么 |
|---|---|---|---|
| 01 基线 | 用户登录 | 登录控制平面 | setup/status 确认管理员已经初始化 |
| 02 | 打开“设置 → 执行面” | 执行面 ready，verifier 心跳很新 | setup/status 的 execution_plane 真的是 ready |
| 03 基线 | 查看仓库页 | 四个夹具仓都有验证配置 | 四个仓的测试命令都不是空的 |
| 04 | 创建仓库团队并选择托管原生 | 模态默认选择“托管原生” | 数据库里的 construction_mode 是 hosted_native |
| 05 基线 | 查看团队页 | 团队就绪、模式明确、运行时 Running | AgentTeams Controller 返回 8 个 Running Worker/Leader |
| 06 基线 | 查看智能体页 | 8 个 CoPaw 容器 Running | Docker 中确实有 8 个 Up 的 Worker 容器；原 spec 不要求 Manager Running |

这一段回答的是：页面上的“就绪”有没有真实运行实例支撑。

### 第二段：创建 issue 并开工（07～10）

| 幕 | 要做什么 | 人在页面上看到什么 | 机器必须证明什么 |
|---|---|---|---|
| 07 基线 | 新建多币种 issue | issue 出现在列表里 | 创建接口返回 201 |
| 08 基线 | 跑完发现链 | 计划 v1、4 个任务节点、3 个执行批次 | 计划快照里确实是三批 |
| 09 | 打开开工模态 | verifier、每个 Worker 和 Leader 都绿，按钮可点 | readiness 接口返回所有成员和服务 ready |
| 10 | 点击“物化并开工” | 若房间仍在准备，页面自动重查，90 秒内转绿后继续 | 服务端最终成功开工，不把内部 503 直接甩给用户 |

这一段回答的是：RepoMesh 会不会在执行面没准备好时制造一条假运行计划。

### 第三段：证明 Worker 真的在容器里写代码（11～13）

| 幕 | 要做什么 | 人在页面上看到什么 | 机器必须证明什么 |
|---|---|---|---|
| 11 基线对照 | 查看 pricing-core 团队房 | 只有一条派单，告诉 Worker 任务目录；新版不再出现 `start_assigned_task` | 共享目录里真实存在 spec、meta、manifest 和 base |
| 12 | 等 Worker 领取 | Worker 在房间里表示收到；终端可看到 `/work/<attempt>` | meta.json 有领取时间，状态为 in_progress；本地工作区里有仓库文件 |
| 13 | 等 Worker 交包 | 新版显示 TASK_COMPLETED；基线版预计 BLOCKED | candidate 目录里有 bundle、diff、changes、evidence；基线 result.md 为 BLOCKED |

这一段是整个验收最重要的证明：代码不是另一个本地 CLI 写的，确实是 AgentTeams 原生 Worker 在自己的容器里完成的。

幕 11 还要额外做密钥扫描：遍历任务目录里的文本，确认网关 key 和模型 key 的前缀都没有出现。扫描脚本必须先用一枚假 key 做正对照，证明它不是一个永远返回“没找到”的坏探针。

### 第四段：Leader 审阅，但不能替代复验（14）

| 幕 | 要做什么 | 人在页面上看到什么 | 机器必须证明什么 |
|---|---|---|---|
| 14 | 等 Leader 审阅 | Leader 房出现审阅任务，最后给出 ACCEPT | 审阅目录的 result.md 是 SUCCESS，而且第一行明确写 VERDICT: ACCEPT |

这一幕证明 Leader 收到的是一条真实可执行的审阅任务，而不是在房间里凭空聊天。

### 第五段：独立复验并形成候选提交（15～18）

| 幕 | 要做什么 | 人在页面上看到什么 | 机器必须证明什么 |
|---|---|---|---|
| 15 | 看 issue 详情 | Task 显示“第 1 次尝试 · verifying” | 验证任务被 verifier 真实领取，不再停在 queued |
| 16 | 观察 Docker | 验证时出现 `rm-verify-*` 容器，结束后消失 | Docker 事件里有 create 和 destroy |
| 17 | 查看复验结果 | Task succeeded，计划推进到下一批 | 候选 ref、候选工作树 HEAD 和证据 commit SHA 三者相同 |
| 18 | 查看交付读模型 | 候选分支就绪，但没有推送 | RepoMesh 的 head SHA 正确；GitHub 上没有新的 `repomesh/*` 分支 |

这一段证明：Leader 说“可以”之后，平台真的用一台干净的一次性容器重新验证过，而不是直接相信 Worker 或 Leader。

### 第六段：确认观测面没有继续假绿（19～22）

| 幕 | 要做什么 | 人在页面上看到什么 | 机器必须证明什么 |
|---|---|---|---|
| 19 基线 | 查看推理轨迹 | 有 Worker 和 Leader 会话，事件随施工增加 | observe summary 至少能看到相关会话 |
| 20 基线 | 查看用量大盘 | 按 issue 汇总不再为空 | observe issues 中能找到本 issue |
| 21 基线对照 | 日志页过滤 ERROR | 新版不再出现 Worker MCP 未处理错误；基线预计出现 | 数据库里对应错误数为 0 |
| 22 基线 | 查看告警 | 默认告警规则存在，没有无故触发 | 告警接口返回可解释的状态 |

这一段回答的是：执行链成功以后，观测、用量和日志是不是也与真实发生的事情一致。

### 第七段：故意把系统弄坏，看它会不会拦住（23～29）

这些反证不是“可选破坏测试”，而是正式验收的一部分。只跑成功路径，不算通过。

| 幕 | 故意制造什么问题 | 系统应该怎样反应 | 机器必须证明什么 |
|---|---|---|---|
| 23 | 停掉 verifier，再尝试开工 | 开工模态把 verifier 标红，服务端拒绝开工 | 409 明确返回 execution_plane_not_ready，并点名 verifier；恢复服务后转绿 |
| 24 | 停掉一个 Worker 容器 | 开工被拒绝，并点名真实 Worker | readiness 返回该 agentId 不可用；重启后恢复 |
| 25 | 给 Leader 一个测试会失败的候选，让它仍然 ACCEPT | 独立复验把任务判失败，不能被 Leader 放行 | 终态是 runner.failed，测试结果有非零退出码，Task 不是 succeeded |
| 26 | Worker 施工中重启容器 | 系统创建新代次；旧目录晚交结果也不能推进 Task | 数据库出现 fenced 事件，当前 generation 为 2，重复通知没有产生重复状态 |
| 27 | 让 Worker 修改禁止路径 | 复验失败，页面显示路径越界 | blockers 以 changed_path_denied 开头；同类允许路径改动可以通过 |
| 28 基线 | 建一条一定触发的告警规则 | 新 issue 被 intake_paused 拦住 | 创建 issue 返回 503 和 intake_paused |
| 29 | 建一个本地 CLI 团队，但不启动 Bridge | 开工被拒绝，点名本地 CLI 成员离线 | 409 的成员状态是 offline |

幕 25、26、27 是新版最关键的三条反证：

- Leader 不能绕过测试；
- 旧 Worker 不能靠迟交覆盖新尝试；
- Worker 不能越过路径边界。

### 第八段：对账和收尾（30）

| 幕 | 要做什么 | 人在页面上看到什么 | 机器必须证明什么 |
|---|---|---|---|
| 30 基线 | 做终态账面对照 | 一张表能解释 Task、尝试、调度、事件、候选提交和共享对象各有多少 | 各处数量能对上；共享任务目录没有 `.git`、`node_modules` 或其他工作区垃圾 |

这一幕确保系统没有“页面成功、数据库一套、共享盘又是另一套”的分裂状态。

## 7. 14 条正式验收标准

原 spec 把完成条件整理成 14 条 AC。人话版如下：

| AC | 必须证明什么 |
|---|---|
| 01 | 托管原生不启动本地 coding CLI，也不依赖本地成员租约。 |
| 02 | CoPaw Worker 确实在自己的容器内完成施工。 |
| 03 | Leader 可以审阅，但不能代替独立验证。 |
| 04 | 每一条验证任务都有人领取，不再出现永远 queued 的“无人消费”调度。 |
| 05 | Worker、Leader 或 verifier 未就绪时，开工明确失败并点名原因。 |
| 06 | RepoMesh 能回答任务被谁领取、现在第几代、处于什么阶段。 |
| 07 | 每次复验确实启动全新的一次性验证容器。 |
| 08 | 共享目录只保存任务和候选成果，不同步整个 Git 工作区。 |
| 09 | 重复通知、容器重启和旧结果迟到不会制造第二次成功。 |
| 10 | Leader 或 Worker 都不能越过冻结测试和路径规则。 |
| 11 | 任务包、共享盘和候选结果中没有模型密钥。 |
| 12 | 新模式没有破坏本地 CLI 模式原来的路径。 |
| 13 | 前端可以选择施工模式，并能看到真实执行阶段。 |
| 14 | 成功路径最终到达可信的候选提交，但不自动推 GitHub。 |

## 8. 什么情况不能算通过

以下任意一条发生，都不能把托管原生版记为 PASS：

- Worker 只在房间里回复，没有产生代码候选；
- 实际改代码的是本地 coding CLI；
- Leader ACCEPT 后没有独立复验；
- verifier 调度一直 queued；
- 测试红或路径越界仍然生成成功候选；
- Worker 重启后旧结果推进了新 generation；
- 任务目录包含模型密钥、`.git` 或 `node_modules`；
- 为了走通链路手工补写 candidate 文件；
- 自动或手工向 GitHub 推送了测试内容；
- 只保存截图，没有保存机器探针；
- 幕 25～27 没有执行。

## 9. 最终交付物

基线版完成后应得到：

```text
docs/startup-records/<日期>-hosted-native-e2e-baseline.md
```

托管原生正式验收完成后应得到：

```text
docs/startup-records/<日期>-hosted-native-e2e.md
docs/startup-records/<日期>-hosted-native-e2e/
output/hosted-native-e2e/<日期>/
```

正文中每一幕都要记录命令、预期、实际、状态和耗时，最后再按严重度列出本次发现的 F-n 问题。

正式验收记录完成后，它就是“波次 1 是否真正闭环”的判定文档，不能再用一句“我本地跑通了”代替。
