# 托管原生施工方案（人话版）

> 这是原文 [`agentteams-native-execution-mode-spec-20260902.md`](../agentteams-native-execution-mode-spec-20260902.md) 的易读版。
>
> 它帮助产品、设计、测试和第一次接触 RepoMesh 的开发者快速理解方案，不替代原始施工 spec。需要实现、写测试或核对字段时，仍以原文为准。
>
> 原文目前的状态是“设计定稿草案，待用户复核后开工”。下面出现的 D-1～D-22 是原文当前主张，不表示全部已经由用户最终拍板。

---

## 1. 先说结论

旧方案失败，是因为一个任务要经过两拨“会写代码的东西”：

1. AgentTeams 房间里的 Worker 先收到任务；
2. Worker 再去调用 RepoMesh；
3. RepoMesh 再找另一个本地 coding CLI 真正改代码。

第一拨只负责转交，第二拨才负责施工。两拨人各有自己的身份、凭据、运行状态和失败方式。9 月 2 日的实测中，第一拨调用 RepoMesh 时遇到 401，第二拨又根本没有 Runner 进程领取任务，所以页面看起来已经开工，实际上没有任何进程在写代码。

新方案把中间转交删掉：

> AgentTeams 原生 Worker 就是唯一施工者。它直接在自己的容器里改代码、跑自测并交候选结果。RepoMesh 负责任务治理、记录状态、组织 Leader 审阅、独立复验和接回交付链。

可以把它理解成：

- RepoMesh 是工程管理和质检制度；
- Worker 是真正写代码的工程师；
- Leader 是第一道代码审阅；
- verifier 是不相信口头承诺、会重新跑一遍测试的独立质检员；
- Matrix 房间是协作和通知空间，不是任务真相源。

## 2. 两种施工模式仍然都保留

RepoMesh 以后有两种并列模式：

| 模式 | 谁真正写代码 | 在哪里写 | 适用情况 |
|---|---|---|---|
| 托管原生 `hosted_native` | AgentTeams 自带的 CoPaw Worker | Worker 自己的容器 | 默认模式；平台统一托管 |
| 本地 CLI `local_cli` | 用户本机或外部环境里的 CLI | 受控的本地工作区 | 需要复用个人 CLI 登录态或本地工具时 |

本次施工只重做“托管原生”执行段，不重写本地 CLI 的 Bridge、Runner 和交付逻辑。

前端会让用户在创建仓库团队时选择施工模式。模式切换状态机不在第一波实现；第一波只支持创建时选定。

## 3. 每个角色到底做什么

### RepoMesh

RepoMesh 仍然是任务和治理的真相源。它负责：

- 保存 issue、计划、仓库团队、Task、判据和状态；
- 生成冻结的任务包；
- 决定任务派给哪个 Worker；
- 记录领取、提交、返工、过期和 fencing；
- 给 Leader 创建审阅任务；
- 让 verifier 独立复验；
- 复验通过后，把结果接回现有候选提交与交付链。

RepoMesh 不负责替 Worker 思考，也不会在 Worker 容器里再启动另一个 coding agent。

### Worker

Worker 是托管原生模式下唯一的代码施工者。它负责：

- 领取自己被分配的任务；
- 在容器本地的独立工作区恢复源码；
- 阅读 spec 和判据；
- 修改代码并自测；
- 生成候选 Git bundle、diff、变更清单和自测证据；
- 用 AgentTeams 原生 `submit_task` 交结果。

Worker 不直接推 GitHub，也不能用自己的自测结果宣布平台验证通过。

### Leader

Leader 不再负责实际写代码，也不取代 RepoMesh 拆任务。它在 Worker 交付候选结果之后做第一道审阅：

- `ACCEPT`：看起来可以，允许进入独立复验；
- `REVISION`：指出问题，让 Worker 开新一轮尝试返工；
- `BLOCKED`：无法判断或存在重大问题，转人工处理。

Leader 接到的是一条真正的原生审阅任务，而不只是房间里的一句话。Leader 的“接受”不等于最终通过，verifier 仍然必须重新验证。

### verifier

verifier 是 RepoMesh 新增的专职复验服务。它自己不写代码、不调用模型，只做这些事：

1. 领取等待复验的候选结果；
2. 启动一个一次性验证容器；
3. 从冻结基线恢复源码并应用候选 bundle；
4. 检查父提交、允许修改的路径和禁止修改的路径；
5. 重新运行测试命令；
6. 把机器证据回传 RepoMesh；
7. 销毁一次性容器。

API 容器和 bootstrap 容器都不直接跑项目测试。bootstrap 只负责确保 verifier 服务被正确启动。

### Manager

原始 spec 的 D-16 当前主张：第一阶段不要求组织 Manager 容器运行，也不把它放进开工门禁；Manager 暂时只表现为 RepoMesh 中的组织 leader 记录加人。

这是一项会改变原始产品模型的草案决策，不能因为写进 spec 就视为已经最终拍板。它仍应在开工前单独复核。

## 4. 一条任务从开工到候选提交会怎样走

以下用 pricing-core 的多币种任务举例。

### 第一步：RepoMesh 开一轮施工尝试

RepoMesh 根据冻结的 Task 创建：

- 分配记录；
- 第几次尝试的 generation；
- 45 分钟执行预留；
- 唯一的 attempt id；
- 一份任务包 v2。

每次尝试都有一个全新的目录，旧目录永不复用。

### 第二步：把任务包送到 Worker

任务包放进该仓库团队的共享任务目录，房间里只发通知并 @Worker。通知告诉 Worker：任务包在哪里、应该按哪三条帮助命令执行。

房间消息不是开工真相。即使通知重复，也不能产生第二次施工。

### 第三步：Worker 领取

Worker 使用 AgentTeams 原生 `ack_task` 领取。RepoMesh 的观察适配器从共享目录看见领取时间，把它记进自己的尝试状态。

第一阶段不再要求 Worker 先拿 RepoMesh 凭据调用 `start_assigned_task`，因此绕过了 9 月 2 日遇到的 MCP 401。

### 第四步：Worker 在本地工作区施工

真正的 Git 工作区位于 Worker 容器本地：

```text
/work/<attempt_id>
```

它不在对象存储同步目录内，所以 `.git`、`node_modules`、缓存和大量临时文件不会被上传。

Worker 通过帮助脚本：

1. `init`：从冻结的 `base.bundle` 恢复仓库；
2. `test`：运行任务包规定的测试；
3. `bundle`：生成候选交付物。

### 第五步：Worker 交候选结果

共享目录里只放这些需要治理和审计的东西：

- 候选 `candidate.bundle`；
- 便于阅读的 `candidate.diff`；
- `changes.json` 变更文件清单；
- `evidence.json` Worker 自测证据；
- AgentTeams 原生 `result.md`。

Worker 的自测证据只是它的声明，不是平台最终证据。

### 第六步：Leader 审阅

RepoMesh 检查候选文件齐全后，给 Leader 创建一条独立审阅任务。审阅包包含 diff、变更清单、自测摘要、冻结判据和路径规则。

Leader 返回 ACCEPT、REVISION 或 BLOCKED。

### 第七步：RepoMesh 物化候选工作树

Leader ACCEPT 后，RepoMesh 把候选 bundle 放进自己的镜像仓，校验父提交，并创建一棵候选工作树。

这棵工作树以后供现有交付链使用，保证最终证据里的 commit SHA 和磁盘上的 Git HEAD 是同一个提交。

### 第八步：独立复验

verifier 领取验证任务，启动一次性验证容器。它重新检查：

- 候选是不是建立在指定基线上；
- 有没有改白名单之外的路径；
- 有没有命中黑名单；
- 每条冻结测试命令是否通过。

越界时不继续执行候选代码和测试，直接失败。

### 第九步：接回原来的交付链

复验通过后，verifier 把 commit SHA、测试结果、变更文件和 bundle 证据回传。RepoMesh 沿用现有逻辑：

- Task 成功；
- 推进下一批任务；
- 生成候选分支；
- 在 issue 和交付读模型中显示结果。

第一阶段明确关闭自动外推，所以不会向 GitHub 推任何内容。

## 5. 为什么要有“尝试”、generation 和 fencing

容器可能重启，Worker 可能迟交，房间通知可能重复，网络也可能让同一个结果晚到几分钟。

因此系统不能只凭“目录里出现了 result.md”就相信它，而要同时核对：

- 这是哪个 Task；
- 第几次 assignment attempt；
- 当前 generation 是多少；
- 对应哪次 execution reservation；
- 这次预留是否仍然有效。

如果旧 Worker 在第二轮已经开始后才提交第一轮结果，RepoMesh 会把它记为 `fenced`，留作审计，但绝不推进 Task。

原始 spec 当前规定：

- 同一个 Task 默认最多 3 次施工尝试；
- 单次预算默认 45 分钟；
- Worker 容器不再 Running 时立即中断当前尝试；
- Leader 审阅预算默认 15 分钟；
- Leader 超时不会自动跳过审阅，而是 blocked 并转人工检查点。

Worker 返回 `REVISION_NEEDED` 表示它认为任务本身需要澄清，不会自动换一个 Worker 重试。

## 6. 任务包里有什么

一份施工任务包大致长这样：

```text
tasks/<attempt_id>/
├─ spec.md                     给 Worker 看的任务、判据和命令
├─ meta.json                   Task、attempt、generation、人员和时间
├─ manifest.json               文件清单和整体内容摘要
├─ base/
│  ├─ base.bundle              钉死的源码基线
│  └─ tools/rm-work.sh         init / test / bundle / clean
├─ candidate/
│  ├─ candidate.bundle         Worker 做出的候选 Git 提交
│  ├─ candidate.diff           便于 Leader 阅读的 diff
│  ├─ changes.json             改了哪些文件
│  └─ evidence.json            Worker 自测情况
└─ result.md                   AgentTeams 原生提交结果
```

审阅任务也有自己的独立目录和 attempt id，不与施工目录共用。

任务包、共享目录、工作区和结果包都不允许包含模型密钥。模型访问始终由 AgentTeams 网关治理。

## 7. 原文的 22 项决策，用人话重述

### 产品形态与职责

| 编号 | 人话版 |
|---|---|
| D-1 | 托管原生和本地 CLI 是两种正式并列的施工模式，默认托管原生。 |
| D-2 | 托管原生只有 CoPaw Worker 写代码，不再启动第二个 coding CLI。 |
| D-3 | Leader 保留，但只负责候选结果的第一道审阅。 |
| D-4 | 项目测试由独立 verifier 通过一次性容器运行。 |
| D-5 | 真正的 Git 工作区放在 Worker 容器本地，共享盘只放任务和候选成果。 |
| D-6 | 第一阶段使用 AgentTeams 原生领取和提交事件，RepoMesh 从共享盘观察并记账。 |
| D-7 | 模型密钥只由 AgentTeams 网关管理，RepoMesh 不把密钥塞进任务包。 |

### 尝试、验证与失败处理

| 编号 | 人话版 |
|---|---|
| D-8 | 每一次施工尝试使用全新任务目录，绝不覆盖旧尝试。 |
| D-9 | 尽量复用现有分配 generation、执行预留和租约，只新增托管原生的阶段记录。 |
| D-10 | 不再用 Runner 写代码，但暂时复用 `runner_dispatches` 作为 verifier 的验证任务队列。 |
| D-11 | Leader 接受后，API 把候选 bundle 变成真实 Git 工作树，供验证和交付使用。 |
| D-12 | 施工预算复用执行租约，默认 45 分钟、最多 3 次，并沿用现有恢复决策。 |
| D-13 | Leader 审阅默认 15 分钟，超时不跳过。 |
| D-14 | verifier 是路径越界的最终判定者，越界算本次尝试失败。 |
| D-15 | 第一版统一使用一张同时含 Git、Python 和 Node 的工具链镜像，团队自选镜像留到第二波。 |

### 模式、就绪和启动

| 编号 | 人话版 |
|---|---|
| D-16 | 原 spec 暂定第一阶段不要求 Manager 容器运行，也不修它的端口冲突。此项仍需产品裁决。 |
| D-17 | 仓库团队新增施工模式字段，并由它推导容器托管、Worker runtime 和默认拆解模式。 |
| D-18 | 第一阶段仍把旧 MCP 工具投影给 Worker，但新的任务说明不再让 Worker 调它；第二阶段再移除。 |
| D-19 | `setup/status` 增加执行面三态并成为开工真相；原 spec 不准备让 `/health/ready` 反映业务执行面是否可用。 |
| D-20 | 同一轮修复 Windows/Linux 启动脚本、网络和卷、配置写完后的服务重启等从零启动问题。 |
| D-21 | 任务包 v2、候选结果和审阅格式属于跨进程契约，正式放进 `contracts/agentteams-task/v2/`。 |
| D-22 | 最后一波把安装和启动逻辑收到容器中，宿主脚本只负责生成 token、启动 compose 和等待状态。 |

## 8. 系统内部会新增哪些“零件”

普通读者不需要记类名，只要知道各自职责：

| 零件 | 它负责什么 |
|---|---|
| HostedNativeRound | 把“一次施工尝试”的领取、提交、审阅、返工、过期和验证串成一个完整状态机。 |
| SharedTaskDirectoryObserver | 定期观察共享目录，把文件变化转成幂等事件。 |
| 任务包 v2 发布器 | 生成 Worker 和 Leader 真正能执行的任务包。 |
| repomesh_verifier | 领取验证任务并启动一次性容器复验。 |
| CandidateWorktreeMaterializer | 把候选 bundle 变成 RepoMesh 本地可验证、可交付的 Git 工作树。 |
| BaseBundleBuilder | 从镜像仓生成钉死基线的源码 bundle。 |
| ConstructionMode | 表示仓库团队使用托管原生还是本地 CLI。 |
| ExecutionPlaneReadiness | 判断某个计划现在是否真的具备开工条件。 |

系统只在确实有多个实现的边界上定义接口，例如共享目录既可能在 MinIO，也可能是本地磁盘；复验既需要真实 Docker 实现，也需要测试用的脚本实现。

## 9. 用户在前端会看到什么变化

- 创建仓库团队时可以选“托管原生”或“本地 CLI”；
- 设置页能看到执行面是 missing、wired 还是 ready；
- 开工模态会显示 verifier、Leader、Worker 的实际就绪情况；
- 房间或成员仍在准备时，页面会自动重查一段时间，不要求用户连续点三次；
- issue 的 DAG 节点会显示“第几次尝试、当前处于什么阶段”；
- 团队页会同时显示施工模式和拆解模式；
- 第一波没有模式切换按钮，只能在建团队时选择。

开工仍然 fail-closed：只要需要的 Worker、Leader 或 verifier 没准备好，服务端不会创建一条假运行任务。

## 10. 复验容器的安全边界

verifier 服务本身需要 Docker socket，因为它要创建一次性验证容器。这是一个高权限组件，因此必须把危险面限制住：

- 一次性容器不挂 Docker socket；
- 不传模型密钥、GitHub 写凭据、Matrix 凭据或对象存储凭据；
- 只挂本轮 scratch 子目录；
- 有 CPU、内存和命令超时；
- 跑完即销毁；
- 默认工具链镜像只有 Git、Python、Node 等测试工具，没有 coding agent。

原 spec 第一版为了安装依赖，暂定验证容器使用默认 bridge 网络；“哪些仓可以完全断网、依赖怎样缓存和镜像”仍是开放项。

## 11. 怎么分波实施

### 波次 0：先做实证，不改代码

在目前活着的环境中手工给 pricing-core Worker 放一份符合 v2 结构的任务包，再给 Leader 一份审阅包，并在中途重启一次 Worker。

必须回答三个问题：

1. CoPaw + DeepSeek 能不能独立完成多币种任务；
2. Worker 会不会照任务说明执行 init、test、bundle；
3. 容器重启后，它会不会继续向旧目录提交结果。

### 波次 1：最薄可用闭环

完成任务包、尝试状态、观察器、Leader 审阅、候选工作树、独立 verifier、开工门禁和前端显示，让一条新 issue 真正到达候选提交。

### 波次 2：产品化

增加团队工具链配置、按团队选 Worker 镜像、组织默认施工模式、可配置预算和更完整的执行面详情。

### 波次 3：从零复验

修完从零启动遗留问题，整拆环境后严格按 README 一条命令重新搭建，并再走到候选提交。

### 波次 4：启动逻辑归容器

把 AgentTeams 安装、token 获取、运行时配置和服务重启收进 bootstrap 容器；宿主脚本只做最小启动工作。

---

## 12. 明确不在第一波做的事

- Worker 的 RepoMesh 主体凭据和直连回调；
- 仓库团队在两种施工模式之间的完整切换状态机；
- 每个仓库或团队单独选择工具链镜像；
- 大仓库的浅 bundle 优化；
- 候选工作树的长期清理策略；
- 企业内网依赖镜像和完整网络策略；
- 测试团队联调轮的一次性隔离环境。

---

## 13. 当前仍需要复核的关键点

原文虽然写成了 D-n 决策，但以下内容会改变产品形态或复用边界，开工前仍值得单独确认：

1. Manager 到底继续作为真实 Agent，还是第一阶段只保留记录和人；
2. 施工模式是否应该同时决定拆解策略；
3. verifier 是否应该复用 `runner_dispatches`，还是拥有独立的验证调度；
4. `/health/ready`、`setup/status` 和仓库团队执行面三者的职责边界；
5. Worker 短暂不是 Running 时是否立即中断，还是先等心跳宽限期；
6. 验证容器的网络默认值；
7. 同一个仓库有多个 Task 时，后一个 Task 应基于哪个候选提交。

这份人话版只忠实解释原 spec，不代替用户对这些问题作最终裁决。
