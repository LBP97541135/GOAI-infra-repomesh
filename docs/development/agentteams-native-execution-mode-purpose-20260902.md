# RepoMesh 托管原生施工模式：产品目的与边界

> 日期：2026-09-02  
> 状态：设计讨论共识；已纳入 2026-09-02 的五项执行边界裁决，作为后续方案与契约设计的目的基线  
> 范围：只说明为什么做、要保留什么、两种施工模式如何分工；暂不冻结接口与施工细节

术语遵循仓库根目录 `CONTEXT.md`。本文使用“施工模式”描述仓库团队实际由谁完成代码施工；
“档案开关”仍只指测试团队的供给侧开关，不用于本文的模式选择。

## 1. 一句话目的

RepoMesh 保持组织、仓库团队、Task、组合、判据、验证、提交与交付的治理真相，
同时让 AgentTeams 原生 Agent 在其托管容器中成为唯一施工者；本地 coding CLI 则保留为另一种明确、可切换的施工模式。

## 2. 原始产品设想

AgentTeams 提供原生的多 Agent 编制与协作运行时：

- 一个组织由一个 Manager 编排；
- Manager 面向多支仓库团队派工；
- 每支仓库团队由一名队长和至少一名 worker 组成；
- AgentTeams 负责 Agent 进程、身份、团队关系、房间和容器生命周期。

RepoMesh 在其外部增加仓库与交付治理：

- 每支仓库团队锚定一个仓库；
- Issue、发现链、执行计划和开工由 RepoMesh 管理；
- Manager 冻结组合与判据，并向仓库团队派发 Task；
- RepoMesh 保存执行状态、验证结果、候选提交和最终交付事实；
- 房间负责协作与展示，不是 Task、权限或终态的真相源。

产品从一开始就需要两种施工模式：

1. **托管原生模式**：AgentTeams 原生 Agent 在 AgentTeams 管理的容器中施工；
2. **本地 CLI 模式**：外部成员通过 Bridge 使用操作者本机的 coding CLI 施工。

两种模式共享同一套 RepoMesh 治理，只替换实际施工者及其运行位置。

## 3. 当前实现偏离了什么

现有托管路径没有让 AgentTeams 原生 worker 直接施工，而是形成了两段式转交：

1. 原生 worker 在房间收到消息后调用 RepoMesh 的开始任务工具；
2. RepoMesh 准备宿主侧 worktree 并创建 Runner dispatch；
3. 另一个 RepoMesh Runner 再启动 Codex、Claude Code 等 coding CLI 真正修改代码。

这使房间里的 Agent 与真正施工的 Agent 变成两个运行实体，带来双重身份、双重就绪状态和脆弱的转交链。
实走已经证明：原生 worker 的调用凭据未被 RepoMesh 接受；即使绕过该门禁生成 dispatch，产品部署里也没有进程领取它。
最终表现为编制、房间和任务包都存在，但没有任何进程真正施工，计划长期停在假运行状态。

托管原生模式的重设计不是修补这次转交，而是取消不必要的第二施工者。

## 4. 目标产品形态

### 4.1 托管原生模式

- AgentTeams 原生 worker 是唯一施工大脑；
- worker 在自己的 AgentTeams 托管容器中工作；
- worker 可使用其原生 shell、编辑器与工具完成修改和测试；
- 容器内不再启动 Codex、Claude Code 或其他第二个 coding agent；
- 托管原生路径不依赖另一个 Runner 进程领取 dispatch；
- RepoMesh 提供 Task 分配与领取记录、任务级工作区、权限范围、判据、结果提交和独立复验能力；
- worker 不持有 GitHub 写凭据，不直接向正式仓库推送。

#### 4.1.1 队长职责

托管原生模式保留队长进程，但把队长收窄为**候选结果的第一道审阅者**，不再让它充当第二个调度器：

- RepoMesh 采用服务端拆解时，队长不重复拆任务，也不靠一条自然语言房间消息猜下一步；
- worker 提交候选补丁、变更清单和测试证据后，队长收到一个结构化审阅包；
- 队长只返回 `ACCEPT`、`REVISION` 或 `BLOCKED` 及理由；
- `ACCEPT` 只表示可以进入 RepoMesh 独立复验，不表示 Task 已经完成；
- `REVISION` 产生同一 Task 下的新施工尝试，原尝试随即封存；
- 队长无权修改判据、绕过平台复验、形成提交或推送仓库。

因此，队长房继续承载审阅记录和进度回放，而不是成为 Task 真相源或隐藏的启动开关。若托管原生模式声明需要队长审阅，则队长不可用应在开工门禁中直接暴露，不能静默绕过。

### 4.2 本地 CLI 模式

- 仓库团队成员以外部成员形态运行；
- Bridge 绑定 AgentTeams 身份、房间与本地 coding CLI；
- 本地 CLI 使用操作者已有的登录态、订阅和本机工具；
- readiness、单活、Task、工作区、验证和提交仍受 RepoMesh 治理。

本地 CLI 模式不是托管原生模式的补丁或兜底；它是正式的第二种施工模式。

## 5. RepoMesh 必须保持的治理不变量

无论采用哪种施工模式，下列事实与行为都必须保持一致：

1. RepoMesh PostgreSQL 是 Task、Run、验证、候选提交与交付状态的真相源；
2. AgentTeams 资源与房间是可重建的运行时投影，不反向成为业务真相；
3. Matrix 消息只能通知、请求或展示，不能授予权限、改变 assignee 或推进 Task 终态；
4. Manager 冻结组合与判据，仓库团队不得自行换钉或改变验收依据；
5. 每次施工必须绑定明确的 Task、worker、仓库、base commit、允许路径和判据；
6. 同一 worker 同一时刻最多有一个活跃施工 Run，同一 Run 同一时刻最多有一个有效尝试代次；
7. 每个外部副作用具有幂等键或明确重试策略；
8. worker 提交的是候选结果，不是未经验证的正式交付；
9. RepoMesh 必须在可信环境中独立检查父提交、修改路径与判据；
10. 只有 RepoMesh 接受的验证结果才能形成平台认可的候选提交并进入交付链。
11. 托管原生模式的模型访问由 AgentTeams 网关治理；RepoMesh 可以记录或约束模型策略，但不得把模型密钥写入任务包、共享任务目录、工作区或结果包，也不得向 worker 下发模型密钥。

## 6. 托管原生模式的概念执行链

```text
Manager 冻结组合与判据
  → RepoMesh 开工并创建 Task / Run / 尝试代次
  → RepoMesh 生成不可变任务包与源码引用
  → 房间消息唤醒 AgentTeams 原生 worker
  → worker 通过 AgentTeams 原生 ack_task 确认领取
  → RepoMesh 幂等摄取领取事件并推进本轮尝试
  → worker 在自己容器内的本地非同步工作区施工
  → worker 通过原生 submit_task 上传候选 patch 或 git bundle、测试证据或 BLOCKED 原因
  → 队长对结构化候选结果做第一道审阅
  → RepoMesh 复验器进程拉起一次性验证容器独立复验
  → 验证通过后形成平台认可的候选提交
  → RepoMesh 推进 Task、批次与交付状态
```

房间消息不是唯一启动依据。RepoMesh 必须记录通知投递与领取状态，并能幂等重试；
worker 最终只相信 RepoMesh 投影到原生任务协议中的 Task 与权限事实。

第一阶段不要求 worker 再向 RepoMesh 发起一次带主体凭据的领取调用。现有 `ack_task` 在改变任务状态前已经校验 Matrix 身份必须等于 `assigned_to`；元数据落盘的是唯一被分配者 `assigned_to` 和领取时间 `acknowledged_at`，并没有另一个独立的 `acknowledged_by` 字段。AgentTeams 共享任务目录在这里只是外部事件传输与证据面，RepoMesh 必须通过幂等收件箱把事件持久化后才能推进业务状态，不能直接把共享文件当成真相源。

第二阶段可以在同一个应用接口之后增加 worker 主体凭据和 RepoMesh 直连回调，替换第一阶段的共享目录观察适配器，而不改变任务状态机。这样先打通原生施工闭环，再增强端到端主体认证，避免把 RepoMesh Skill、主体凭据和 `mcporter` 鉴权故障放到首条关键路径上。

`ack_task` 只是领取事实，不是带续约的执行租约。每个任务包还必须带 RepoMesh 生成的尝试代次；超时、worker 容器重启或工作区丢失时，平台封存旧代次并创建新尝试，迟到结果因代次不匹配而被拒绝。

## 7. 工作区目的边界

托管原生 worker 在自己的容器中施工，但工作区仍由 RepoMesh 治理：

- AgentTeams 原生 worker 容器可以长期存在，以保留身份、房间连接和协作上下文；
- 每个施工尝试使用独立的任务级工作区，不能与其他尝试混用；
- 源码以钉死 base commit 的不可变包或 git bundle 进入工作区；
- 工作区必须位于容器本地、明确排除在对象存储后台同步和任务目录显式同步之外的路径；
- 不把宿主的宽泛目录暴露给 worker；
- 不向 worker 下发 GitHub 写凭据；
- AgentTeams 共享任务目录只允许保存控制元数据、候选 patch 或 git bundle、测试证据和 `BLOCKED` 原因，不得保存仓库 checkout、`.git`、依赖目录或构建缓存；
- 本轮结束后，候选结果进入 RepoMesh，任务工作区按策略清理；容器重启或重建都视为该尝试中断——只有重建才会丢失工作区，重启会保留工作区与未提交改动但丢失会话内存，worker 不会自发续做（2026-09-03 实证 S-6，2026-09-04 修订措辞）；
- 中断后从不可变源码输入创建新尝试和新工作区，旧尝试被 fencing，不得继续提交结果；
- RepoMesh 的最终复验必须在独立于 worker 工作区的新环境中完成。

第一阶段倾向于“长期 worker 容器 + 每轮独立工作区”，而不是每个 Task 再创建第二个施工容器，
避免重新产生房间 Agent 与施工实体分裂的问题。

### 7.1 独立复验的执行位置

独立复验不在 API 容器、AgentTeams worker 容器或 bootstrap 进程内直接运行。第一版新增一个专职的 **RepoMesh 复验器进程**，作为独立 compose 服务运行：

- 它消费 RepoMesh 已持久化的验证调度；
- 它必须报告可消费状态，并被纳入开工门禁；未就绪时不能创建一个无人消费的验证调度；
- 它持有创建验证容器所需的 Docker 能力，API 和 AgentTeams worker 不持有 Docker socket；
- 每个被队长 `ACCEPT` 的候选结果对应一个一次性验证容器；
- 验证容器按仓库工具链需求选择镜像，因而可以运行 Node、Python 或其他仓库真实需要的测试；
- 验证容器不加载模型、不运行编码 Agent、不加入 Matrix，只接收钉死的源码输入、候选结果和冻结判据；
- 验证结束后只回传结构化命令、退出码、日志摘要和证据，随后销毁容器与临时工作区。

领域和应用层只依赖“复验执行器”端口，Docker 是基础设施适配器。bootstrap 负责安装、配置和保证复验器服务存在，可以复用当前 Docker 接入能力，但不兼任验证任务的业务消费者。这样新增的是测试执行器，不是第二个编码 Agent，也不会再次留下“已生成调度但无人消费”的隐式环节。

`CONTEXT.md` 中的“一次性隔离环境”专指测试团队的一轮跨仓联调现场；单仓候选结果复验在本文中明确称为“一次性验证容器”，避免把两个生命周期不同的概念混为一谈。两者未来可以共享 Docker 执行适配器，但不共享业务状态。

## 8. 前端施工模式选择

前端应把两种路径呈现为仓库团队级的“施工模式”：

- `托管原生`；
- `本地 CLI`。

建议允许组织设置默认施工模式，并允许每支仓库团队覆盖。Issue 与开工确认界面显示本轮实际采用的模式及其就绪状态。

模式切换不是即时布尔翻转，而是受控状态迁移：

1. 停止向旧模式分配新 Task；
2. 有活跃 Run 时默认拒绝切换，除非先完成或明确取消；
3. 撤销旧执行实例的租约和凭据；
4. 准备并检查新模式的执行面；
5. 新模式通过就绪门禁后才正式激活；
6. 任何时刻不得有两个施工模式同时为同一 worker 接活。

仓库团队的业务身份、队长、worker、房间和历史 Task 不因模式切换而改变。

## 9. 保留范围与替换范围

### 保留

- Manager 与仓库团队的领域模型；
- 仓库团队与仓库的绑定；
- 队长、worker、团队房与队长房；
- 队长作为仓库团队内的候选结果审阅者；
- Issue、发现链、计划、批次与开工；
- Task、组合、判据、验证、候选提交和交付真相；
- 测试团队、测试资产仓与档案开关的既有语义。

### 替换

托管原生路径中，从 Task 已指派到候选结果回到 RepoMesh 之间的执行段：

- worker 如何发现和领取 Task；
- 源码如何进入 worker 容器；
- 任务级工作区和租约如何建立；
- 第二阶段 worker 主体凭据如何签发、投影和撤销；
- 进度、BLOCKED 和候选结果如何回传；
- RepoMesh 如何独立复验并形成候选提交。

原有“原生 worker 调开始工具 → 创建 Runner dispatch → 第二个 coding agent 施工”的路径不再用于托管原生模式。

## 10. 成功判据

本目的达成至少意味着：

1. 选择托管原生模式后，不启动任何本地 coding CLI，也无需操作者手工启动 Bridge；
2. AgentTeams 原生 worker 在自己的托管容器中真实修改代码并运行测试；
3. 队长能对候选结果返回结构化审阅结论，且不能替代 RepoMesh 的最终复验；
4. Issue 从开工到候选提交不依赖另一个无人领取的 Runner dispatch；
5. 执行面未就绪时，开工或派工明确失败，不产生假运行状态；
6. RepoMesh 能准确回答谁领取、何时开始、当前尝试是否仍有效；
7. 专职 RepoMesh 复验器能按仓库工具链拉起一次性验证容器并真实执行冻结测试；
8. 工作区、`.git`、依赖目录和构建缓存不会进入对象存储同步面；
9. 重复通知或网络重试不会产生并行施工；容器重启产生同一 Task 的新尝试，旧尝试的迟到结果不会形成重复提交或状态倒退；
10. worker 无权绕过组合、判据、允许路径和 RepoMesh 的最终复验；
11. 任何任务包、共享目录和结果包都不包含模型密钥；
12. 本地 CLI 模式继续可用，并与托管原生模式共享同一套任务与交付治理；
13. 前端可以明确选择、观察并安全切换仓库团队的施工模式。

## 11. 非目标

本文不决定：

- 具体 HTTP、MCP 或对象存储字段；
- 具体 AgentTeams 原生 runtime 选型；
- 每种语言或仓库的依赖镜像策略；
- 自动故障切换；
- 两种模式之间迁移原生会话；
- 在有活跃 Run 时无条件强制切换；
- 用 AgentTeams 或 Matrix 状态替代 RepoMesh 业务真相。

## 12. 后续需要冻结的设计项

后续方案与契约设计应依次裁决：

1. AgentTeams 原生 `ack_task` / `submit_task` 的事件摄取、幂等键、尝试代次、超时、fencing 和恢复协议；
2. 本地非同步工作区、源码包、任务包、候选结果与清理生命周期；
3. 队长的结构化审阅包与 `ACCEPT`、`REVISION`、`BLOCKED` 结果契约；
4. worker 的 `BLOCKED`、失败、完成、测试证据和候选补丁结果契约；
5. RepoMesh 复验执行器端口、验证调度、一次性验证容器、工具链镜像和候选提交生成协议；
6. 第二阶段每 worker 主体凭据、RepoMesh 直连回调、权限范围、投影和撤销；
7. 施工模式的持久模型、单活 generation 与切换状态机；
8. 前端创建、切换、就绪诊断与开工门禁体验。
