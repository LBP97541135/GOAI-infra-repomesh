## 4. 实现方案（对应赛题 5 项必答）

### 4.1 观测数据采集方式（三层 + 网关）

| 层 | 位置 | 手段 | 工作量 |
|---|---|---|---|
| 规划/编排（Python） | RepoMesh API + `repomesh-runner` | OTel SDK `setup_tracing` + `@traced` + 手写 span（**已写好**） | 仅需配 endpoint |
| **Agent 容器侧（补最大缺口）** | Higress 网关 | **Higress OTel wasm 插件**（网关层采集 LLM，不侵入容器）；可选 LoongSuite Pilot 装进 Agent 镜像补 Skill/MCP 内部调用 | 网关 1 天 + Pilot 半天 |
| CLI 子进程 | runner 内 claude/codex | LoongSuite JS hook + `OtelDriverObserver`（已接线） | 半天 |
| Log / Metrics | 全进程 | logging 结构化（注入 `trace_id`）+ OTel Metrics（token / 成本 / 延迟 / 成功率） | 1 天 |

> **Higress 网关 = 天然汇聚点**。所有 Agent 的 LLM 请求都经过 `key-auth` + `ai-route` + `ai-proxy` wasm，
> 在网关挂 OTel 插件，等价于"埋一个点覆盖 8 个容器"，同时拿到模型、token、provider、状态码，
> 是投入产出比最高的一步，也是与"纯 AgentScope 方案"差异化的加分项。

### 4.2 语义规范

- **OpenTelemetry GenAI 语义约定 v1.38**（已实现于 `deepseek.py`）：
  - `gen_ai.operation.name` = `chat` / `invoke_agent` / `execute_tool`
  - `gen_ai.request.model`、`gen_ai.provider.name`、`gen_ai.request.temperature`
  - `gen_ai.usage.input_tokens` / `output_tokens`、`gen_ai.response.finish_reasons`
  - `gen_ai.input.messages` / `output.messages`（截断 32 KiB 防膨胀）
- **自有命名空间 `repomesh.*`**（已冻结，`tests/test_telemetry.py` 兜底防改名）：
  `organization_id / project_id / changeset_id / repository_id / task_id / run_id /
  correlation_id / attempt / adapter / worker_agent_id`
- 建议新增三类 span 命名：`retrieval.<source>`（检索）、`skill.<name>`（Skill）、`mcp.<server>.<tool>`（MCP）
- 凭据约束：api_key、token 不得进入任何 span 属性（沿用 `runtime-planes.md` 的凭据序列化禁令）

### 4.3 数据类型

| 类型 | 内容 | 说明 |
|---|---|---|
| **Trace**（主打） | `chat` / `invoke_agent` / `execute_tool` / `retrieval.*` / `skill.*` / `mcp.*` | 覆盖 LLM、Skill、MCP、RAG 四项赛题要求 |
| **Log** | 结构化 JSON + `trace_id`；Matrix 消息、Agent 内部事件、审计（MCP `auditEveryCall`） | 补 trace 装不下的内容 |
| **Metrics** | token 用量、成本（$）、延迟分位、成功率、限流/欠费告警 | 支撑在线监控与告警 |

### 4.4 后端存储与检索方案

```
OTel SDK / Higress 插件 ──OTLP/HTTP──▶ Collector ──▶ 存储 ──▶ 查询 API
   短期：AgentScope Studio（零成本，认 GenAI 语义，只收 Trace）
   中期：自建 Collector（OpenObserve / OTel Collector + ClickHouse，收三类数据）
```

- 落库后由 `src/repomesh/modules/observability`（README 已定义职责：不可变审计 + trace 层级 +
  模型/工具用量 + 成本 + 交付时间线；现状 `status="planned"`）做 **durable projection + 查询 API**，
  前端 `EventTimeline` / `EvidenceModal` 消费
- 成本归因：按 `repomesh.run_id` 聚合 span token → 单 issue 成本（**直接支撑买套餐决策**）
- 检索：按 `task_id / run_id / repository_id / correlation_id` 索引，单条 trace 可回放

### 4.5 应用场景与效果

| 场景 | 效果 | 对应赛题点 |
|---|---|---|
| 在线监控与告警 | 欠费 502、模型 503、任务卡死、成功率骤降 → 分钟级告警 | 在线监控与告警 |
| 成本核算 | 按 issue / 仓库 / agent 聚合 token 与费用 | 评估与优化 |
| 推理质量回放 | `confirmation` 的输入输出在 span 上可回放，区分判定对错 | 评估与优化 |
| 效率瓶颈定位 | 延迟分位 + 阶段耗时瀑布（规划 s 级 / 执行 min 级） | 评估与优化 |
| 离线评估 | 与 `scoring.py` 联动（见 4.6） | 实时或离线评估 |

### 4.6 评估落地（观测驱动的评估）

现有 `datasets/train-ticket/scoring.py` 已能对 15 个用例算 recall / precision / F1，
但只消费 discovery 的输出文件。升级路径：

1. 从 trace 抽取 `planning.discovery` / `planning.confirmation` 的输入输出（`gen_ai.input/output.messages`）
2. 与 `validation_cases.json` 的三层 ground truth（direct 0.6 / propagated 0.2 / context 0.2）对齐
3. 每轮运行自动生成 `predictions/*.json` → 跑 `scoring.py` → 结果写回观测库
4. 形成"判定置信度 vs 实际命中"校准曲线，量化推理效果与效率
