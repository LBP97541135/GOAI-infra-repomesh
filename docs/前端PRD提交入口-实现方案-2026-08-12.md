# 前端 PRD 提交入口 — 实现方案

> 日期：2026-08-12
> 状态：已确认，开始实现
> 范围：前端补全（`web/`），后端零改动

## 背景与目标

后端 repository_intelligence 的方案制定链路已完整实现并挂载于 `/api/v1`（`requirement-analysis` → `discovery` → `confirmation` → `integration`），PRD 文本即各端点的 `requirement` 字段。但前端仅有「人工审核台 / 创建项目 / 人员与权限」三个视图，`web/src/api.ts` 未封装该链路，缺少「提交 PRD」入口。

本方案在现有前端新增「提交 PRD」视图，打通 **PRD → 需求分析 → 仓库发现 → TM 确认 → 集成方案 → 派发执行** 全流程。

## 产品流程（2026-08-12 调整）

> 根据评审反馈：PRD 入口不放在左侧独立导航，而是**项目工作台**内。

1. 「创建项目」页绑定 AgentTeams 组织/仓库团队 → 点击「创建项目并启动 Agent」
2. 创建成功后跳转到 **项目工作台**（新视图 `Workspace`）
3. 工作台含两个选项卡：
   - **方案制定（提交 PRD）**：四步向导（PRD → 发现 → 确认 → 集成方案）
   - **派发执行 · 与 Leader 交互**：展示绑定 Leader/仓库团队，将集成方案 `materialize` 派发给仓库 Leader（生成任务 + 对接文档进人工审核台）

## 后端接口依赖（已存在，零改动）

| 步骤 | 端点 | 请求要点 | 响应要点 |
|---|---|---|---|
| 0 | `POST /api/v1/requirement-analysis` | `{requirement}` | sufficient / confidence / missing_dimensions / questions / extracted_keywords |
| 1 | `POST /api/v1/discovery` | `{requirement, limit, entry_point}` | DiscoveryCandidate[]：repository_id / repository_name / score / matched_terms / rationale / is_entry_point |
| 2 | `POST /api/v1/confirmation` | `{requirement, candidate_repos, discovery_evidence, limit}` | required[] / maybe[] / excluded[]（含 plan 变更明细）、supplemented_repos、final_repos |
| 3 | `POST /api/v1/integration` | `{requirement, confirmation}` | engineering_spec / contracts[] / task_dag[] / execution_batches[] |

LLM 依赖 `.env` 的 `DEEPSEEK_API_KEY`，已配置。所有端点无需认证。

## 组件设计：PrdPlanner 分步向导

整体复用现有视觉体系（`.content` / `.section-head` / `.step` / `.form-section` / `.action-bar` / `.primary` 等），四步纵向排布，仿 `ProjectSetup` 的步进徽章（step 01/04 …）。

### Step 1 提交 PRD
- 大 `textarea`（`minLength 3`、`maxLength 20000`，实时字数）
- 「需求分析」按钮 → `requirement-analysis`，展示分析面板：
  - 充分性徽章（sufficient → 绿 / 红）
  - 缺失维度 chips、待澄清问题列表、提取关键词 chips
- 「开始发现仓库」→ 校验长度后进入 Step 2

### Step 2 仓库发现
- 调 `discovery`，渲染候选仓库卡片：
  - 仓库名 + 入口点星标（is_entry_point）
  - 分数条（0–100）
  - matched_terms tags、rationale
- 每张卡勾选框（默认全选），记录 `discovery_evidence[repo] = [[term, score], ...]`
- 「进入 TM 确认」→ 提交勾选的 `candidate_repos` + evidence

### Step 3 TM 确认
- 调 `confirmation`，三组展示：required（绿）/ maybe（黄）/ excluded（灰）
- 每张卡：状态、置信度、理由、plan 明细（变更 API / 模块 / 依赖 / 影响 / 风险标签）、缺失依赖
- 「生成集成方案」→ 回传完整 confirmation 响应

### Step 4 集成方案
- 调 `integration`，展示：
  - `engineering_spec`：等宽字体、可滚动
  - 契约表：producer → consumer / interface / agreement
  - task DAG：仓库、指令、depends_on、parallelizable_with、tests
  - 执行批次：批次序号 → 仓库 chips

### 通用行为
- 每步结果缓存 state；修改 PRD 重跑将清空后续步骤结果
- LLM 调用耗时（10–30s）：按钮 loading（「分析中…」「发现中…」）并禁用
- 错误展示于 `form-message`（透传后端 `detail`）
- 底部 `action-bar` 常驻：PRD 字数 + 当前步骤主按钮

## 边界说明

- **materialize 已接入**「派发执行」选项卡：使用创建项目时的 `project_id` + 组织 `leader_agent_id`，幂等前缀 `ui-{projectId}`。派发为真实副作用（写库、发 Matrix 任务、写 `.agentteams-storage`、生成 handoff 文档进人工审核台），测试时注意。
- **不做 PRD 落库 / 历史记录**：后端无此能力，跨模块改动需先定契约。
- **与 Leader 对话**（Matrix 会话式聊天）：后端暂无 HTTP 端点，第一版以「派发执行」作为 Leader 交互动作；会话式交互后续基于 messenger 扩展。

## 验证方式

1. 起后端：`uvicorn repomesh.main:app --port 8001`
2. 起前端：`npm run dev`（5173，vite 代理 `/api` → 8001）
3. 登录后进入「提交 PRD」，用真实需求跑四步
4. 用 `GET /api/v1/dependency-graph`、`GET /api/v1/repositories` 交叉验证发现结果合理性
5. 回归：人工审核台 / 创建项目 / 人员与权限三页不受影响
6. 前端构建验证：`npm run build` 通过（TS 严格模式）
