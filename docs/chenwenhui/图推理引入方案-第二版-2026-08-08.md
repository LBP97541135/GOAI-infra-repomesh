# 图推理引入方案：第二版架构升级

> 创建时间：2026-08-08
> 模块：repository_intelligence
> 状态：方案设计（经两轮第一性原理对抗性审查）

---

## 一、问题定义

### 1.1 当前 MVP 的局限

当前架构中，confirmation（确认 + 方案）和 integration（整合 DAG）全靠 LLM 从 AutoCard 的文本信息推断：

- TM 确认时，LLM 要猜 `impacts`（"谁在调我的 API"）——TM 只看自己的 AutoCard，没有反向依赖数据
- Leader 整合时，LLM 要从所有 TM 的 `depends_on`/`impacts` 文本推断 Contract 配对和 DAG 执行顺序——在不可靠的文本上再推理一层，错误会放大

### 1.2 核心洞察

多仓库变更协调做三件事：

1. **确定要改哪些仓库**（语义问题——需求文本 → 仓库集合）
2. **确定仓库间的结构关系**（确定性问题——谁依赖谁、谁影响谁、什么顺序执行）
3. **确定每个仓库具体改什么**（语义问题——Contract 内容、Engineering Spec、instruction）

当前 MVP 把三个问题全交给 LLM。第二版的核心改动：**第 2 步是确定性的，应该从 LLM 手里拿出来，交给图推理。**

---

## 二、边界细化

第 2 步不是完全确定性的。拆开看：

| 子问题 | 是否确定性 | 原因 |
|--------|-----------|------|
| 仓库 A 依赖仓库 B（有调用关系） | 大部分确定 | AutoCard.deps 和 exposed_apis 可推断 |
| 仓库 A 的某次具体变更会影响 B | 不完全确定 | 需要 API 级别调用链分析，AutoCard 粒度不够 |
| 仓库 A 和 B 之间需要 Contract | 不完全确定 | 有依赖关系 ≠ 这次变更需要 Contract（可能改的 API 和对方无关） |
| 执行顺序（DAG 拓扑排序） | 完全确定（前提：边确定） | 拓扑排序是纯算法 |

**精确结论**：图推理能确定"谁和谁有依赖关系"和"拓扑顺序"，但不能确定"这次变更是否真的影响对方"和"是否需要 Contract"。后者仍需 LLM 语义判断。

图推理提供的是**候选集和约束**，不是最终答案。LLM 在图的约束下做语义判断。

---

## 三、最终职责分工

| 职责 | 由谁做 | 性质 |
|------|--------|------|
| 需求 → 仓库发现 | LLM | 语义 |
| 确认"是否要改" | LLM | 语义 |
| 确认"具体改什么"（plan_summary, changed_apis） | LLM | 语义 |
| 反向依赖（impacts） | 图推理 | 确定（catalog 内） |
| Contract 候选对 | 图推理 | 确定（有依赖边的仓库对） |
| Contract 是否需要 | LLM | 语义（基于具体变更的 API） |
| Contract 具体内容 | LLM | 语义 |
| DAG 拓扑排序 | 图推理 | 确定（纯算法） |
| Task instruction | LLM | 语义 |
| Engineering Spec | LLM | 语义 |
| 补充图中遗漏的依赖 | LLM | 语义 → 可补充边 |

LLM 从"猜结构 + 填内容"变成"只填内容"。结构是确定性的，由图查询保证；内容是语义性的，由 LLM 生成。

## 四、三个介入点

### 4.1 介入点 1：confirmation——给 TM 提供反向依赖

**现在**：TM 的 prompt 只有自己的 AutoCard，LLM 要猜 impacts（"谁可能调我的 API"）。

**第二版**：图查反向依赖，提供确定结果。

```
图查询：reverse_dependencies(ts-order-service)
→ 返回：[ts-notification-service, ts-billing-service]
  （这两个仓库的 deps 里包含 ts-order-service）

prompt 增加：
  ## Reverse Dependencies (graph-derived, not guessed)
  These repos depend on yours:
  - ts-notification-service
  - ts-billing-service
```

TM 不再猜 impacts——图直接给答案。LLM 集中到"这个需求是否真的需要改我的仓库"和"具体改什么"。

### 4.2 介入点 2：integration——给 Leader 提供确定的 Contract 候选对

**现在**：Leader 靠 LLM 从各 TM 的 `depends_on` 文本推断谁和谁需要 Contract。

**第二版**：图查正向边，提供确定的候选对。LLM 只需判断哪些候选对真的需要 Contract（基于这次变更的具体 API），并写约定内容。

```
图查询：edges(confirmed_repos)
→ 返回确定的有向边：
  ts-order-service → ts-auth-service
  ts-notification-service → ts-auth-service
  ts-notification-service → ts-order-service

LLM 的任务变为：
  - 对每条边判断：这次变更是否需要 Contract？（是/否）
  - 如果是，写 Contract 的具体约定内容
```

### 4.3 介入点 3：integration——给 Leader 提供确定的 DAG 排序

**现在**：Leader 靠 LLM 推断执行顺序。

**第二版**：图做拓扑排序，返回确定的执行批次。LLM 只需为每个仓库写 instruction。

```
图查询：topological_batches(confirmed_repos)
→ 返回确定的执行批次：
  Batch 1: ts-auth-service (无外部依赖)
  Batch 2: ts-order-service (依赖 auth)
  Batch 3: ts-notification-service (依赖 order + auth)
```

## 五、数据来源与图构建

### 5.1 数据来源

AutoCard 的 `deps`（依赖列表）和 `exposed_apis`（暴露的 API）。当前这些是扁平文本列表，没有被组织成图结构。

```
ts-order-service:
  deps: ["ts-auth-service", "ts-notification-service", "redis-driver"]
  exposed_apis: ["/api/v1/orders", "/api/v1/orders/{id}"]

ts-notification-service:
  deps: ["ts-auth-service", "redis-driver"]
  exposed_apis: ["/api/v1/notifications"]
```

### 5.2 边构建逻辑

从 deps 提取有向边，匹配规则是"dep 字符串匹配 catalog 中已注册的仓库名"。

```python
def _build_graph(self, profiles):
    names = {p.name for p in profiles}
    edges = {}  # name -> {confirmed: [...], possible: [...]}
    for p in profiles:
        if not p.auto_card:
            continue
        for dep in p.auto_card.deps:
            # 精确匹配
            if dep in names and dep != p.name:
                edges.setdefault(p.name, {}).setdefault("confirmed", []).append(dep)
                continue
            # 模糊匹配（子串 + 后缀）
            for name in names:
                if name != p.name and self._fuzzy_match(dep, name):
                    edges.setdefault(p.name, {}).setdefault("possible", []).append(name)
    return edges
```

### 5.3 匹配策略

| 匹配方式 | 置信度 | 示例 |
|---------|--------|------|
| 精确匹配 | confirmed | dep="ts-auth-service" == repo name |
| 子串匹配 | possible | dep="github.com/org/ts-auth-service" 包含 "ts-auth-service" |
| 后缀匹配 | possible | dep="@team/auth-service" 后缀匹配 "auth-service" |

**匹配策略从宽**：宁可 False Positive（多余的候选边，LLM 可过滤），不要 False Negative（遗漏真实依赖边，导致并行执行出错）。

### 5.4 名称不一致问题

仓库名 `ts-auth-service` 可能在 dep 里写成 `@team/auth`、`auth-service`、`github.com/org/ts-auth-service`。精确匹配会漏掉这些。

**应对**：
1. 多级匹配（精确 → 子串 → 后缀 → 编辑距离）
2. 匹配结果标记置信度（confirmed / possible）
3. 保留 confirmation 的 `missing_dependencies` 兜底——TM 发现图没覆盖到的依赖时仍可上报

## 六、对抗性审查发现的问题与应对

### 6.1 有依赖边 ≠ 需要 Contract

A 依赖 B，但这次只改了 B 的 `/api/v1/billing`，A 只调用 B 的 `/api/v1/auth`。有依赖边但这次不需要 Contract。

**应对**：图给候选对，LLM 判断是否真的需要。图不强制 Contract，只提供候选集。

### 6.2 环依赖

A 依赖 B，B 依赖 A。拓扑排序遇到环会失败。

**应对**：检测到环时，环内仓库放同一 batch（标记为"需要同时改"），或降级到 LLM 推理。

### 6.3 LLM 发现图中不存在的依赖

如果 A 通过反射或动态配置调用 C，图中没有 A→C 边。

**应对**：LLM 可以补充边，但不能推翻图已有的边。最终边集 = 图的 confirmed 边 + 图的 possible 边（LLM 确认后升级）+ LLM 补充的新边。排序基于最终边集。

### 6.4 low_signal 仓库

AutoCard `low_signal=True` 的仓库没有 deps 和 exposed_apis 数据，图建不出边。

**应对**：图推理是增强器，不是替代器。有图数据 → 图确定结构，LLM 填语义。没图数据 → 退化到 MVP 行为（LLM 猜）。两条路径共存。

### 6.5 catalog 外的调用者

图推理只能发现 catalog 内的反向依赖。catalog 外的调用者（未注册的仓库）发现不了。

**应对**：这不是图推理的缺陷——当前 LLM 猜测同样发现不了 catalog 外的调用者。图推理至少保证 catalog 内的完整性。catalog 外的覆盖靠 `missing_dependencies` 机制。

## 七、具体实现

### 7.1 新增组件：DependencyGraphService

```python
@dataclass(frozen=True, slots=True)
class GraphEdge:
    producer: str
    consumer: str
    confidence: str  # "confirmed" | "possible"
    match_reason: str  # 审计日志："exact match" | "substring: dep contains name"


class DependencyGraphService:
    """从 RepositoryProfile 的 AutoCard 构建依赖图，提供图查询。"""

    def __init__(self, profiles: list[RepositoryProfile]):
        self._edges = self._build_edges(profiles)
        self._reverse = self._build_reverse_index()

    def reverse_dependencies(self, repo_name: str) -> list[GraphEdge]:
        """谁依赖我？（impacts 的确定来源）"""

    def forward_dependencies(self, repo_name: str) -> list[GraphEdge]:
        """我依赖谁？（depends_on 的确定来源）"""

    def edges_in(self, repos: list[str]) -> list[GraphEdge]:
        """在给定仓库集合内的所有有向边。"""

    def topological_batches(
        self, repos: list[str]
    ) -> list[list[str]]:
        """拓扑排序，返回执行批次。检测环时同一 batch 处理。"""
```

约 150-200 行代码。

### 7.3 plan_integration.py 接入

```python
class PlanIntegrationService:
    def __init__(
        self,
        llm: LLMClient,
        graph: DependencyGraphService | None = None,  # 新增
    ):
        ...

    def integrate(self, requirement, summary) -> IntegratedPlan:
        if self._graph:
            return self._integrate_with_graph(requirement, summary)
        else:
            return self._integrate_with_llm(requirement, summary)  # 原 MVP 逻辑
```

`_integrate_with_graph` 流程：

```
1. confirmed = summary.final_repos
2. edges = graph.edges_in(confirmed)        # 图确定边
3. batches = graph.topological_batches(confirmed)  # 图确定排序
4. prompt = build_graph_assisted_prompt(requirement, summary, edges, batches)
5. raw = llm.chat(prompt)                    # LLM 只写语义内容
6. result = merge_graph_and_llm(edges, batches, raw)  # 图的 edges/batches 优先
```

prompt 变化：

```
现在（MVP）：
  你要推断：
  1. 谁和谁之间需要 Contract
  2. 执行顺序是什么
  3. Engineering Spec
  4. 每个 Task 的 instruction

第二版：
  图推理已确定：
  - 依赖边：ts-order → ts-auth, ts-notification → ts-auth, ts-notification → ts-order
  - 执行批次：[ts-auth], [ts-order], [ts-notification]

  1. Engineering Spec
  2. 对每条边判断是否需要 Contract（是/否），如果是需要则写具体约定内容

```

### 7.4 container.py 接入

```python
def dependency_graph(self) -> DependencyGraphService | None:
    profiles = await self.repository_catalog.list()
    if not profiles:
        return None
    return DependencyGraphService(profiles)

async def confirmation_service(self, llm_client: LLMClient) -> ConfirmationService:
    profiles = await self.repository_catalog.list()
    by_name = {p.name: p for p in profiles}
    graph = DependencyGraphService(profiles) if profiles else None
    return ConfirmationService(llm_client, by_name, graph=graph)

def plan_integration_service(self, llm_client: LLMClient) -> PlanIntegrationService:
    # graph 需要在调用时注入（因为 profiles 在变化）
    return PlanIntegrationService(llm_client, graph=self._graph_cache)
```

### 7.5 渐进式迁移

| 步骤 | 改动 | 风险 | 可回退 |
|------|------|------|--------|
| 1. 新增 DependencyGraphService | 纯新增 | 无 | 不接入即可 |
| 2. confirmation 接入图 | prompt 增加一个 section | 低 | graph=None 回退 |
| 3. integration 接入图 | DAG 排序用图结果 | 中 | graph=None 回退 |
| 4. 移除 LLM 的结构推断职责 | prompt 简化 | 需验证 | 保留旧 prompt fallback |

每一步通过 `graph=None` 回退到当前 MVP 行为。没有破坏性变更。

## 八、MVP vs 第二版对比

| 维度 | MVP（LLM 全包） | 第二版（图 + LLM） |
|------|----------------|-------------------|
| impacts 准确率 | LLM 从自己的 deps 猜"谁可能调我" | 图查反向边，catalog 内完整覆盖 |
| Contract 配对 | LLM 从所有 TM 的 depends_on 文本推断 | 图提供候选对，LLM 只判断 + 填内容 |
| DAG 排序 | LLM 排序，可能出现循环或遗漏依赖 | 拓扑排序保证无环，覆盖所有图内边 |
| prompt 聚焦度 | LLM 需要推理结构 + 内容 | LLM 只写内容，prompt 更聚焦 |
| 可解释性 | LLM 黑盒 | 图边可审计（匹配理由日志），错误可定位 |
| 复杂度增量 | — | 一个 Service 类，约 200 行 |
| 回退能力 | — | graph=None 退化到 MVP |

## 九、API 端点变化

第二版不需要新增端点。图的构建在 container 工厂方法中自动完成（从 catalog 提取 profiles）。

调用方感知到的变化：
- `/confirmation` 返回的 `impacts` 字段更准确（catalog 内确定覆盖）
- `/integration` 返回的 `contracts` 和 `execution_batches` 更可靠（图保证无环、无遗漏）

可选新增端点：

```
GET /api/v1/dependency-graph
→ 返回当前 catalog 的完整依赖图（可视化 + 调试用）
```

## 十、后续演进

图推理建立后，可以进一步细化边的数据来源：

| 阶段 | 边数据来源 | 精度 |
|------|-----------|------|
| 第二版（当前） | AutoCard.deps 的名字匹配 | 仓库级，有 FP/FN |
| 第三版 | 代码扫描的 import/require 分析 | 文件级，精确 |
| 第四版 | 运行时调用链（APM trace） | API 级别，最精确 |

第二版用 AutoCard 的名字匹配启动，投入产出比最高。后续随着扫描能力增强，图的数据质量会自动提升——DependencyGraphService 的接口不变，只是 `_build_edges` 的实现更精确。
