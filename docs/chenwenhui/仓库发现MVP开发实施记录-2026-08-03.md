## 三、关键技术决策

### 3.1 为什么不删老字段

老字段（name/url/description/topics/languages）全部保留，理由：
- 零成本：有就给 LLM 看，没有不报错
- 渐进迁移：有些仓库可能还没跑 scan.py，只有人工填的信息
- `searchable_text` 属性同时纳入两套数据，关键词 fallback 也能利用 AutoCard 信息

### 3.2 为什么不改数据库表结构

RepositoryRecord 已有 `metadata_payload`（JSONB）字段。AutoCard 存在 `metadata_payload["auto_card"]` 下即可，不需要 ALTER TABLE。读取时反序列化挂回 profile。

### 3.3 为什么用 Protocol 而不是 ABC

`LLMClient` 用 `typing.Protocol`，这样测试时传入的 mock 对象不需要显式继承任何基类——鸭子类型。生产用 `DeepSeekClient` 实现该协议。

### 3.4 为什么 httpx 懒导入

`DeepSeekClient.chat()` 方法内部 `import httpx`，而不是在模块顶部导入。这样 domain 层保持纯净——单元测试不需要安装 httpx，只有真正调 LLM 时才需要。

### 3.5 CLI 为什么用 JSON 文件而不是数据库

MVP 阶段临时 CLI 的目的是验证核心逻辑（scan → AutoCard → LLM 推理 → 候选输出）。引入 PostgreSQL 会增加环境依赖，拖慢验证速度。用 `.repomesh_registry.json` 文件做持久化，`scripts/repomesh_cli.py` 完全自包含。正式 API 走 PostgreSQL 不变。

## 四、AutoCard 数据结构

```python
@dataclass(frozen=True, slots=True)
class AutoCard:
    top_dirs: tuple[str, ...] = ()         # 仓库 2 层目录结构
    deps: tuple[str, ...] = ()             # 依赖文件里声明的包列表
    recent_commits: tuple[str, ...] = ()   # 最近 5 条 commit message
    exposed_apis: tuple[str, ...] = ()     # 扫描到的 API 路由
    low_signal: bool = False               # 信息量不足标记
```

## 五、low_signal 评分逻辑

```
信息量评分 = 0
+0.3  if 仓库名包含业务关键词（pay/order/user/auth 等 30+ 个）
+0.3  if 任何目录名是非泛命名（非 src/lib/test/handler 等 25 个泛名）
+0.2  if 任何依赖是非框架包（非 fastapi/express/redis 等 30 个泛依赖）
+0.2  if 任何 commit message 是具体的（非 "fix bug" / "update" / "wip" 等）

score < 0.3 → low_signal = True
```

## 六、LLM Prompt 设计

### System message

设定角色：大型工程组织的仓库发现助手。给出 JSON 数组格式要求（repository / confidence / rationale），禁止 markdown fence。

### User message

```
## Repository Catalog

### order-service
- url: https://github.com/org/order-service
- description: Order management
- top_dirs: src/api, src/models, src/orders
- dependencies: fastapi, sqlalchemy, stripe
- recent_commits: feat: add multi-currency | fix: cart total calculation
- exposed_apis: fastapi:/api/v1/orders, fastapi:/api/v1/cart

### payment-service
- url: https://github.com/org/payment-service
- description: Payment processing
- low_signal: TRUE (information may be insufficient)

## Requirement

Add a new payment method to checkout

⚠️ The following repositories have insufficient information (low_signal)...
payment-service

## Task

Return the JSON array now.
```

## 七、JSON 容错解析流程

```
raw LLM response
  │
  ├─ 尝试剥离 ```json ... ``` markdown 围栏
  │
  ├─ 提取第一个 [ 到最后一个 ] 之间的内容
  │
  ├─ json.loads
  │   ├─ 成功 → 继续
  │   └─ 失败 → 自纠正重试（把错误响应 + 修正指令丢回 LLM），再解析一次
  │
  ├─ 遍历数组元素，过滤掉不在注册表里的仓库名（幻觉过滤）
  │
  ├─ confidence 裁剪到 [0, 1]
  │
  └─ 按 repository 去重（保留最高 confidence），按 confidence 降序排序
```

## 九、环境依赖说明

### 运行时需要

| 依赖 | 说明 |
|------|------|
| Python 3.12+ | 项目 `pyproject.toml` 要求 `>=3.12`，现有代码用了 `StrEnum` / `datetime.UTC` |
| `pip install -e ".[dev]"` | 安装项目本身 + 测试依赖 |

### 不需要

| 不需要 | 原因 |
|--------|------|
| PostgreSQL | pytest 用 SQLite (aiosqlite)，CLI 用 JSON 文件 |
| AgentTeams Controller | 测试用 MockCodingAgent |
| DeepSeek API Key | 不设 key 时自动走关键词 fallback |

### CLI 使用示例

```bash
# 扫描本地仓库
python scripts/repomesh_cli.py scan ./components/agentteams/hermes

# 注册仓库（自动扫描）
python scripts/repomesh_cli.py register \
    --name hermes \
    --url https://github.com/example/hermes \
    --path ./components/agentteams/hermes

# 发现（关键词 fallback）
python scripts/repomesh_cli.py discover "Matrix messaging integration"

# 发现（LLM 推理）
$env:DEEPSEEK_API_KEY="你的key"
python scripts/repomesh_cli.py discover "Matrix messaging integration"

# 查看已注册
python scripts/repomesh_cli.py list
```
