# DAG 动态更新方案：多 Agent 计划版本管理与协调

> 创建时间：2026-08-08
> 模块：repository_intelligence × task_orchestration × specification
> 状态：方案设计

---

## 一、问题定义

当 Leader 通过 PlanIntegrationService 生成了 IntegratedPlan（DAG），并通过 PlanExecutionBridge 分发给各 Team Manager 后，执行过程中 TM 会发现计划有误——依赖缺失、scope 变化、API 契约对不上。此时需要回答四个问题：

1. **什么时候**接受 TM 的反馈来触发计划更新？
2. **怎么**调整 DAG？
3. **怎么**协调多个 TM 拿到的计划版本？
4. 别人是怎么做的？

## 二、业界真实数据

### 2.1 各系统机制对比

| 系统 | 触发方式 | DAG 可变性 | 版本一致性策略 | 冲突解决 |
|------|---------|-----------|--------------|---------|
| **Augment / Intent** | Living Spec 变更自动传播 | 可变，Coordinator 重算依赖图 | Git Worktree 隔离 + 顺序合并 | 文件级隔离预防；顺序 git merge 解决 |
| **Devin** | 遇阻时推理式重规划（事件驱动） | 可变，"计划是起点不是合同" | 持久工作记忆，无并发 | 四策略：调查 / 修复 / 记录继续 / 升级 |
| **Magentic-One** | 停滞检测（连续 N 步无进展） | 可变，整体替换计划 | 双账本（Task Ledger + Progress Ledger） | 中心化 Orchestrator 决策 |
| **LangGraph** | 节点返回 Command(goto=...) | 可变（动态边）+ 不可变 checkpoint | 不可变 checkpoint 链 + Fork | 顺序 superstep，无并发写 |
| **AutoGen** | 发布/订阅消息驱动 | GraphFlow 支持循环图 | 单线程运行时 | 中心化消息编排 |
| **ChatDev / MetaGPT** | 阶段转换（瀑布式） | 不可变，无执行中重规划 | 共享消息池 | 无（顺序流水线） |

数据来源：Augment Code 官方架构指南<sup>[1]</sup>；Devin 技术分析<sup>[2]</sup>；Magentic-One 论文 (arXiv:2411.04468)<sup>[3]</sup>；LangGraph 官方文档<sup>[4]</sup>；AutoGen v0.4 设计文档<sup>[5]</sup>。

### 2.2 关键发现

**发现一：没有一个主流系统实现了真正的分布式并行 DAG 修改。**

全部通过"中心化编排器 + 隔离执行 + 顺序合并"回避了这个问题。Augment 的 Coordinator、Devin 的单 agent 执行、Magentic-One 的 Orchestrator、AutoGen 的 GroupChatManager、LangGraph 的单线程 superstep——都是单写入者模式。

**发现二：协调失败是多 agent 系统最大的失败来源。**

调研覆盖 AutoGen、CrewAI、LangGraph 的失败案例，协调失败占所有失败的 **36.94%**<sup>[6]</sup>。主要失败模式包括：消息路由错误、agent 间状态不一致、死锁等待。

**发现三：事件驱动是共识，但"事件"的定义差异很大。**

从最简单的"消息到达"（AutoGen）到复杂的"连续 N 步质量下降"（Magentic-One 停滞检测），再到"agent 完成工作时 Living Spec 自动更新"（Augment）。GraSP 论文定义的五种图修复原语（Rebind、InsertPrereq、Substitute、Rewire、Bypass）代表了最细粒度的事件驱动恢复<sup>[7]</sup>。

**发现四：CRDT / OT 在多 agent 编码系统中没有生产级先例。**

Augment、Devin、LangGraph、AutoGen、CrewAI、MetaGPT 均未使用 CRDT 或 OT。原因在于多 agent 编码系统的冲突本质是语义冲突（"这个 API 该不该改"），而非文本冲突。CRDT 解决数据结构冲突，解决不了语义冲突。语义冲突需要 LLM 推理或人类判断。

### 2.3 架构成熟度分层

```
层级 4（理论最优，尚未实现）：CRDT/OT 分布式合并 + 向量时钟一致性
           未来方向
层级 3（新兴）：事件溯源 + CQRS + 投影 + 快照
           LangGraph checkpoint 接近此层
层级 2（当前最佳实践）：不可变 checkpoint + 中心化编排器 + 隔离执行 + 顺序合并
           Augment/Intent、Magentic-One
层级 1（主流）：中心化编排器 + 共享状态 + 顺序执行
           Devin、AutoGen GroupChat、CrewAI Hierarchical
层级 0（基础）：固定流水线 + 无执行中重规划
           ChatDev、MetaGPT 基础版
```

## 三、第一性原理推导

### 3.1 本质问题

DAG 更新是一个**分布式状态一致性问题**。多个 TM 各自执行计划的一部分，发现需要修改计划。核心矛盾在于：

**谁有权改计划？谁保证所有人的计划版本一致？**

### 3.2 三条路径

| 路径 | 做法 | 代价 | 先例 |
|------|------|------|------|
| **A. 中心化编排** | 所有反馈上报 Leader，Leader 统一重算 DAG | 单点瓶颈，延迟高 | Augment、Devin、Magentic-One |
| **B. 事件溯源 + 投影** | 计划变更是不可变事件，当前计划是事件重放的投影 | 复杂度高，无界日志 | LangGraph checkpoint |
| **C. CRDT/OT 分布式合并** | 每个 TM 本地修改，自动合并 | 数学复杂，语义冲突无法自动解决 | 无生产级先例 |

### 3.3 为什么不选路径 C

1. **无先例**：调研覆盖 6 个主流系统，无一使用 CRDT/OT。
2. **语义冲突不可自动合并**：两个 TM 对同一个 API 的不同修改方案，CRDT 只能让两者"都保留"或"后写覆盖先写"，无法判断哪个方案正确。这需要 LLM 推理或人类判断。
3. **实现成本极高**：需要设计计划 DAG 的 CRDT 数据结构、处理向量时钟、实现合并协议。投入产出比不合理。

### 3.4 为什么 MVP 选路径 A

1. **有充分先例**：Augment、Devin、Magentic-One 都选了这条路径，验证了可行性。
2. **实现简单**：Leader 是单写入者，天然避免并发冲突。
3. **MVP 阶段 Task 数量有限**（10-30 个），全量重规划成本可控。
4. **大多数 Task 不需要重规划**：Magentic-One 的数据显示，只有 BLOCKED 才触发重规划，大多数 Task 正常完成。

### 3.5 为什么中期演进到路径 B

1. **Task 数量增长时全量重规划成本上升**：50+ Task、5+ Team 时，全量重规划的 LLM 调用成本和延迟会超过增量更新。
2. **事件溯源提供时间旅行调试**：可以回溯到任意时间点的计划状态，对调试多 agent 失效非常有价值。
3. **LangGraph checkpoint 已验证可行性**：SqliteSaver / PostgresSaver 在每步后写 checkpoint，实现暂停-恢复和零丢失恢复<sup>[4]</sup>。

## 四、方案设计

### 4.1 阶段 1（MVP）：中心化编排 + 全量重规划

#### 触发条件（事件驱动）

三个触发条件，参考 Magentic-One 停滞检测 + Devin 遇阻推理：

| 触发条件 | 实现 | 参考系统 |
|---------|------|---------|
| Task report 状态为 BLOCKED | TM 在 report.remark 中标记 `BLOCKED: <reason>` | Devin |
| Task report 显式请求计划修订 | TM 在 report 中标记 `plan_revision_needed: true` | Magentic-One |
| 连续 N 个 Task 超时未完成 | Leader 轮询 Task 状态，检测停滞 | Magentic-One 停滞检测 |

#### 重规划流程

```
                    ┌─────────────────────────────────┐
                    │         TM 执行 Task             │
                    │  发现问题（依赖缺失/scope变化）    │
                    └──────────┬──────────────────────┘
                               │
                               ▼
                    ┌─────────────────────────────────┐
                    │  Task Report (status=BLOCKED)    │
                    │  remark: "need ts-order API      │
                    │  change"                          │
                    │  plan_revision_needed: true       │
                    └──────────┬──────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────┐
│                    Leader 收到反馈                        │
│                                                          │
│  Step 1: 冻结当前 DAG 版本 (v=N)                          │
│  Step 2: 收集所有 BLOCKED Task 的反馈                     │
│  Step 3: 把新发现加入需求上下文                            │
│          requirement += "\n[FEEDBACK] ts-notification    │
│          needs ts-order-service to expose /api/v2/users" │
│  Step 4: 重新调 PlanIntegrationService.integrate()        │
│          → 生成新 DAG (v=N+1)                             │
│  Step 5: diff(v=N, v=N+1) → 找出增量变化                  │
│  Step 6: 对增量变化调 PlanExecutionBridge.materialize()   │
│          → 创建新 Spec + Task                             │
│  Step 7: 通知所有 TM: 新版本 v=N+1 可用                    │
│  Step 8: 对已过时的 Task 标记 superseded                   │
└──────────────────────────────────────────────────────────┘
                               │
                               ▼
                    ┌─────────────────────────────────┐
                    │         TM 收到通知               │
                    │  如果当前 Task 已被 superseded:   │
                    │    → 停止执行，保存 checkpoint     │
                    │    → 拉取 v=N+1 的新 Task          │
                    │  如果当前 Task 不受影响:           │
                    │    → 继续执行                      │
                    └─────────────────────────────────┘
```

#### 版本协调机制

每个计划有单调递增的版本号。TM 在每次 report 里带上自己执行的 `plan_version`。Leader 比对版本号：

```python
@dataclass(frozen=True)
class TaskReport:
    task_id: UUID
    status: TaskStatus  # IN_PROGRESS / COMPLETED / BLOCKED / FAILED
    plan_version: int   # TM 执行时所基于的计划版本
    remark: str         # BLOCKED 时填写原因
    plan_revision_needed: bool = False
```

Leader 维护 `current_plan_version`，当收到 TM report 时：

```
if report.plan_version < current_plan_version:
    # TM 在旧版本上执行
    if task 已被 superseded:
        通知 TM 停止，分配新 Task
    else:
        通知 TM 继续（Task 不受影响），但更新到新版本
else:
    # TM 在最新版本上
    if report.plan_revision_needed:
        触发重规划
```

#### 半成品处理

参考 LangGraph checkpoint 模式。TM 被叫停时：
- 已完成的部分保留为 git commit（worktree 隔离）
- 未完成的部分标记为 `abandoned`
- 新版本 DAG 重新分配时，可以在 instruction 里引用之前的中间结果

### 4.2 阶段 2（中期）：事件溯源 + 增量更新

当 Task 数量超过 50+、Team 数量超过 5+ 时，全量重规划的成本超过增量更新。引入事件溯源：

#### 事件日志（append-only）

```
PlanCreated v1
TaskAssigned(ts-order, v1)
TaskAssigned(ts-notification, v1)
TaskCompleted(ts-order, v1, commit=abc123)
TaskBlocked(ts-notification, v1, reason="need ts-auth API")
PlanRevised v2 (reason: ts-notification needs ts-auth, delta=+ts-auth-task)
TaskSuperseded(ts-notification, v1→v2)
TaskAssigned(ts-auth, v2)
TaskCompleted(ts-auth, v2, commit=def456)
TaskAssigned(ts-notification, v2, depends_on=ts-auth@v2)
```

#### 投影（当前计划 = 事件重放）

```python
def project_plan(events: list[PlanEvent]) -> IntegratedPlan:
    """重放事件日志，得到当前计划状态。"""
    plan = IntegratedPlan.empty()
    for event in events:
        plan = apply(plan, event)
    return plan
```

#### TM 本地投影 + 订阅

每个 TM 维护自己的本地投影，订阅事件流。当 `PlanRevised` 事件到达时，TM 更新本地投影，检查自己的 Task 是否受影响。

#### GraSP 五原语细粒度修复

参考 GraSP 论文<sup>[7]</sup>，定义五种计划修复操作：

| 原语 | 含义 | 场景 |
|------|------|------|
| **Rebind** | 同一个 Task 换一个 Agent 执行 | TM-A 无法完成，换成 TM-B |
| **InsertPrereq** | 插入一个缺失的前置 Task | TM 发现需要先改依赖仓库的 API |
| **Substitute** | 用不同方案替换当前 Task | 原方案不可行，换技术路线 |
| **Rewire** | 重新连接依赖边 | 依赖关系变了，A 不再依赖 B |
| **Bypass** | 跳过不需要的 Task | 发现某 Task 其实不需要 |

MVP 阶段只用 InsertPrereq（最常见场景：发现缺失依赖）。中期实现全部五种。

### 4.3 阶段 3（长期）：如果需要真正的并行

如果未来 RepoMesh 需要多个 Leader 并行管理不同子项目，才需要考虑分布式一致性。此时参考 LangGraph 的 checkpoint + Fork 模式：每个 Leader 有自己的 checkpoint 链，跨 Leader 的冲突通过 merge checkpoint 解决。

但这不是当前优先级。中心化编排器在可预见的未来（单个项目内 10-50 个 Task）足够用。

## 五、对抗性审查

### 质疑 1：阶段 1 全量重规划太慢，Leader 会成瓶颈。

**回应**：Magentic-One 的数据显示，停滞检测 + 全量重规划在复杂任务中仍然高效，因为大多数 Task 不需要重规划。只有 BLOCKED 才触发。MVP 阶段 Task 数量有限（10-30 个），重规划成本可控。一次 PlanIntegrationService.integrate() 调用是一次 LLM 请求，耗时约 5-15 秒，对于非频繁触发的重规划是可接受的。

### 质疑 2：TM 在执行中途被通知停下来，半成品怎么办？

**回应**：参考 LangGraph 的 checkpoint 模式。TM 的每次中间状态通过 git commit 保存（worktree 隔离）。被叫停时已完成的部分保留，未完成的部分标记 abandoned。新版本 DAG 重新分配时，可以在 instruction 里引用之前的 commit hash 作为上下文。

### 质疑 3：多个 TM 同时发现不同问题，同时上报怎么办？

**回应**：中心化编排的天然优势——Leader 是单写入者。所有上报进入队列，Leader 串行处理。每次重规划都基于最新的完整状态。不存在并发写冲突。这比任何分布式方案都简单可靠。

### 质疑 4：为什么不用 CRDT？

**回应**：三个原因。第一，无先例——调研覆盖 Augment、Devin、LangGraph、AutoGen、CrewAI、MetaGPT，无一使用 CRDT。第二，语义冲突不可自动合并——两个 TM 对同一个 API 的不同修改方案，CRDT 无法判断哪个正确。第三，实现成本极高——需要设计 DAG 的 CRDT 数据结构、向量时钟、合并协议，投入产出比不合理。

### 质疑 5：阶段 2 事件溯源值得吗？

**回应**：当 Task 数量超过 50+、Team 数量超过 5+ 时，全量重规划的 LLM 调用成本和延迟会超过增量更新。事件溯源还提供时间旅行调试——回溯到任意时间点的计划状态，对调试多 agent 失效非常有价值。但 MVP 阶段不需要，先做阶段 1，等瓶颈出现再演进。

### 质疑 6：如果 Leader 自己也出错了呢？比如重规划后新 DAG 比旧的更差。

**回应**：引入人类检查点（参考 Devin 的 Planning Checkpoint）。重规划后的新 DAG 在 materialize 之前，可以选择性地展示给人类审批。MVP 阶段可以通过 API 返回 diff，让调用方决定是否 accept。

## 六、与现有代码的对接

### 6.1 MVP 需要的改动

| 组件 | 改动 | 说明 |
|------|------|------|
| `TaskReport` contract | 新增 `plan_version: int` 和 `plan_revision_needed: bool` 字段 | TM 上报时携带版本信息 |
| `TaskStatus` | 新增 `BLOCKED` 和 `SUPERSEDED` 状态 | 区分"失败"和"需要重规划" |
| `PlanExecutionBridge` | 新增 `replan()` 方法 | 封装"冻结→重算→增量 materialize"流程 |
| `PlanExecutionBridge.materialize()` | 返回 `plan_version` | 让调用方知道当前版本 |
| API | 新增 `POST /bridge/replan` 端点 | 触发重规划 |
| API | 新增 `GET /bridge/plan/{version}` 端点 | 查询指定版本的计划 |

### 6.2 数据流

```
TM 执行 Task (v=1)
  → BLOCKED: need ts-order API
  → POST /tasks/{id}/report { status: BLOCKED, plan_version: 1, plan_revision_needed: true }

Leader 检测到重规划请求
  → POST /bridge/replan { project_id, feedback_task_id }
  → Bridge.replan():
      1. 查询所有 BLOCKED Task 的 feedback
      2. 合并 feedback 到 requirement
      3. 调 PlanIntegrationService.integrate() → 新 IntegratedPlan (v=2)
      4. diff(v=1, v=2) → 新增 Task
      5. materialize 增量
  → 返回 { new_plan_version: 2, new_tasks: [...], superseded_tasks: [...] }

TM 轮询或被通知
  → GET /bridge/plan/2
  → 发现自己的 Task 被 superseded
  → 停止，拉取新 Task
```

## 七、总结

| 维度 | MVP（阶段 1） | 中期（阶段 2） | 长期（阶段 3） |
|------|-------------|--------------|--------------|
| 触发机制 | Task BLOCKED + 停滞检测 | 事件驱动（PlanEvent 流） | 分布式事件流 |
| DAG 更新 | 全量重新 generate | 增量（GraSP 五原语） | 跨 Leader merge |
| 版本协调 | 单调递增版本号 | 事件溯源 + 投影 | checkpoint + Fork |
| 冲突解决 | Leader 单写入者 | 事件日志串行化 | merge checkpoint |
| 先例 | Magentic-One、Devin | LangGraph | 无（需自研） |
| Task 规模 | 10-30 | 30-100 | 100+ |
