## 〇、为什么需要这份清单

`delivery_auto_enabled` 默认 `False` 是防误配的防御性默认（方案 §3.1 关键事实）。结果是：**代码在、开关没开 → 整个自动交付链路（PR 创建、门禁、auto-merge、推进挂钩）默认不激活**，构成"隐性死链"。

本清单把"启用前置条件"显式化，供部署/运维/自检按序核对。全部满足后才应把开关打开；任一不满足时，链路会以可解释的方式停在某个环节（见下文"不满足时的表现"）。

---

## 一、激活前置条件清单（全部满足才启用）

### 前置条件 1：主开关

- 配置：`delivery_auto_enabled=true`
- 作用：plan 完成后自动创建交付 PR、挂载观察驱动推进（`completion_handler` / `on_batch_deliver` 仅在该开关为真时接线）。
- 不满足时的表现：plan 完成后**不会创建任何 PR**，链路停留在"任务完成、交付未开始"。
- 备注：默认 `False` 不修改（保持向后兼容）；本清单即其配套激活文档。

### 前置条件 2：命名 CI check

- 配置：`delivery_required_checks` 至少包含 **1 个命名 CI check**（如 `("ci",)` 或 `("build", "test")`）。
- 作用：`PlanDeliveryFinalizer` 有运行时守卫——PR 创建后的 merge 门禁以命名 check 为依赖（`evaluate_merge_gate` 的 CI 维度）。`delivery_required_checks=()` 时守卫不会放行 merge（或缺省语义不生效）。
- 不满足时的表现：PR 已创建但 merge 门禁停留在"等待 CI"或按配置跳过 CI 维度，auto-merge 永不触发。
- 备注：check 名必须与 GitHub 上实际运行的 CI 状态上下文（context）一致。

### 前置条件 3：审批门槛

- 配置：`delivery_required_approvals >= 1`（默认 `1`）。
- 作用：merge 门禁的 review 维度——auto-merge 前必须获得至少该数量的 approved review。
- 不满足时的表现：PR 长期停留在等待 review 状态；`0` 表示不需要审批（仅当有意为之才设置）。
- 备注：与分支保护规则（branch protection）中 `require_pull_request_reviews` 相互独立、均需满足。

### 前置条件 4：观察源就绪

- 配置/运行时：GitHub webhook 可达，**或** 15s replay worker 可达（`scm_observation_replay_interval_seconds=15`）。
- 作用：merge/PR/review/CI 事件经 observation 流回流 → `reconsider_task` / `undraft_when_allowed` / `merge_ready_repositories` 才会被触发。P1-1 的"依赖 merge → un-draft"延迟上限即 replay 周期（15s）。
- 不满足时的表现：事件到达后状态不更新，PR 停留在已 merge 前的任意状态，推进挂钩不触发。
- 备注：两条路径任一可用即可；生产推荐 webhook，本地/测试可用 replay worker。

### 前置条件 5：merge 权限 token

- 配置：交付所用 GitHub token 具备目标仓库的 **merge 权限**（`Contents: write` + PR merge）。
- 作用：`MERGE_PULL_REQUEST` 命令执行、`ready_for_review`（PATCH `draft: false`）、`add_label`（若启用 `delivery_pr_label`，还需 **issues/labels 写权限**）都依赖该 token。
- 不满足时的表现：命令执行报 403/404，观察流重放后仍失败（命令带幂等 key，可安全重试）。
- 备注：P1-2 的 label 是**可选**能力，token 无 label 权限时保持 `delivery_pr_label=false` 即可，不影响其余链路。

## 二、可选开关与演进项（默认不开启）

| 开关 | 默认 | 语义 | 备注 |
|---|---|---|---|
| `delivery_contract_gate` | `false` | P0-2 契约门禁：consumer 纳入交付候选为主路径；`evaluate_merge_gate` 第 8 重兜底（拒绝"producer 已交付但 consumer 无候选"的 merge） | 启用前提：图推理契约识别已产出候选对（`SpecificationKind.CONTRACT`，状态 APPROVED/FROZEN）；无契约批次行为不变 |
| `delivery_pr_label` | `false` | P1-2 可选 label：为每个交付 PR 打 `changeset/<change_set_id 前 8 位>` | 需 token 有 label 写权限；PR body 的 change_id / Sibling 回填不依赖此开关 |
| `delivery_required_approvals` | `1` | 见前置条件 3 | — |

### 演进项（本方案明确**不拆**，列为后续）

`delivery_auto_enabled` 语义过载（同时控制 PR 创建、governance/validation 门禁、auto-merge）。后续可拆为：

- `delivery_create_pr`：只控制 PR 创建；
- `delivery_enforce_gates`：只控制 governance/validation 门禁；
- `delivery_auto_merge`：只控制 merge 推进。

建议默认全 `False`、逐步灰度。拆分需新增配置与接线改动，会扩大改动面，本方案不实施。

## 三、P0/P1/P2 实施后的完整开关拓扑（截至 2026-08-11）

| 环节 | 开关 | 说明 |
|---|---|---|
| PR 创建 | `delivery_auto_enabled` | plan 完成/批次成功 → 创建交付 PR（draft=True，P1-1） |
| 契约门禁 | `delivery_contract_gate` | P0-2 主路径 + 兜底；默认关 |
| draft → ready | `delivery_auto_enabled` + 观察源 | P1-1 `undraft_when_allowed`：依赖全部 MERGED 后 un-draft（15s replay 轮询触发） |
| merge 门禁 | `delivery_required_checks` / `delivery_required_approvals` / 分支保护 | `evaluate_merge_gate` 7+1 重判定 |
| 推进挂钩 | `delivery_auto_enabled` | P0-1：批次全部 merge 后 `plan.advance()` |
| Related PRs | `delivery_pr_label`（可选） | P1-2：PR body 含 change_id / execution order / 仓库清单 + Sibling 回填；label 可选 |

---

## 四、激活自检顺序（SOP）

1. 确认 token 权限（前置条件 5）→ 2. 确认观察源（前置条件 4）→ 3. 设置 `delivery_required_checks` 与 `delivery_required_approvals`（前置条件 2/3）→ 4. 打开 `delivery_auto_enabled=true`（前置条件 1）→ 5. （可选）按需打开 `delivery_contract_gate` / `delivery_pr_label`。

任一步骤不满足时，不要打开主开关；用 §一 的"不满足时的表现"对照排障。
