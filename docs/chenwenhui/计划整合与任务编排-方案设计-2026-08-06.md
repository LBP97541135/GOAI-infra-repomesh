# 计划整合与任务编排 - 方案设计

> 创建时间：2026-08-06
> 状态：**MVP 实现中**
> 对应计划书任务：PP-04 Contract 生命周期、ORCH-01 Task DAG

## 一、问题定义

仓库发现完成后，总 Manager 持有：
- 需求文本
- 确认后的仓库列表（REQUIRED + MAYBE）
- 每个仓库 Team Manager 返回的初步方案（plan_summary）

**需要产出：**
- Engineering Spec：项目级完整方案
- Contract list：跨仓库接口约定
- Task DAG：带依赖关系的任务图

**核心挑战：** 从"每个仓库各自要改什么"推导出"仓库之间有什么接口依赖、谁先改谁后改"。

---

## 二、MVP 方案（纯 LLM）

### 设计原则

当前没有 call_graph 确定性数据，也没有真实的 Worker Agent 做消费者确认。MVP 用 LLM 做全部推理，但用结构化输出约束降低出错概率。

### 整体流程

```
确认后的仓库列表 + plan_summary（已有）
    ↓
阶段 1：升级 plan_summary → 结构化 RepositoryPlan
    Team Manager 的输出从一句话升级为结构化 JSON
    ↓
阶段 2：总 Manager 整合（一次 LLM 调用）
    输入：需求 + 所有仓库的 RepositoryPlan
    输出：
    ├── Engineering Spec（项目级完整方案）
    ├── Contract list（跨仓库接口约定）
    └── Task DAG（执行顺序）
    ↓
阶段 3：拓扑排序检查（确定性）
    检查 DAG 无环，输出执行批次
```

### 阶段 1：结构化 RepositoryPlan

Team Manager 的确认输出升级：

```python
@dataclass(frozen=True, slots=True)
class RepositoryPlan:
    repository: str
    summary: str                     # 改动概述
    changed_apis: tuple[str, ...]    # 涉及的 API 端点
    changed_modules: tuple[str, ...] # 预估改动的模块
    depends_on: tuple[str, ...]      # 依赖的其他仓库的服务
    impacts: tuple[str, ...]         # 自己 API 变化会影响的仓库
    risk: str                        # low / medium / high
```

prompt 要求 Team Manager 基于自己的 AutoCard（deps + apis + commits）填充这些字段。

### 阶段 2：总 Manager 整合

一次 LLM 调用，输入全部 RepositoryPlan + 需求，输出结构化 JSON：

```python
@dataclass(frozen=True, slots=True)
class IntegratedPlan:
    engineering_spec: str            # 项目级完整方案
    contracts: list[ContractSpec]    # 跨仓库接口约定
    task_dag: list[TaskNode]         # 带依赖的任务图

@dataclass(frozen=True, slots=True)
class ContractSpec:
    producer: str                    # 生产者仓库
    consumer: str                    # 消费者仓库
    interface: str                   # 约定的接口/API
    agreement: str                   # 具体约定内容

@dataclass(frozen=True, slots=True)
class TaskNode:
    repository: str
    instruction: str                 # 具体改动指令
    depends_on: tuple[str, ...]      # 必须先完成的仓库
    parallelizable_with: tuple[str, ...]  # 可并行的仓库
```

### 阶段 3：拓扑排序检查（确定性）

对 LLM 返回的 Task DAG 做拓扑排序：
- 检测是否有环 → 有环报错
- 输出执行批次（batch 1: [A, C], batch 2: [B], ...）

### MVP 的风险与应对

| 风险 | MVP 应对 | 未来改进 |
|------|---------|---------|
| LLM 推断的依赖关系不准确 | 用结构化输出约束格式 | call_graph 确定性数据 |
| Contract 内容可能是编的 | MVP 可接受，先跑通链路 | Worker Agent 消费者确认 |
| Task DAG 可能有环或遗漏 | 拓扑排序检测有环 | call_graph 交叉验证 |
| plan_summary 质量不够 | 升级为结构化 RepositoryPlan | 结合代码分析 |

## 三、未来方案（LLM + 图推理）

### 设计原则

当 call_graph 和 reverse_call_graph 可用时，将依赖推理从"LLM 猜"升级为"确定性数据 + LLM 语义理解"。

### 整体流程

```
确认后的仓库列表 + RepositoryPlan
    ↓
阶段 1：规则层（确定性，无 LLM）
    ├── 用 reverse_call_graph 补充每个仓库的 impacts
    ├── 找出有调用关系的仓库对 → 标记需要 Contract
    └── 从调用关系推导 Task DAG 的边
    ↓
阶段 2：LLM 层（语义推理）
    ├── 基于需求 + RepositoryPlan 生成 Engineering Spec
    ├── 对每个需要 Contract 的仓库对，推断接口约定内容
    └── 识别 RepositoryPlan 之间的矛盾
    ↓
阶段 3：Contract 校验（确定性 + 人工）
    生产者声明接口变化 → 消费者确认影响 → 不一致则标记 UNRESOLVED
    ↓
产出：
    ├── Engineering Spec（项目级完整方案）
    ├── Contract list（有确定性依据的接口约定）
    └── Task DAG（来自 call_graph 的确定性依赖图）
```

### 图推理层的数据来源

```python
# call_graph.json 已有 90 条调用关系
call_graph = {
    "ts-preserve-service": ["ts-order-service", "ts-notification-service", "ts-seat-service"],
    "ts-seat-service": ["ts-travel-service", "ts-order-service"],
    ...
}

# reverse_call_graph 反向索引
reverse_call_graph = {
    "ts-order-service": ["ts-preserve-service", "ts-seat-service", "ts-cancel-service"],
    ...
}
```

### Contract 配对规则（确定性）

```
对于确认列表中的每对仓库 (A, B)：
  如果 call_graph[A] 包含 B → A 依赖 B 的 API
      → 生成 Contract(producer=B, consumer=A)
  如果 call_graph[B] 包含 A → B 依赖 A 的 API
      → 生成 Contract(producer=A, consumer=B)
```

### Task DAG 边推导规则（确定性）

```
对于每个 Contract(producer=P, consumer=C)：
  → DAG 边：P 必须在 C 之前完成
  → task_dag[C].depends_on += [P]
```

### 图推理 vs LLM 的分工

| 判断 | LLM 负责 | 图推理负责 |
|------|---------|----------|
| 仓库间有没有依赖 | ❌ 不可靠 | ✅ call_graph 确定性 |
| 依赖的具体接口是什么 | ✅ 语义理解 | ❌ call_graph 只有仓库级 |
| Contract 的具体约定内容 | ✅ 结合需求理解 | ❌ 无法理解语义 |
| Task 执行顺序 | ❌ 不可靠 | ✅ DAG 边确定性 |
| 方案矛盾检测 | ✅ 语义推理 | ❌ 无法理解语义 |
| Engineering Spec 生成 | ✅ 全局视角 | ❌ 无法生成文本 |


### MVP 的已知限制

| 限制 | 说明 | 后续解法 |
|------|------|---------|
| Contract 引用可能不在确认列表中 | LLM 可能虚构仓库 | ✅ 已修：确定性过滤（见下方） |
| impacts 字段不可靠 | Team Manager 看不到反向调用关系 | reverse_call_graph 补充 |
| DAG 依赖边可能缺失 | depends_on 依赖 LLM 推断 | call_graph 确定性推导 |
| Contract 内容是 LLM 编的 | 具体接口约定可能不准确 | Worker Agent 消费者确认 |
| exposed_apis 全部为空 | 远程扫描只读目录和依赖文件，不下载源文件。Java 项目的 `@RestController`/`@RequestMapping` 注解需要逐文件解析，成本太高（45 仓库 × ~20 文件 = ~900 请求） | 图推理阶段下载源文件并解析注解 |

## 七、动态更新方案（进化方向）

### 问题定义

当前 MVP 是**静态的**——`integrate()` 一次性生成完整方案，之后不可变。但真实执行中，Worker Agent 可能发现新情况：

- "我发现还需要改 ts-food-service"
- "我的 API 改了，ts-order-service 需要适配"
- "这个仓库不需要改，我误判了"

总 Manager 需要根据这些反馈**动态调整计划**。

### 动态更新流程

```
integrate() → IntegratedPlan v1
    ↓
执行 Batch 1
    ↓
Worker A 报告新发现：
  ├── 新增仓库："ts-food-service 也需要改"
  ├── 接口变化："我的 /api/order 返回值变了"
  └── 排除仓库："实际上不需要改 ts-route-service"
    ↓
总 Manager 收集反馈 → 重新 integrate() → IntegratedPlan v2
    ↓
执行 Batch 2（基于 v2）
    ↓
... 循环直到所有 Batch 完成
```

### 需要新增的能力

| 能力 | 说明 | 实现要点 |
|------|------|---------|
| Plan 版本管理 | IntegratedPlan 不可变，每次更新生成新版本 | 新增 `version` 字段 + 版本链 |
| Worker 反馈通道 | Worker Agent 执行后报告新发现 | 复用 task_orchestration 的 report 机制，扩展 `discoveries` 字段 |
| 增量重新整合 | 基于反馈部分更新而非全部重来 | 新增 `re_integrate()` 方法，传入 v1 + 反馈，输出 v2 |
| DAG 动态调整 | 新增/移除节点，重新拓扑排序 | 复用 `_topological_batches`，支持动态增删 |
| Contract 动态更新 | 接口变化时更新 Contract | 新增 Contract 版本管理 |

### 反馈数据结构

```python
@dataclass(frozen=True, slots=True)
class WorkerFeedback:
    """Worker Agent 执行后的反馈。"""

    repository: str
    # 新发现的仓库（需要加入计划）
    discovered_repos: list[str]
    # 接口变化（需要更新 Contract）
    api_changes: list[dict]  # [{api, change_description, affected_repos}]
    # 实际不需要改的仓库（需要从计划中移除）
    false_positives: list[str]
    # 其他备注
    notes: str
```

### 增量整合接口

```python
class PlanIntegrationService:
    def integrate(self, requirement, summary) -> IntegratedPlan:
        """初始整合（已有）。"""
        ...

    def re_integrate(
        self,
        current_plan: IntegratedPlan,
        feedbacks: list[WorkerFeedback],
        requirement: str,
    ) -> IntegratedPlan:
        """增量重新整合。

        基于 Worker 反馈动态更新计划：
        1. 新增仓库 → 加入 DAG
        2. 接口变化 → 更新 Contract
        3. 误判仓库 → 从 DAG 移除
        4. 重新拓扑排序 → 新的执行批次
        """
        ...
```

### 与 task_orchestration 模块的集成

当前 task_orchestration 已有：
- Task 状态机（assigned → in_progress → succeeded/failed/blocked）
- BLOCKED 状态（Worker 报告阻塞时触发）
- report 机制（Worker 返回结果）

动态更新需要扩展：
- Worker report 时携带 `WorkerFeedback`
- BLOCKED 状态触发 `re_integrate()`
- 新 Task 基于 v2 的 DAG 创建

### 实施优先级

```
Phase 1（当前 MVP）：
  ✅ 静态 integrate() 一次性生成完整方案
  ✅ 按批次执行，不支持中途调整

Phase 2（动态更新）：
  ├── Worker 反馈通道
  ├── re_integrate() 增量整合
  └── Plan 版本管理

Phase 3（图推理 + 动态更新）：
  ├── call_graph 确定性 Contract 配对
  ├── reverse_call_graph 补充 impacts
  └── 动态更新时用图推理做校验
```
