## 一、审查方法说明（为什么是"第一性原理 + 两遍对抗"）

第一性原理的起点不是文章，而是 RepoMesh 的产品命题与代码事实：

> **RepoMesh 的核心命题 = 跨仓库 AI 编码协作的确定性编排。**
> 它区别于 Claude Code 的唯一价值点，是"图的顺序推理决定了谁先做、谁后做、谁依赖谁"，而不是让每个 agent 各自为战。

从该命题推导系统必须成立的三条不变量：

| 不变量 | 含义 | 违反时的后果 |
|---|---|---|
| **I1 顺序不变量** | 下游批次不得在上游未 merge 的基线上开发 | DAG 顺序白排，下游 Worker 在旧基线上产出，合并冲突与隐性破坏 |
| **I2 正确性不变量** | 跨仓接口变更（CONTRACT）必须经 consumer 侧验证后才能合入 | 接口破坏无声发生——唯一可能造成生产事故的路径 |
| **I3 可观测性不变量** | plan_snapshot 状态必须与真实交付（PR/merge）一致 | 进度脱节、人提前介入未就绪批次、review 质量下降 |

两遍对抗性审查的定义：
- **第一遍：审查"问题定义"是否被文章框架带偏** —— 对 5 个缺口逐一问：去掉文章提示，它是否仍从 RepoMesh 代码事实独立成立？成立到哪一层？
- **第二遍：审查"解决方案"是否第一性原理正确** —— 对每个拟议方案问：它修复的是哪条不变量？它是否引入了新耦合/新风险？有没有更内聚的替代做法？

## 二、第一遍对抗性审查：问题定义是否被文章框架带偏

### 2.1 文章框架对问题列表的实际影响

5 个缺口的来源构成（诚实拆解）：

| 缺口 | 文章对应项 | 是否文章提示 | 代码事实（独立于文章） |
|---|---|---|---|
| draft 状态 | G3 draft/un-draft、B4"依赖未合时 draft" | 是 | `plan_delivery.py` 第 98 行显式传 `draft=False`；`github.py` SCM adapter docstring 写明 "restricted to draft PRs and reconciliation"（**设计意图就是 draft**，代码行为与意图不一致） |
| poll_and_undraft | G3"轮询依赖 merge 后自动 un-draft" | 是 | observation 骨架已存在（见 2.2），缺的只是 UNDRAFT 命令 |
| Related PRs 链接 | G3 change_id 标签 | 是 | PR body 仅含 plan id，无兄弟 PR 链接、无批次标注 |
| 契约门禁 | B8"契约化接口对齐"（弱相关） | 部分 | `SpecificationKind.CONTRACT`（producer/consumer/interface_changes）已在 specification 模块实现，但 delivery 全链路零引用——**这是 RepoMesh 自己的半成品，文章只字未提跨仓 CI 门禁** |
| Delivery 不合并 | B4/B6（弱相关） | 部分 | `on_task_terminal` 批次推进只检查 `_batch_succeeded`（任务状态），不看 merge；`ExecutionPlanStatus` 无等待交付状态 |

结论：**文章影响的是"解法形状"（draft/un-draft、change_id 标签、分批开 PR），而不是问题真实性。** 5 个缺口中，契约门禁与 Delivery 不合并即使没有文章也能从代码独立推出——它们是 RepoMesh 自己的结构性问题。

### 2.2 误判一修正：poll_and_undraft 并非"完全不存在"

此前诊断："poll_and_undraft 完全不存在"。

代码事实（`src/repomesh/integrations/scm/`）：
- `observation_processor.py`：`GitHubObservationProcessor.process()` 已完整实现——消费 claimed observation，解析 `check_run / pull_request / pull_request_review` 事件，路由到 ChangeSet，调用 `coordinator.record_github_ci` / `delivery.observe_merge` / `delivery.observe_pull_request` / `coordinator.record_github_review`；`auto_merge` 开启时还会调用 `merge_ready_repositories`。
- `SCMObservationReplayWorker`：每 15s 轮询 `_observations.list_replayable()` 并处理——**轮询骨架已存在**。
- `github_events.py` 第 75 行：`draft=bool(pull_request.get("draft"))`——PR 的 draft 状态会被观察捕获。

修正后的事实陈述：
- ✅ 已存在：observation 消费、15s replay 轮询、PR draft 状态捕获、merge 后状态流转。
- ❌ 不存在：`SCMCommandKind` 中只有 `MERGE_PULL_REQUEST` 一种命令（`delivery/contracts.py` 107-108 行），**没有 UNDRAFT / ready_for_review 命令**；也没有"依赖 merge 完成 → 自动 un-draft"的触发器。
- 影响：该缺口**降格**——它不再是一个独立缺口，而是"draft 生命周期控制器"（P1-1）的组成部分。

### 2.3 误判二修正：merge 门禁并非"只看 branch protection"

此前诊断："merge 门禁只检查 branch protection"。

代码事实（`src/repomesh/modules/delivery/application.py` `evaluate_merge_gate`，440-507 行）：**已有 7 重判定**：
1. 目标仓库状态必须是 `READY_TO_MERGE`（CI 已过）；
2. review 状态（`REVIEW_PENDING` / `REVIEW_CHANGES_REQUESTED` 视为未过）；
3. `depends_on` 中的上游仓库必须 `MERGED`；
4. `merge_order > merge_cursor` 时等待游标；
5. 更早的候选仓库若 `CI_FAILED` 则阻塞；
6. 存在未完成的 recovery plan 则阻塞；
7. `require_governance` / `require_validation` 时检查治理决策与 validation snapshot。

修正后的事实陈述：
- merge 门禁能力是完备的，且第 3/4/5 重已经体现了"依赖顺序"。
- 真正的缺口不在门禁强度，而在**两个外层事实**：
  a) `require_governance` / `require_validation` 绑定 `delivery_auto_enabled`（`container.py` 349-353 行），默认关闭 → 门禁大部分判定实际不生效；
  b) 门禁里**没有契约维度**——CONTRACT 的 consumer 侧验证从未被纳入判定（见 P0-2）。

### 2.4 第一遍审查结论

| 原缺口 | 审查后判定 | 等级调整 |
|---|---|---|
| Delivery 不合并 | **成立，且为根因**（违反 I1） | 保持高 |
| 契约门禁 | **成立，且为独立推导**（违反 I2；文章弱相关） | 保持高 |
| draft 状态 | **成立**（违反 I3 + I1 的 PR 层体现） | 保持中，升级为"生命周期控制器" |
| poll_and_undraft | **诊断修正**：骨架已存在，仅缺 UNDRAFT 命令与触发器 | 并入 draft 生命周期控制器，不再单列 |
| Related PRs 链接 | **成立但应降级**：是 I3 的可观测性增强，不是正确性 | 中高 → 中（P1-2） |

## 三、第二遍对抗性审查：方案是否第一性原理正确

### 3.1 关键事实修正（对抗审查新发现）

> **整个 Delivery 自动链路默认不激活。**

`src/repomesh/bootstrap/container.py`：
- 477-486 行：`completion_handler`（plan 完成 → `PlanDeliveryFinalizer.handle` 自动开 PR）仅在 `delivery_auto_enabled=True` 时挂载；默认 **False** → **plan 完成后根本不会创建 PR**。
- 349-353 行：`DeliveryService` 的 `require_governance` / `require_validation` 绑定同一个开关 → merge gate 的治理/验证维度默认关。
- 391-392 行：`ChangeSetSCMCoordinator(auto_merge=delivery_auto_enabled)` → 自动 merge 默认关。

含义：
- "Delivery 不合并"的第一性根因不只是"批次推进不查 merge"，而是**"默认配置下 PR 都不会被创建，链路整体处于未激活状态"**。
- 但注意 `plan_delivery_finalizer`（container.py 411-418 行）带有运行时守卫：激活前强制要求 `delivery_required_checks` 至少一个命名 CI check、`delivery_required_approvals >= 1`——**激活路径本身已有防误配设计**。因此 `delivery_auto_enabled` 更像"尚未启用的产品开关"，而非永久防御。
- 方案影响：P0-1 必须同时处理"激活路径"与"推进挂钩"，否则修了推进逻辑也不会被触发。

### 3.2 逐方案对抗性质疑

**质疑 A：批次推进真的需要等 merge 吗？等多久？**
- 反对意见：merge 是异步外部过程，等待会让 plan 长时间"看起来卡住"。
- 回答：等 merge 正是 I1 的本质要求。做法不是新增 `BLOCKED`（BLOCKED 会触发 replan/失败语义，是错误信号），而是**让批次自然停在当前 `current_batch_index`**：`on_task_terminal` 在 `_batch_succeeded` 为真后、`plan.advance()` 之前，追加 merge 检查；不满足则直接 return（plan 保持 `IN_PROGRESS`，批次索引不动）。等待期间由 observation 流驱动：最后一个上游 PR 的 merge 事件 → `observe_merge` → 状态变 `MERGED` → 下次任务事件或观察回调触发重新评估。
- 可观测性补充：在 `progress()` / 视图层暴露"批次内任务全完成但 delivery 未 merge"的派生状态（不新增状态机枚举，保持 `IN_PROGRESS` 语义，避免波及 replan/失败路径）。

**质疑 B：契约门禁应该放在哪一层？**
- 候选 1：放进 `evaluate_merge_gate`（第 8 重判定）。
- 候选 2：在 `PlanDeliveryFinalizer._candidates` 里，把涉及 CONTRACT 的 **consumer 仓库也纳入交付候选**（consumer 出适配 PR），从而 consumer PR 自然进入 observation 流与既有门禁（依赖顺序 + CI）的覆盖范围。
- 回答：选 **候选 2 为主、候选 1 为兜底**。理由：
  - CONTRACT 的正确性验证发生在"交付后"（consumer 需要看到 producer 的 PR 才能写适配代码），而 `_candidates` 校验的是"交付前"（任务是否成功）——所以主逻辑应放在交付编排侧，把 consumer 变成正式候选；
  - consumer 一旦成为候选，`evaluate_merge_gate` 现有的"upstream merged + CI"判定自然覆盖"producer 未合不 merge consumer"——不需要为契约发明新的判定语言；
  - 候选 1 作为兜底：若某批次包含 CONTRACT 变更但没有 consumer 候选（契约声明了 consumer 但交付计划未纳入），`evaluate_merge_gate` 应拒绝 producer merge（提示"契约变更缺少 consumer 适配候选"），防止接口破坏无声发生。
- 端口设计：delivery 模块新增只读端口 `ContractCatalogPort`（按 plan/change_set 查询 CONTRACT 及其 producer/consumer），由 composition root 注入——遵守"应用服务依赖端口"的模块规则。

**质疑 C：我们真的需要 draft 控制吗？全开非 draft PR 不行吗？**
- 反对意见：draft 增加复杂度；GitHub 上全开 PR 让 CI 全跑，reviewer 提前 review，效率更高。
- 回答：需要 draft，且这是 RepoMesh 确定性的 PR 层体现。区分两种模式：
  - 全非 draft：reviewer 会 review 顺序靠后的 PR 并提前批准，随后被 merge gate 挡住——"系统不让我 merge"的沟通噪音，人的随机性覆盖图的确定性（正是用户表格里"图推理的确定性排序被人的随机性覆盖"的原话）。
  - draft 控制：依赖未合的下游 PR 保持 draft，人只 review 当前可 merge 的；依赖合并后自动 undraft 进入 review 窗口。**这是文章 G3 的形状，但其第一性依据是 I3：PR 可见性必须与批次顺序一致。**
- 额外事实支撑：`github.py` adapter docstring 明写 "restricted to draft PRs and reconciliation"，且 `plan_delivery.py` 方法名就叫 `publish_and_open_draft_pull_request`——**draft 本来就是设计意图，P1-1 是"回到意图 + 补自动化"，不是新发明**。
- 注意：draft PR 仍会触发 GitHub CI（draft 只隔离人的 review 介入，不隔离 CI）——所以 draft 不会延迟检查，只会延迟 review，这正好符合"顺序保障"语义。

**质疑 D：Related PRs 链接到底解决什么？**
- 回答：解决 review 质量问题（I3 的可观测性分支）。reviewer 打开一个 PR 时，需要知道"这个变更单元里还有哪些 PR、顺序是什么、我该先看哪个"。MVP 不做复杂的跨仓 API 调用：PR 描述写 `change_id`（= project_id）、`execution_order`、同批次仓库列表；PR 创建是逐个进行的（第 N 个创建时前 N-1 个已有编号），因此**创建后回填更新兄弟 PR 描述**，或至少保证后续创建的 PR 引用已存在的兄弟链接。这是增强项，不与正确性挂钩。

**质疑 E：delivery_auto_enabled 默认 False 怎么办？**
- 回答：不改变默认值（它是防误配的防御性默认），但方案要求：
  a) P0-1 的推进挂钩与 P1-1 的 draft 生命周期都在"开关开启"时生效，开关关闭时行为与现在完全一致（向后兼容，队友的既有测试不受影响）；
  b) 文档给出激活清单（见 P2-1），把"启用前置条件"显式化，避免"代码在、开关没开"的隐性死链。

### 3.3 第二遍审查结论

- 方案全部可以映射到三条不变量之一，无"为做而做"的项；
- 不做的事（防过度设计）：
  - 不新增 `ExecutionPlanStatus` 枚举（避免波及 replan/失败路径）；
  - 不为契约发明新的门禁判定语言（复用既有依赖顺序 + CI 判定）；
  - 不改变 `delivery_auto_enabled` 默认值；
  - 不做"执行中动态挂载新仓库"（G3 之外的文章项，属于另一个议题，不在本方案）。

## 四、最终调整方案

优先级符号：P0 = 违反不变量，必修；P1 = 违反可观测性，应修；P2 = 激活与文档化。

### P0-1 批次推进挂钩 merge 状态（修复"Delivery 不合并"，I1）

**现状**：`AdvanceExecutionPlan.on_task_terminal`（`modules/task_orchestration/application.py` 481-514 行）在 `_batch_succeeded(plan)` 为真后立即 `plan.advance()`，**不检查当前批次 PR 是否已 merge**。下游 Worker 在旧基线上开发。

**改动**：
1. `AdvanceExecutionPlan` 新增端口 `DeliveryStatePort`（只读）：`async def repositories_merged(change_set_id) -> bool` / `async def current_batch_delivery_status(plan) -> view`。
2. `on_task_terminal`：`_batch_succeeded` 通过后，若配置为"delivery-gated"（`delivery_auto_enabled=True`），查询当前批次涉及的 ChangeSet，全部仓库 `MERGED` 才 `plan.advance()`；否则 return（plan 保持 `IN_PROGRESS`，自然等待）。
3. 视图层：`progress()` 或 plan 视图暴露派生字段 `delivery_pending_repositories`（任务全完成但未 merge 的仓库列表），供 UI/报告展示，**不新增状态机枚举**。
4. 边界：`delivery_auto_enabled=False` 时行为与现在完全一致（纯任务驱动），保证队友既有测试与回退路径不变。

**测试要点**：批次任务全成功但 PR 未 merge → 计划不推进；merge 事件到达后（`observe_merge` 写入）→ 推进；开关关闭 → 行为不变。

**✅ 实施状态（2026-08-11）**：已完成并合入。实现采用**逐批交付**（比方案正文的"plan 完成后一次性检查"更进一步）：批次任务全成功 → `on_batch_deliver` 回调交付该批次 → `_delivery_gate` 检查当前批次所有仓库是否 merge → 全部 merge 后才 `plan.advance()`。要点如下：

1. `task_orchestration` 新增只读端口 `DeliveryStatePort.repository_states(project_id)`（返回 `DeliveryGatedRepositoryView(repository_id, merged)`），`AdvanceExecutionPlan` 新增 `delivery_state` 与 `on_batch_deliver` 构造参数；`on_task_terminal` 改为经 `_advance_if_ready` → `_delivery_gate` 推进。
2. `reconsider_task(task_id)` 为观察驱动的重新评估入口：merge 事件到达后重新检查 `_delivery_gate`，支持传入 leader 任务或 worker 任务（经 `parent_task_id` 解析到 leader）。
3. delivery 模块新增 `AppendCandidatesCommand` / `DeliveryService.append_candidates`（幂等追加，重复批次跳过）与 `ChangeSet.append_repositories`（保护既有仓库状态与 merge order）；`_merge_order_for_append` 在既有 max order 之后按依赖拓扑分配。
4. `PlanDeliveryFinalizer.handle_batch(plan)`：首个批次 `prepare` 建 ChangeSet，后续批次 `append_candidates` 追加同一 ChangeSet；重复调用幂等（已开 PR 跳过）。
5. `GitHubObservationProcessor` 新增 `on_observed` 回调，处理后通知容器侧 `_on_observed` → 循环调用 `advancer.reconsider_task`；container.py 在 `delivery_auto_enabled=True` 时接线 `on_batch_deliver=handle_batch` + `delivery_state_adapter()`（ChangeSet 状态投影为 merged 标志）。
6. 测试：新增 4 个行为测试（批次未 merge 不推进、无关仓库 merge 不解锁、批次未成功不触发交付回调、`handle_batch` 逐批并入同一 ChangeSet 且 merge order 递增）；`ruff check src tests` 通过；全量 pytest 674 通过 / 13 跳过。

### P0-2 契约门禁（修复"契约门禁"，I2）

**现状**：`SpecificationKind.CONTRACT`（`modules/specification/contracts.py`，含 producer/consumer/interface_changes）已实现，图推理介入点 2 能产出候选对；但 delivery 全链路（`PlanDeliveryFinalizer`、`evaluate_merge_gate`）零引用。

**改动**：
1. delivery 模块新增只读端口 `ContractCatalogPort`：`async def contracts_for_plan(plan_id) -> tuple[ContractView, ...]`（含 producer、consumer、interface_changes、status）。
2. `PlanDeliveryFinalizer._candidates`：若批次关联的 CONTRACT 的 producer 在该批次，**把 consumer 仓库也纳入交付候选**（consumer 出适配 PR），consumer 的 PR 自然进入 observation 流与既有门禁。
3. `evaluate_merge_gate` 兜底判定（第 8 重）：若仓库是某 CONTRACT 的 producer，且该契约存在未纳入候选的 consumer，则拒绝 merge（reason："contract change is missing a consumer adapter candidate"）。
4. 配置：`delivery_contract_gate`（bool，默认随 `delivery_auto_enabled`）或直接复用开关；文档注明启用前提（图推理契约识别已产出候选对）。

**测试要点**：producer-only 契约变更 → 被门禁拒绝；producer+consumer 均在批次 → consumer merge 前被 producer 顺序约束；无契约批次 → 行为不变。

### P1-1 draft 生命周期控制器（修复"draft 状态"+"poll_and_undraft"，I3 + I1 的 PR 层）

**现状**：`plan_delivery.py` 第 98 行显式传 `draft=False`（与方法名 `publish_and_open_draft_pull_request` 矛盾）；`SCMCommandKind` 仅 `MERGE_PULL_REQUEST`；无 undraft 命令与触发器。

**改动**：
1. `plan_delivery.py`：`draft=True`（回到设计意图）。
2. `delivery/contracts.py`：`SCMCommandKind` 增加 `UNDRAFT_PULL_REQUEST = "undraft_pull_request"`。
3. `integrations/scm/github.py`：新增 `ready_for_review(pr_number)`（PATCH `draft: false`），与既有命令执行器对齐。
4. `ChangeSetSCMCoordinator`：新增 `undraft_when_allowed(change_set_id)`——对每个 `PR_OPEN` 且所有 `depends_on` 已 `MERGED` 的仓库发 UNDRAFT 命令（触发条件与 `evaluate_merge_gate` 的依赖维度一致，但不等待 review/CI——那是 undraft 之后才开始）。
5. 触发器挂载：`SCMObservationReplayWorker` 处理 `pull_request` observation 之后调用 `undraft_when_allowed`（每轮 15s 轮询天然覆盖"依赖 merge 完成"到"un-draft"的延迟）。

**测试要点**：draft=True 创建；依赖未 merge → 保持 draft；依赖 merge 事件到达 → 15s 内发出 UNDRAFT 命令；命令执行失败 → 观察流可重放。

### P1-2 Related PRs + change_id 标签（修复"Related PRs 链接"，I3 可观测性）

**改动**：
1. `plan_delivery.py` PR body 模板扩展：`change_id`（= plan id）、`execution_order`、同批次仓库清单。
2. PR 创建循环（第 N 个创建后）回填更新前 N-1 个兄弟 PR 描述，追加"本批次其他 PR"链接列表（含仓库名 + PR 号 + 状态）。
3. GitHub 侧可配置 label：`changset/<plan-id>`（若 token 有 label 权限）。

**测试要点**：同批次 3 仓 → 第 3 个 PR 创建后，前 2 个 PR 描述含全部 3 个链接；文案含 change_id 与 execution_order。

### P2-1 激活路径与开关决策（修复"链路默认不激活"）

**改动（不改代码默认值）**：
1. 文档化激活前置条件清单：
   - `delivery_auto_enabled=true`；
   - `delivery_required_checks` ≥ 1 个命名 CI check（`plan_delivery_finalizer` 已有运行时守卫）；
   - `delivery_required_approvals >= 1`；
   - 观察源就绪（GitHub webhook 或 15s replay worker 可达）；
   - merge 权限 token 已配置。
2. 建议拆分开关（可选演进）：`delivery_auto_enabled` 语义过载（同时控制 PR 创建、governance/validation 门禁、auto-merge）。可拆为 `delivery_create_pr` / `delivery_enforce_gates` / `delivery_auto_merge`，默认全 False，逐步灰度。**本方案默认不拆**（避免扩大改动面），列为后续演进项。
