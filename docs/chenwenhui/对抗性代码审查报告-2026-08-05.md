### 三、"保证 RepositoryProfile 在 API、数据库、缓存中的字段一致"

#### 判定：❌ 误报（字段已完全一致）

#### 逐字段跨层对比

`RepositoryProfile` 定义了 8 个字段（`src/.../domain/models.py`）：

| 字段 | domain 定义 | cache 序列化 | cache 反序列化 | PostgreSQL 持久化 | PostgreSQL 反序列化 | API RepositoryView |
|------|------------|-------------|---------------|-------------------|--------------------|--------------------|
| `name` | `str` | ✅ `"name": profile.name` | ✅ `data["name"]` | ✅ `name=profile.name` | ✅ `record.name` | ✅ `name: str` |
| `url` | `str` | ✅ `"url": profile.url` | ✅ `data["url"]` | ✅ `url=profile.url` | ✅ `record.url` | ✅ `url: str` |
| `description` | `str = ""` | ✅ `"description": ...` | ✅ `data.get("description", "")` | ✅ `description=...` | ✅ `record.description` | ✅ `description: str` |
| `topics` | `tuple = ()` | ✅ `list(profile.topics)` | ✅ `tuple(data.get(...))` | ✅ `list(profile.topics)` | ✅ `tuple(record.topics)` | ✅ `tuple[str, ...]` |
| `languages` | `tuple = ()` | ✅ `list(profile.languages)` | ✅ `tuple(data.get(...))` | ✅ `list(profile.languages)` | ✅ `tuple(record.languages)` | ✅ `tuple[str, ...]` |
| `auto_card` | `AutoCard \| None` | ✅ dict 结构 | ✅ `AutoCard(...)` | ✅ `metadata_payload` JSONB | ✅ `_deserialize_auto_card` | ✅ `AutoCardView \| None` |
| `id` | `UUID` | ❌ 不序列化 | ✅ `default_factory=new_id` | ✅ `id=profile.id` | ✅ `record.id` | ✅ `id: UUID` |
| `profiled_at` | `datetime` | ❌ 不序列化 | ✅ `default_factory=lambda: now()` | ✅ `profiled_at=...` | ✅ `record.profiled_at` | ❌ 不暴露 |

#### 两个"不一致"的设计原因

**`id` 在 cache 中不序列化**：

cache 是本地文件缓存，用于减少重复 API 调用。`id` 是运行时生成的 UUID，每次反序列化时通过 `default_factory=new_id` 重新生成。这不会影响功能，因为：
- CLI 路径中，profiles 从 cache 加载后立即注入 catalog，id 在同一个进程生命周期内保持不变
- LLM discovery 通过 `catalog.list()` 获取 profiles，通过 `repository_id` 引用，全程使用同一个 id

**`profiled_at` 在 cache 中不序列化 / API 中不暴露**：

`profiled_at` 是内部元数据（profile 的生成时间），cache 反序列化时重新生成。API 不暴露这个字段是因为消费者（前端/调用方）不需要知道 profile 的生成时间。

**结论**：这些是合理的设计决策，不是字段不一致的 bug。
