## ① 输入解析与平台识别

| # | 问题 | 影响 | 相关位置 |
|---|------|------|----------|
| 1.1 | 平台判断过于武断：URL 含 github.com 即 GitHub，其余全部当作 GitLab | Gitee、Bitbucket、自建 Git 服务会被调错 API，扫描静默失败 | `infrastructure/platform/fetcher.py` `detect_platform` |
| 1.2 | GitLab 多段路径误判：subgroup 仓库（多级路径）会被当成单仓库 | subgroup 仓库解析失败或识别错对象 | `application/scan_remote.py` `identify_url_type` |

**① 已实施（2026-08-25）**

- **1.1 平台识别**：`detect_platform` 不再「非 GitHub 即 GitLab」。新增 `UNSUPPORTED`/`UNKNOWN` 判定：已知但未支持的主机（Gitee/Bitbucket/Azure DevOps/Codeberg/SourceForge）按名拒绝并给出友好中文提示；未知名主机要求运维在 `REPOMESH_REPOSITORY_PLATFORMS`（新配置项，`host=platform` 逗号分隔）中声明，否则拒绝。拒绝发生在任何出站请求之前。路由层 `build_scan_fetcher` 统一执行该校验。
- **1.2 subgroup 误判**：服务端单仓库校验 `require_single_repo_url` 从离线 URL 猜测改为调用平台 API（`fetcher.identify`），GitLab subgroup 路径由 `/projects/:id` 在线确认，不再按「≥2 段路径」误判为单仓库。仓库名也由平台元数据提供（`fetcher.resolve_repo_name`，GitLab 取项目显示名、GitHub 取 repo 名），API 不可达时回退 URL 推断。`GET /repositories/url-type`（控制台输入时的离线徽标）保持离线设计，其返回名仅为输入提示，实际注册名以平台元数据为准。

**② 方案更新：服务依赖改从「执行证据」提取（2026-08-25）**

证据来源 = 「能证明依赖存在的东西」。按依赖如何被证明分类（技术栈无关），共有 6 种机制：

| # | 机制 | 普适描述 | 示例载体（可扩展） | 被什么验证 | confidence |
|---|---|---|---|---|---|
| ① | 构建期依赖 | A 的构建描述声明依赖 B 的产物 | pom/build.gradle/package.json/go.mod/Cargo.toml | 构建系统 | `confirmed` |
| ② | 运行时调用声明 | A 声明「我会调用 B 的服务」 | FeignClient/Dubbo/gRPC client/OpenAPI 客户端/服务发现配置 | 运行时框架 | `confirmed` |
| ③ | 数据/资源共享 | A 和 B 共享存储或消息通道 | datasource/MQ topic/对象存储/缓存配置 | 运行时加载（可能死配置） | `declared` |
| ④ | 部署拓扑 | 部署清单中 A 依赖 B | K8s manifest/docker-compose/Helm/CI | 部署系统 | `declared` |
| ⑤ | 源码引用 | A 直接引用 B 的代码（跨仓库边界） | import/workspace/submodule | 编译器/包管理器 | `confirmed` |
| ⑥ | 运行时观测（留位） | 真实发生的调用记录 | 调用链/注册中心/网关日志 | 事实本身 | `confirmed` |

- 机制⑥ 扫描器默认拿不到（需外部数据源），**架构留位**：将来飞书、GitHub Actions 日志、SkyWalking 等平台提供调用记录接口时，写 adapter 把记录转成边喂进图，边模型不动。
- 原 2.1 的字符串猜测（`_JAVA_SERVICE_PATTERNS`）**删除**：猜测不是证据，不参与建边。

证据获取不需要 clone 仓库：远程扫描本就是 `fetch_file_tree` + `fetch_file_content` 按路径读小文件，本地扫描读磁盘，两种模式证据一致。

| # | 问题 | 影响 | 相关位置 |
|---|------|------|----------|
| 5.1 | 靠名字猜关系 | 依赖名包含仓库名即建边，无真实调用证据，「谁调用了谁的 API」未建模 | `application/dependency_graph.py` `_match_dep_to_name` |

| 5.3 | 边无置信度 | 猜测边与确定边同等参与拓扑排序，分批可能出错 | `application/dependency_graph.py` `GraphEdge`；解法见下方「证据来源 → 边置信度」 |
| 5.4 | 图无持久化 | SingleGraph 边索引方案有设计未在本模块落地 | `application/dependency_graph.py` |

**证据来源 → 边置信度（5.3 解法，2026-08-25）**

`GraphEdge` 已有 `confidence` 字段（`confirmed_edge_count()` 已实现），缺失的只是取值依据。边的证据机制 → confidence：

| 机制 | confidence | 判定依据 |
|---|---|---|
| ① 构建期依赖 / ② 运行时调用声明 / ⑤ 源码引用 | `confirmed` | 构建/框架/编译器真实执行 |
| ③ 数据共享 / ④ 部署拓扑 | `declared` | 配置会被加载，但可能过期或未启用 |

字符串猜测不建边（无证据）。下游消费规则（待定，随 5.3 一起定）：`confirmed` 边直接参与拓扑排序与影响分析；`declared` 边仅作候选提示。公共依赖（5.2）匹配不到 catalog 内仓库，天然不产生边。

## 证据获取管道（①-⑤ 怎么拿到）

> 2026-08-25 汇总。结论：5 种机制走同一条管道，只是「定位文件」和「解析器」不同；不需要 clone 仓库——远程模式走 `fetch_file_content` 按路径读小文件，本地模式读磁盘，证据内容一致。

```
全树定位证据文件 → 按路径读内容（远程 API / 本地磁盘） → 专用解析器
→ 提取标识 → 过服务清单校准 → 建边 (mechanism, confidence)
```

### ① 构建期依赖（BUILD / confirmed）

| 环节 | 做法 |
|---|---|
| 文件在哪 | `pom.xml`、`build.gradle(.kts)`、`package.json`、`go.mod`、`pyproject.toml`、`Cargo.toml`、`requirements.txt`、`CMakeLists.txt` |
| 怎么定位 | 全树按文件名匹配（2.2 改动：全树 + 每类 N 个、每仓 M 个上限） |
| 怎么解析 | `pom.xml`→`xml.etree`（groupId:artifactId:version）；`package.json`→`json`；`go.mod`→逐行 module/require；`pyproject.toml`→`tomllib`。全标准库，零新依赖 |
| 怎么变边 | artifact 名过**服务清单**，命中仓库 → `BUILD/confirmed` 边 |
| 新增改动 | 全树定位（2.2）+ 各文件解析器完善（2.3） |

### ② 运行时调用声明（RUNTIME_CALL / confirmed）

| 环节 | 做法 |
|---|---|
| 文件在哪 | 各语言源码中的框架注解/声明：`@FeignClient(name=…)`、`@DubboReference`、gRPC client target、OpenAPI 客户端配置 |

| 怎么解析 | 只提取**框架注解属性**（如 FeignClient 的 name），不扫任意字符串——这是它和已删除的字符串猜测的本质区别：name 是框架真实拿去注册中心用的 |
| 怎么变边 | 服务名过**服务清单**，命中仓库 → `RUNTIME_CALL/confirmed` 边 |
| 新增改动 | 注解提取器（新）；文件读取已有，带上限防爆炸 |

### ③ 数据/资源共享（SHARED_RESOURCE / declared）

| 环节 | 做法 |
|---|---|
| 文件在哪 | `application.yml` / `application.properties` / `bootstrap.yml` / `.env` / ConfigMap 类配置 |
| 怎么定位 | 全树匹配配置文件（`application*.yml`、`application*.properties`、`*.env`） |
