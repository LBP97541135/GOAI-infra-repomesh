# 仓库发现 MVP — 方案设计

**日期**: 2026-08-03
**作者**: chenwenhui

---

## 一、目标

用户提交自然语言需求（PRD），系统自动判断该需求涉及组织内哪几个仓库需要改动，输出候选仓库列表 + 置信度 + 理由，人工确认后进入后续流程。

---

## 二、核心架构

一个扫描脚本 + 一个 LLM 调用。没有依赖图，没有第二层，没有 embedding。

```
PRD 输入
  │
  ▼
读仓库注册表（PostgreSQL，每个仓库含 AutoCard）
  │
  ▼
拼所有仓库名片进 prompt → 调 DeepSeek（temperature=0）
  │
  ▼
解析返回 JSON → 过滤幻觉仓库名 → 按 confidence 排序
  │
  ▼
输出候选列表 + low_signal 风险提示 → 人工确认
```

---

## 三、数据模型

### RepositoryProfile（每条仓库记录）

```
RepositoryProfile
├── name              ← 人工填（注册时）
├── url               ← 人工填（注册时）
├── description       ← 人工填（可选，可以空）
├── topics            ← 人工填（可选，可以空）
├── languages         ← 人工填（可选，可以空）
├── auto_card         ← scan.py 自动生成
│   ├── top_dirs         仓库 2 层目录结构
│   ├── deps              依赖文件里声明的包列表
│   ├── recent_commits    最近 5 条 commit message
│   ├── exposed_apis      扫描到的 API 路由
│   └── low_signal        信息量不足标记（布尔值）
├── id                ← 系统生成
└── profiled_at       ← 系统生成
```

老字段（name/url/description/topics/languages）全是可选的补充信息，AutoCard 是自动扫描的主力信息。两套共存，有啥用啥。

## 四、五个变动

### 变动一：扩展 RepositoryProfile（domain/models.py）

新增 AutoCard 数据结构（top_dirs、deps、recent_commits、exposed_apis、low_signal 五个字段）。RepositoryProfile 加一个可选字段 auto_card 指向它。description 改成可选（default=""）。

不删任何老字段——name/url/description/topics/languages 全部保留，理由：老字段零成本，有就给 LLM 看，没有不报错。

### 变动二：发现服务重写（application/discovery.py）

把现有的关键词匹配逻辑替换成 LLM 推理。核心组件：

- **LLMClient Protocol**：抽象接口，测试时用 mock，生产时用 DeepSeekClient
- **DeepSeekClient**：httpx 薄封装，调用 OpenAI 兼容的 DeepSeek API
- **build_discovery_prompt**：把所有 profile 拼成文本 + 用户需求 + low_signal 提示
- **parse_llm_response**：JSON 容错解析（markdown fence / 额外文字）+ 幻觉仓库名过滤
- **自纠正重试**：JSON 解析失败时，把错误响应丢回 LLM 让它修，重试一次
- **关键词 fallback**：无 API key 时自动回退到原始关键词匹配逻辑

DiscoveryEvidence 输出结构不变（repository_id、score、rationale）。

### 变动三：数据库层适配（infrastructure/postgres_catalog.py）

不改数据库表结构。RepositoryRecord 已有 `metadata_payload`（JSONB）字段。

- `add` 方法：如果 profile 带了 auto_card，序列化成 dict 存进 metadata_payload（key = `"auto_card"`）
- `_to_domain` 方法：从 metadata_payload 反序列化出 auto_card 挂到 RepositoryProfile

in_memory_catalog.py 不用改，ports/catalog.py 不用改，infrastructure/models.py 不用改。

### 变动四：API 模型透传（api/models.py + api/router.py）

新增 AutoCardCreate（前端传入）和 AutoCardView（返回前端），字段就是 AutoCard 的五个字段。

- `RepositoryCreate` 加可选字段 auto_card
- `RepositoryView` 加可选字段 auto_card
- `description` 从必填改成可选
- `register_repository` 接口构造 RepositoryProfile 时把 auto_card 传进去
- `discover_repositories` 接口从环境变量读 DeepSeek 配置传给 service

### 变动五：新增扫描脚本（application/scan.py）

全新模块，提供 `scan_repo(repo_path)` 函数，输入仓库本地路径，输出 AutoCard。

| 字段 | 提取方法 |
|------|---------|
| top_dirs | 遍历目录树，限制 2 层深度，过滤 .git/node_modules/\_\_pycache\_\_ 等 |
| deps | 按语言读依赖文件：Python 读 requirements.txt/pyproject.toml，Node 读 package.json，Go 读 go.mod |
| recent_commits | subprocess 调 `git log --oneline -5 --no-merges` |
| exposed_apis | 正则扫描路由定义（MVP 先支持 3 种框架：FastAPI、Express、Gin） |
| low_signal | 信息量评分逻辑（见兜底一） |

scan.py 自带 `__main__` 块，可通过 `python -m repomesh.modules.repository_intelligence.application.scan ./repo` 调用。

## 五、兜底策略（三层，从轻到重）

### 兜底一：扫描时检测，主动暴露风险（MVP 就做）

scan.py 生成 AutoCard 时，算一个信息量评分：

```
信息量评分 = 0
if 仓库名包含业务关键词（pay/order/user/auth/notify/email/front/api/service/admin/config 等）: +0.3
if 目录名有业务语义（非 src/lib/test/a/b/c/handler 这种泛命名）: +0.3
if deps 中有业务相关第三方包（非纯框架如 fastapi/express/react/redis）: +0.2
if recent_commits 有具体内容（非 "fix bug" "update" "refactor" "wip"）: +0.2
```

分数 < 0.3 → `low_signal = True`

discover.py 的 prompt 里加一句提示：

> "以下仓库信息量不足，你可能无法判断它是否相关，如果不确定请将其纳入候选并标注 low_confidence：[low_signal 仓库列表]"

**本质**：不隐藏盲区，把不确定的明确标出来交给人工。系统可以判断不了，但不能假装判断得了。

### 兜底二：人工确认环节兜底（MVP 就做）

最终输出必须经过人工确认。在确认界面额外展示：

```
候选仓库：
  [0.92] order-service
  [0.88] payment-service
  [0.75] frontend-web

以下仓库信息量不足，系统无法充分判断，请人工检查是否涉及：
  [?] svc-3721（低信息量仓库）
```

宁可多选，不能漏选。

### 兜底三：依赖图传播（V1 做，MVP 不做）

预先从代码的 import 和依赖文件提取仓库间调用关系，构建依赖图。从第一层定位到的入口仓库出发，沿图传播 1~2 跳，找出间接受影响的仓库。

## 六、Prompt 容错策略

| 风险 | 解法 |
|------|------|
| LLM 返回的 JSON 前后带 markdown 标记或多余文字 | 先尝试剥离 ```` ```json ``` ```` 围栏，再提取第一个 `[` 到最后一个 `]` 之间的内容 |
| json.loads 失败 | retry 一次，把原始返回丢回 LLM 让它修 |
| LLM 编造不存在的仓库名 | 解析后过滤掉不在注册表里的名字 |
| 同一需求多次跑结果不一致 | temperature=0，接受 LLM 固有的非确定性 |

## 七、临时 CLI（MVP 验证用）

新增 `scripts/repomesh_cli.py`，提供 6 个子命令，使用 JSON 文件持久化，不依赖 FastAPI / PostgreSQL：

| 命令 | 用途 |
|------|------|
| `scan <repo_path>` | 扫描本地仓库，输出 AutoCard JSON |
| `register --name ... --url ... --path ...` | 注册单个仓库（可选自动扫描） |
| `register-bulk catalog.json` | 从 JSON 文件批量注册 |
| `discover "requirement"` | 发现候选仓库（有 DEEPSEEK_API_KEY 走 LLM，无则走关键词） |
| `list` | 列出已注册仓库 |
| `clear` | 清空本地 registry |

## 八、调用流程

```
仓库接入时：
  CLI 跑 scan.py → 拿到 AutoCard
  → POST /repositories 传 name + url + auto_card
  → postgres_catalog 存进 metadata_payload

用户发需求时：
  → POST /discovery 传 requirement
  → discovery 读所有 profile（含 auto_card）
  → 拼 prompt + low_signal 提示 → 调 DeepSeek
  → 解析 JSON + 过滤幻觉
  → 返回候选仓库 + 置信度 + 理由 + low_signal 风险提示

人工确认后：
  → 发布 RepositorySelected 事件（现有逻辑不变）
```

## 九、测试方案

自建测试集，20~30 条：
- 对着仓库名片人工编需求，自己标标准答案
- 队友交叉验证
- 覆盖三种场景：单仓库 5 条、少量联调 10 条、跨仓库链路 5 条
- 包含陷阱题（容易漏选和误判的）
- 及格线：Recall ≥ 85%，Precision ≥ 60%

当前已实现的自动化测试（19 个，全部通过）：
- domain model 测试（AutoCard 默认值、description 可选、searchable_text 包含 auto_card）
- scan 测试（top_dirs / deps / exposed_apis 提取，low_signal 评分正反向）
- discovery keyword fallback 测试
- discovery LLM 测试（候选排序、幻觉过滤、markdown JSON 容错、bad JSON 重试、low_signal prompt 提示）
- catalog 契约测试（AutoCard 往返、description 可选）

## 十、MVP 不做的事情

| 不做 | 什么时候做 |
|------|----------|
| 依赖图构建与传播 | V1 |
| 第二层深度验证 | V1 |
| embedding 向量匹配 | V1（仓库数 > 30 时） |
| 自动扫描触发（git hook） | V1 |
| 多框架 API 路由扫描（超出 3 种） | V1 |
| 公开数据集验证 | 可选，先跑自建测试集 |

## 十一、V1 升级信号

当以下任何一个出现时开始做 V1：
- 仓库数超过 30
- 用户反馈"为什么没选 xxx 仓库"
- 同类需求反复出现需要人工纠正
