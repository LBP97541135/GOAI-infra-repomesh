# 决策链与历史上下文 —— 实施计划（2026-08-28）

> 依据：GOAI 复赛评委反馈（"coding 的核心在于开发者对历史上下文的深度理解"）、
> semantica 项目调研（决策即一等对象 + 决策链追溯 + 相似先例检索）、
> RepoMesh 现有架构（plan_snapshot JSON 快照、confirmation 留痕、audit_events）。

---

## 1. 目标（一句话）

让 RepoMesh 从"无状态推理"变成"有记忆的开发者"：**把每次"为什么这么做"沉淀为可追溯、可复用的决策记录**，
新需求进来时能引用历史决策（RAG），企业审计时能回答"这个变更为什么被批准"。

## 2. 总体判断（三句话，是本次讨论的收敛结论）

1. **决策链不需要图数据库**——它是线性链（需求→task→PR，2-3 跳），关系表 + 外键 + 递归查询完全够用；
2. **AGE 的正确锚点是代码依赖图**（升级现有 JSON 快照），不是决策链——且**现在规模没到，暂不上**；
3. **向量/RAG 是独立加分项**（pgvector），不依赖 AGE，可以独立推进。

参考项目 semantica 用图存储的原因（网状多跳决策网络 + 图算法 + 十万级规模 + 图原生产品定位）
与我们的场景（线性决策链 + 路径查询 + 小规模）不同，**照抄存储形态是错误的，借鉴它的"决策即对象"理念即可**。

## 3. 分层实施计划

| 层 | 做什么 | 技术 | 时机 |
|---|---|---|---|
| **L1 地基** | 7 个环节产出"决策单" + 串成链 | 改现有记录结构（加字段） | **随 7 步修复一起做**（必须） |
| **L2 功能** | 决策链追溯 + 相似案例检索（结构化匹配） | PG 关系表 + SQL | 紧接着 L1 |
| **L3 加分** | RAG：新需求检索相似历史决策链 → 注入 prompt | pgvector | 独立推进，值得做 |
| **L4 升级** | 代码依赖图升级为真图存储（影响分析/高危区识别） | AGE（先 POC） | 触发条件满足才上，非必需 |

### L1 地基：决策单 + 链（核心，不可后补）

**决策单** = 每个环节产生一条结构化记录，最小字段：

| 字段 | 说明 | 示例 |
|---|---|---|
| `decision_id` | 稳定 id | `RA-2026-008` / `task-1` |
| `step` | 环节 | requirement_analysis / classification / adjustment / integration / task / pr |
| `created_at` / `recorded_at` | 业务时间 + 记录时间 | |
| `actor` | 谁做的 | llm / human(确认) |
| `evidence_ref` | 依据引用 | `classification_evidence_version`、扫描产物 id、确认对话 id |
| `upstream_ref` | **上游决策 id（链的关键）** | `requirement_id` / `classification_id` / `task_id` |
| `status` | 状态 | proposed / confirmed / rejected / adjusted |
| `payload` | 环节特有内容 | 分类结果、改档前后值、PR url |

**链** = 让记录串起来（缺的就是这个）：

```
requirement_id → classification_id → task_id → pr_url
   RA-2026-008      证据指纹          上游引用      关联链
```

7 个环节的现状与缺口：

| 环节 | 现状 | 要补的 |
|---|---|---|
| 需求分析 | 有需求记录 | 无 |
| 候选评分 | 有扫描产物 | 补决策单形态 |
| 三档分类 | **有 evidence_version 指纹**（现成雏形） | 补 `requirement_id` 上游引用 |
| 人工改档 | 有 `adjustments` | 补上游引用 |
| 集成/物化 | 有状态机 | 补决策语义 + 上游引用 |
| task 拆分 | 有 task 表 | **补 `requirement_id`（上游引用）** |
| PR 合入 | 有 PR 记录 | **补 `task_id`（关联链）+ PR url** |

> 必须随 7 步一起改的原因：上游引用只在**数据产生的当下**可知，事后补只能靠猜。

### L2 功能：两个查询

1. `trace_decision_chain(requirement_id)` —— 输入需求 id，输出完整决策链（需求→分类→确认→task→PR），带每环的依据。
2. `find_similar_decisions(requirement)` —— 结构化匹配相似历史决策（同仓库/同模块/同依赖），SQL 实现。

### L3 加分：RAG（独立于 L4）

- 用 pgvector 存决策文本 embedding（需求文本、决策理由、PR 描述）；
- 新需求进来 → 向量相似检索 → 取 Top-K 历史决策链 → 注入 LLM prompt（上下文增强）；
- 这是"深度理解历史上下文"的直接演示，也是比赛 RAG 加分项。

### L4 升级：AGE（可选，触发才上）

- **现在不做**：规模小（几十节点/几百边），JSON 列 + 内存计算毫秒级够用；AGE 是 C 扩展，部署成本高；
- **触发条件**（满足任一再考虑）：
  1. 全量依赖图规模到几百上千节点、几万边；
  2. 要做多跳影响分析（改 X 波及所有下游）/ 中心性分析（高危区识别）等图算法查询；
  3. 实时高频影响面查询。
- **注意**：AGE 升级的是**代码依赖图**（`plan_snapshot.graph_edges` JSON 列 → AGE 图），不是决策链；
  现有"快照为单一事实源、图可从快照重建"的范式保留（`plan_graph_from_snapshot` 已是正确模式）。

## 4. 技术选型总览

| 需求 | 选型 | 理由 |
|---|---|---|
| 决策链存储 | PG 关系表 + 外键 | 线性链、小规模、路径查询 |
| 决策链追溯 | 递归查询 / 多表 join | 2-3 跳，SQL 足够 |
| 相似决策推荐（结构化） | SQL（同仓/同模块/同依赖） | 比赛先例检索的 80% 价值 |
| 相似决策推荐（语义/RAG） | embedding（OpenAI 兼容 `/embeddings`）+ 应用层 cosine | PG 官方扩展独立安装成本高，JSON 列 + 应用层计算小规模够用；已交付（L3） |
| 代码依赖图（现状） | plan_snapshot JSONB 列 + 内存 PlanGraph | 单一事实源 + 可重建，范式正确 |
| 代码依赖图（升级，可选） | Apache AGE | 触发条件满足才上，锚点是依赖图 |

## 5. 时序

```
现在（随 7 步修）  →  L1 地基：7 环节补决策单 + 链
紧接着            →  L2 功能：追溯 + 相似检索
独立推进          →  L3 RAG：pgvector + 相似决策注入 prompt
最后/可选         →  L4 AGE：先 POC 验证可装性，装不上不影响上面三层
```

## 6. 不做什么（对抗性审查沉淀的红线）

1. **决策链不存 AGE**——关系表够用，不为技术而技术；
2. **不引入 semantica 的重量级模块**——ontology/SHACL/SPARQL/推理引擎对比赛过重；
3. **图谱必须是投影**——真值源在关系表，图谱（若建）只读、可随时重建，绝不双写
   （延续"同一事实单一拼写"红线，避免再造一个 `supplemented_repos`）；
4. **不先建图谱再修流程**——源数据（字段/状态机）未稳定前写投影必返工。

## 7. 验收/演示方式

1. 输入需求 id → 展示完整决策链（需求→分类→确认→task→PR，每环带依据）→ 企业审计场景；
2. 新需求 → 自动带出相似历史决策链（✅ 结构化 + 语义双模式已交付）→ LLM 引用历史依据作答 → "历史上下文理解"演示 + RAG 加分；
3. （可选，L4 上了才有）改某仓 → 影响面分析可视化。
