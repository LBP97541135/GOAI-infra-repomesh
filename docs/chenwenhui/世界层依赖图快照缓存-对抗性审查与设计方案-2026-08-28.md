# 世界层依赖图快照缓存 — 对抗性审查与设计方案

- 日期：2026-08-28
- 范围：repository_intelligence 世界层依赖图（candidate 边）的构建、缓存与持久化
- 关联：`contracts/graph.py`、`application/dependency_graph.py`、`bootstrap/container.py`、`repositories` 表

---

## 1 取证：世界层图今天怎么被构建和消费

代码事实（2026-08-28 核查）：

- `confirmation_service`（`container.py:501`）与 `plan_integration_service`（`container.py:507`）**都没有 `@cached_service`**：每次调用都先 `await self.repository_catalog.list()` 全量读取所有仓库档案，再 `DependencyGraphService(profiles)` 在内存重建整张有向图。
- `postgres_catalog.list()` 无缓存，每次直查数据库、全量反序列化所有仓库的 `metadata_payload`（含 AutoCard 依赖证据）。
- 调用频率：每个需求走分类流程都会触发 confirmation；每次生成计划都会触发 plan_integration。也就是说，**每一次分类、每一次计划，都付一次"全表读 + 全量建图"的成本**。
- 世界层图的持久化现状：图本身不落库。`repositories.metadata_payload`（JSON 列）中的 `auto_card.dep_evidence` 是图的唯一事实源，图是每次使用时的内存派生物。
- 仓库的身份：`RepositoryRecord.url` 是 `unique=True` 唯一索引——仓库级"户口本"已存在。

由此得出三个待解决的问题：重复构建成本没有消除；构建成本随仓库规模线性放大，且没有测量手段；多进程部署时每个 worker 各自重建一份，进程重启后全量重来。

---

## 2 对抗性审查：存的必要性与存法

### 2.1 质疑一：图是派生数据，存图等于存冗余副本

世界层图 = f(profiles)，profiles 已持久化在 `repositories` 表。存图引入"源 vs 副本"两套事实，重建路径一旦演进，旧快照立即过期。当前设计的零漂移原则（read graph ≡ projection）正是为此。

**收敛**：这个质疑对"把图当事实存"成立，对"把图当衍生缓存存"不成立。`decision_embeddings` 的先例证明：衍生数据可以持久化，只要来源永远可重建、副本只用于提速、且带失效机制。存图的正确姿势是缓存，不是事实。

### 2.2 质疑二：以"仓库组织 url"为户口本，粒度错位

`repositories.url` 已经是仓库的唯一身份证，仓库级户口本诉求已满足。但世界层图是**跨仓库的边集合**，一张图的身份应是"基于哪一组仓库、用哪个算法版本、在哪个时刻构建"，而不是任何一个 url。拿 url 当图的户口本，是把"人的身份证号"当"全家福照片的编号"。

**收敛**：图的户口本 = `(org_id, fingerprint)`，其中 fingerprint 由参与构建的仓库集合与算法版本共同决定。仓库增删或算法变更时 fingerprint 变化，快照自然失效。

### 2.3 质疑三：照搬历史决策的事件投影模式，语义冲突

决策链是"事件追加 → 不可变投影"，因为决策是已发生的事实。世界层图是"扫描结果 → 重扫覆盖"，是可重算、会过期的派生物。若照搬 `decision_chains` 的不可变投影，每次重扫追加一个版本，图就从"当前图"退化成"扫描审计历史"。

**收敛**：参考对象应是 `decision_embeddings`（衍生缓存表：`(org, 主键, JSON 列)` + 端口 + InMemory 孪生 + 幂等回填），而不是 `decision_chains`（事实投影）。历史决策的存储值得参考的是"可移植 JSON 列 + 端口解耦 + 内存孪生"这套壳，不是"事件追加不可变"的语义。

### 2.4 质疑四：更便宜的解法存在，先别建表

重复构建成本最直接的消除手段是给两个服务加 `@cached_service`（进程内懒加载、复用）。容器里 30 处服务都用这个模式，唯独这两个没有。单进程内缓存能消除绝大多数重复成本，持久化表的必要性只在"多进程部署 + 进程重启 + 大组织"叠加时才显现。

**收敛**：成立。所以方案分两步走——第一步零表结构，先解决今天 95% 的重复成本并加埋点；第二步在数据证明需要时再落快照表。跳过第一步直接建表，是用大炮打蚊子。

### 2.5 质疑五：没有失效机制的缓存是坏缓存

仓库重扫、新增、移除后，缓存图若不失效，编排会按过期的依赖分批执行——比不缓存更危险。

**收敛**：失效机制必须与存储一起设计，不能后补。指纹失配即重建，语义与 `decision_embeddings` 的 pending 回填同构：源变化 → 标记待重建 → 读时重建并覆盖。

### 2.6 审查结论

- 世界层图**有必要缓存并最终持久化**：今天就有真实的重复成本（每次分类/计划全量重建、无任何缓存），规模与多进程下成本线性放大。
- 但存的是**衍生缓存，不是事实**：`metadata_payload` 永远是事实源，图快照只是提速用的投影，必须可随时从源重建。
- 户口本是 **`(org_id, fingerprint)`**，不是 url。
- 实施**分两步**：先进程内缓存 + 埋点（零表），数据证明需要后再落快照表。

## 3 方案总览

```
第一步（零表，立刻做）
  confirmation_service / plan_integration_service 的图构建改为进程内懒加载缓存
  + 每次重建埋点（耗时、节点数、边数）落结构化日志

第二步（规模 / 多进程证明需要时做）
  GraphStore 端口 + world_graph_snapshots 表 + InMemory 孪生
  + fingerprint 失效机制 + 容器接线（完全对齐 decision_embeddings 模式）
```

两步之间由埋点数据决定推进时机：重建耗时稳定在亚毫秒且单进程部署，则停留在第一步；重建耗时进入秒级或启用多 worker，则推进第二步。

## 4 第一步：进程内缓存与测量

### 4.1 改动

在 `container.py` 给 `confirmation_service` 与 `plan_integration_service` 的图构建加进程内缓存。两条实现路线：

- 复用既有 `@cached_service` 语义，把"profiles + graph"作为一个整体懒加载并缓存；
- 或在模块内用 `functools.lru_cache` 包一层带指纹的构建函数。

倾向路线一（与容器既有 30 处模式一致，无新概念）。注意缓存的是**图结构**，不是 LLM 客户端——`confirmation_service(llm_client)` 的 `llm_client` 参数保持每次传入，避免把请求级对象卷进进程级缓存。

### 4.2 测量埋点

在 `DependencyGraphService` 构建入口加一条结构化日志：`graph_build profile_count=.. edge_count=.. duration_ms=..`。阈值告警：单次重建超过 500ms 时按 WARN 记录。这些数据是第二步决策的依据。

### 4.3 验收

- 同一进程内连续两次 `confirmation_service` 调用，第二次不再触发 `catalog.list()`（可用测试断言计数）。
- 仓库扫描更新后，缓存失效（重建）——指纹或显式失效钩子。
- 日志中出现 `graph_build` 记录。

## 5 第二步：GraphStore 端口与快照表

### 5.1 端口契约

```
class WorldGraphStore(Protocol):
    async def load(self, *, fingerprint: str) -> WorldGraphSnapshot | None
    async def save(self, snapshot: WorldGraphSnapshot) -> None
```

`load` 按指纹精确匹配；`save` 幂等 upsert（同指纹覆盖）。端口只回答"这张图在不在、新不新"，不负责构建——构建永远由 `DependencyGraphService` 从 catalog 完成。

### 5.2 模型

```
class WorldGraphSnapshot:
    org_id: UUID | None            # None = 全局图（当前实现无 org 隔离时的形态）
    fingerprint: str               # 唯一键
    edges: list[GraphEdge]         # 边集合（与 DependencyGraphService 输出同构）
    built_at: datetime             # 构建时刻
    source_sha: str                # 参与构建的仓库集合 + 算法版本的指纹（见 5.4）
```

### 5.3 表结构

`world_graph_snapshots`（SQLite / PostgreSQL 双库，JSON 列可移植，与 `decision_embeddings` 同款）：

| 列 | 类型 | 约束 |
|---|---|---|
| org_id | uuid / null | 可空，全局图 |
| fingerprint | text | 主键 |
| edges | JSON_DOCUMENT | 边序列化 |
| built_at | datetime | — |
| source_sha | text | 失效判据 |

### 5.4 指纹与失效

`source_sha = sha256(sorted(所有参与仓库的 url) + "|" + graph_algorithm_version)`。

读路径：

```
profiles = await catalog.list()                    # 事实源，永远读
sha = compute_source_sha(profiles)
snapshot = await store.load(fingerprint=sha)        # 按指纹查缓存
graph = snapshot.edges 若命中，否则 DependencyGraphService(profiles) 重建并 save
```

仓库增删、依赖证据更新、算法版本升级 → sha 变化 → 命中失败 → 重建并覆盖。**每次调用仍会读 catalog**（那是事实源），缓存消除的是"解析证据 + 建图 + 建索引"这部分纯计算成本；若连 catalog 全表读也要省，那是另一层缓存（catalog 级），不在本方案范围。

### 5.5 InMemory 孪生与接线

- `InMemoryWorldGraphStore`（字典实现，供测试与单进程模式）与 PostgreSQL 实现并存，行为经同一组契约测试核对——与 `DecisionEmbeddingStore` 的孪生测试同法。
- 容器：`world_graph_store` 端口在测试环境注入内存孪生，生产注入 PG 实现；`confirmation_service` / `plan_integration_service` 改为"读 catalog → 查快照 → 命中用之 / 未命中重建并回填"。

## 6 测试清单

| 层 | 测试 |
|---|---|
| 端口契约 | `load` 未命中返回 None；`save` 幂等（同指纹两次覆盖不报错、不产生双行）；`load` 精确按指纹匹配 |
| 指纹 | 仓库集合变化 → sha 变化 → 旧快照失效；算法版本变化 → 失效；无关字段变化（如仓库描述）不改变 sha |
| 读路径 | 命中时用缓存边、不触发重建；未命中时重建并回填；重建失败（catalog 异常）时回退"无图"，不阻塞分类（增强非前置） |
| 孪生核对 | 内存孪生与 PG 实现对同一序列操作结果一致 |
| 第一步回归 | `confirmation_service` 二次调用不重复读 catalog；`llm_client` 参数不进入进程级缓存 |
| 架构 | 业务模块不依赖 PG 实现（只依赖端口）；接线只发生在组合根 |

## 7 里程碑与验收

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 | 第一步：进程内缓存 + 埋点 | 二次调用不重读 catalog；日志出现 `graph_build`；测试全绿 |
| M2 | 第二步：端口 + 快照表 + 孪生 + 失效 | 契约测试、指纹测试、孪生核对全绿；读路径测试覆盖命中/未命中/失败回退 |
| M3 | 接线 + 回退验证 | 生产注入 PG 实现；`graph=None` 时全链路回退 MVP；全量回归 + ruff 全绿 |

M1 与 M2 之间以埋点数据为门禁：`graph_build` 单次重建进入秒级，或部署形态转为多 worker，才启动 M2。

## 8 边界与红线

- 图快照是**派生缓存**，永远可从 `metadata_payload` 重建；任何情况下不得成为第二事实源。源与副本不一致时，以源为准并重建。
- 读路径**每次仍读 catalog**（事实源）。本方案省的是建图计算，不是 catalog 读取。
- 世界层图按"重扫覆盖"演进，不套用事件追加的不可变投影语义。
- 第一步必须先行：在埋点数据出现之前，不启动第二步建表（YAGNI 门禁）。
