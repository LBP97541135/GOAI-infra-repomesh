# 仓库发现精度优化 - 方案设计

> 创建时间：2026-08-05
> 最后更新：2026-08-05
> 状态：**V6 为第一层 MVP 最终版本**

---

## 一、问题背景

验证集第一轮（V1）跑完后，仓库发现系统的指标：

| 指标 | V1 值 | 目标值 | 达标？ |
|------|-------|--------|--------|
| Recall | 87.2% | ≥ 80% | ✅ |
| Precision | 50.5% | ≥ 60% | ❌ |
| F1 | 60.5% | — | — |

平均每个用例预测 10.1 个仓库，其中 5.4 个是误报，误报率 53.6%。

### 三个根因

| 根因 | 分析 | 占比 |
|------|------|------|
| **低分没过滤** | LLM 返回 0.3~0.7 分的仓库直接进了结果，没有任何后过滤 | ~40% |
| **Prompt 鼓励多报** | system prompt 用了 "likely to need changes" 和 "if unsure, include them"，变相鼓励宁多勿漏 | ~35% |
| **AutoCard 粒度不够** | LLM 仅凭 top_dirs + deps + recent_commits 无法精确区分功能相似的仓库 | ~25% |

---

## 二、优化方案设计

### P0：后过滤——丢弃低分结果

在 `discovery.py` 的 `parse_llm_response` 之后，添加分数阈值过滤：

```python
_MIN_CONFIDENCE = 0.7
evidence = [e for e in evidence if e.score >= _MIN_CONFIDENCE]
```

**预期**：误报减少 ~40%，Precision 提升约 10 个百分点。

### P1：Prompt 收紧——去掉鼓励多报的措辞

修改 `discovery.py` 的 `build_discovery_prompt` 中 system prompt：

| 当前 | 修改后 |
|------|--------|
| "which repositories are **likely** to need changes" | "which repositories **will** need changes" |
| "If unsure, include them as candidates with confidence ≤ 0.5" | 删除这整句 |
| 新增 | "Only include repositories where you have POSITIVE EVIDENCE (shared dependencies, API calls, or commit history) linking them to the requirement. Do NOT include repositories merely because they are in the same domain." |

**预期**：误报减少 ~20%，Precision 提升约 5 个百分点。

### P2：Team Manager 二次确认

符合方案文档步骤 4（确认范围）和步骤 5（建立协作计划）。

#### 整体流程

```
阶段 1：总 Manager 全局扫描 → 候选列表（高 Recall）
    ↓
阶段 2：每个候选仓库的 Team Manager 判断
    ├── REQUIRED → 确认涉及，开始制定改动方案，返回给总 Manager
    ├── MAYBE   → 可能间接涉及，保留但标注低置信
    └── EXCLUDED → 误判，返回排除原因
    ↓
阶段 3：Project Manager 汇总 → 最终范围 + 方案
```

#### V3 版本（严格确认）

prompt 策略——**需要证据才保留**：

```
Be strict: only say REQUIRED if you have concrete evidence.
Do NOT say REQUIRED just because the topic seems related.
If your repository handles a different concern, say EXCLUDED.
```

#### V4 版本（组合优化）

V3 矫枉过正后，V4 引入三项改进：

| 措施 | V3 | V4 |
|------|----|----|
| 默认判断 | 需要证据才保留 | 需要证据才排除 |
| 上下文 | Manager 从零开始 | 传递总 Manager 的 rationale + confidence |
| 分类 | 二选一 REQUIRED/EXCLUDED | 三层 REQUIRED/MAYBE/EXCLUDED |

#### Team Manager 的能力边界

通过 V3~V7 的迭代实验，明确了 Team Manager 的能力边界：

| Team Manager 能看到的 | Team Manager 看不到的 |
|---------------------|---------------------|
| ✅ 自己的依赖（pom.xml 中的 deps） | ❌ 谁调用了自己（反向依赖） |
| ✅ 自己的 API | ❌ 其他仓库的内部信息 |
| ✅ 自己的 commit 历史 | ❌ 仓库间的调用链路 |

**结论**：Team Manager 不应该承担"判断仓库是否与需求相关"的职责（这需要全局视角），而应该专注于"确认涉及后，制定具体改动方案"。真正的误报排除应交给第二层图推理（call_graph 确定性分析）。

## 三、V5：需求增强

模拟真实用户-LLM 交互，用总 Manager 的需求分析模块对原始需求做澄清补充。

流程：
1. `RequirementAnalyzer` 分析需求缺失维度（业务场景、行为描述等）
2. LLM 模拟 PM 追问 + 用户回答的对话
3. 生成增强后的需求描述（平均从 69 字扩展到 253 字）
4. 用增强需求跑 V4 的发现 + 确认流程

**定位**：V5 不改变发现和确认逻辑，只改善输入质量。适用于 hard 用例（需求文本信息不足的场景）。

---

## 四、V6：pom.xml 解析修复

发现扫描器不支持 Java 项目的 pom.xml，导致全部 42 个仓库的 deps 字段为空。修复后 44/45 个仓库有了依赖信息。

这是**纯收益的 bug fix**——deps 信息从无到有，让总 Manager 能基于依赖关系做更准确的发现。

---

## 五、V7：prompt 调优实验（已回退）

把 prompt 改为中文，调整确认阶段的判断标准，目标排除率 20~30%。实际结果排除率达到 37%，Precision 提升到 69%，但 Recall 跌到 64%——排除太激进。

**回退原因**：Team Manager 信息不足，无法准确判断"无关仓库"。排除机制的精细化需要第二层图推理辅助，而非靠 prompt 调优。

## 六、第一层 MVP 的最终设计

### 分工

| 角色 | 职责 | 依据 |
|------|------|------|
| 总 Manager | 全局扫描，高 Recall 召回 | 能看到所有仓库的 AutoCard |
| Team Manager | 确认涉及后制定改动方案 | 了解自己仓库的内部结构 |
| 第二层图推理 | 排除误报 + 补充漏报 | call_graph 确定性分析 |

### 当前指标（V6）

| 指标 | 发现阶段（总 Manager） | 确认后（Team Manager） |
|------|----------------------|----------------------|
| Recall | **84.6%** | 83.5% |
| Precision | 50.3% | 50.7% |

**结论**：第一层 MVP 已 OK。Recall 84.6% 达标，Precision 的提升交给第二层。
