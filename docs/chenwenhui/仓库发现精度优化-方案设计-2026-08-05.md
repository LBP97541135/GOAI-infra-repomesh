# 仓库发现精度优化 - 方案设计

> 创建时间：2026-08-05
> 状态：方案确认

---

## 一、问题背景

验证集第一轮跑完，仓库发现系统的指标：

| 指标 | 当前值 | 目标值 | 达标？ |
|------|--------|--------|--------|
| Recall | 87.2% | ≥ 80% | ✅ |
| Precision | 50.5% | ≥ 60% | ❌ |

平均每个用例预测 10.1 个仓库，其中 5.4 个是误报，误报率 53.6%。

### 三个根因

| 根因 | 分析 | 占比 |
|------|------|------|
| **低分没过滤** | LLM 返回 0.3~0.7 分的仓库直接进了结果，没有任何后过滤 | ~40% |
| **Prompt 鼓励多报** | system prompt 用了"likely to need changes"和"if unsure, include them"，变相鼓励 LLM 宁多勿漏 | ~35% |
| **AutoCard 粒度不够** | LLM 仅凭 top_dirs + deps + recent_commits 无法精确区分功能相似的仓库 | ~25% |

---

## 二、优化方案

### P0：后过滤——丢弃低分结果

在 `parse_llm_response` 之后，添加分数阈值过滤：

```python
MIN_CONFIDENCE = 0.7

# 过滤掉低分候选
evidence = [e for e in evidence if e.score >= MIN_CONFIDENCE]
```

**预期效果**：误报减少 ~40%，Precision 提升约 10 个百分点。

**风险**：可能过滤掉少量真实需要但低分的仓库。从验证集数据看，所有 Ground Truth 命中的分数都 ≥ 0.7，风险可控。

### P1：Prompt 收紧——去掉鼓励多报的措辞

修改 `build_discovery_prompt` 中的 system prompt：

| 当前 | 修改后 |
|------|--------|
| "which repositories are **likely** to need changes" | "which repositories **will** need changes" |
| "If unsure, include them as candidates with confidence ≤ 0.5" | 删除这整句 |
| 新增 | "Only include repositories where you have positive evidence (shared dependencies, API calls, or commit history) linking them to the requirement. Do NOT include repositories merely because they are in the same domain." |

**预期效果**：误报减少 ~20%，Precision 提升约 5 个百分点。

### P2：Repository Manager 二次确认 + 方案制定

符合方案文档步骤 4（确认范围）和步骤 5（建立协作计划）。

#### 流程

```
阶段 1（已实现）：总 Manager 全局扫描 → 候选列表（高 Recall）
    ↓
阶段 2（新增）：并行派发给每个候选仓库的 Repository Manager
    ↓
    ├── REQUIRED：
    │   ├── 返回本仓库的改动方案（Workstream 草案）
    │   └── 如有一度依赖缺失，返回 missing_dependencies
    │
    └── EXCLUDED：
        └── 返回 "无关" + 排除原因
    ↓
阶段 3（Project Manager 汇总）：
    ├── 收集所有 REQUIRED 仓库的方案
    ├── 对 missing_dependencies 做一轮补充召回（只确认不扩展）
    ├── 收集所有 EXCLUDED 信号 → 从候选列表移除
    └── 输出最终范围 + 各仓库 Workstream 草案
```

#### Repository Manager 的返回结构

```json
{
  "status": "REQUIRED",
  "confidence": 0.9,
  "plan": {
    "summary": "需要修改邮件发送接口的调用参数格式",
    "files_likely_affected": ["src/.../NotificationController.java"],
    "change_type": "bugfix"
  },
  "missing_dependencies": ["ts-xxx-service"]
}
```

或：

```json
{
  "status": "EXCLUDED",
  "reason": "本仓库管理用户头像上传，与订票邮件通知无关"
}
```

#### Repository Manager 的 Prompt

```
你是仓库 {repo_name} 的负责人。
以下是你的仓库概况：{autocard}

以下是本次需求：{requirement}

请基于你仓库的实际功能、依赖和 API 来判断：
1. 你的仓库是否需要为这个需求修改代码？
2. 如果需要，简述改动方案。
3. 如果你的仓库依赖了不在候选列表中的仓库，指出缺失的依赖。

判断标准：
- REQUIRED：有明确证据（API 调用、数据依赖、功能直接对应）
- EXCLUDED：功能无关、不会受影响

不要因为"可能相关"就报 REQUIRED。只有有具体证据时才报。
```

#### 关键约束

| 规则 | 理由 |
|------|------|
| 补充召回只允许一度依赖 | 防止级联扩展导致仓库蔓延 |
| 被补充的仓库只做确认，不再扩展 | 同上 |
| 所有确认并行执行 | 性能 |
| Repository Manager 基于本仓库代码判断 | 提升精度 |

**预期效果**：误报减少 ~30%，Precision 提升约 15 个百分点。

