## 2. 第一遍审查：拷问"为什么"（方向是否正确、是否最小）

### Q1. 问题真实吗？决策链到底断在哪？
**追问**：如果现有系统已经能回答"这个需求干了什么"，那这个问题可能不存在，方案就是无病呻吟。
**查证**：现有系统能回答"每个仓库的当前状态"（plan_snapshot 状态机），但**不能**回答"这次需求为什么这样分档、谁批准的、当时波及哪些仓库"——因为分类/确认记录不带 project_id（E6），与需求之间是断的；PR 观察不带 project_id（E4），与需求之间也是断的。
**结论**：问题真实，且**比文档描述的更精确**——不是"没有历史记录"，是"历史记录存在但串不成链"。

### Q2. MVP 是什么？从第一性原理倒推
**追问**：面试官要的"历史上下文深度理解"，最少的交付是什么？
**推导**：历史上下文 = 一串"是什么→为什么→谁批准→影响谁"。最小可演示闭环 = **输入 project_id → 输出完整链路（分类→确认→task→PR），每环带依据与批准人**。RAG、相似推荐、图、前端展示都不是这个闭环的必要部分。
**结论**：MVP = 决策单 + 链 + 一条追溯查询。其余全部是后续增量。

### Q3. 决策单表需要吗？链 vs payload 的边界
**追问**：源数据（plan_snapshot、task、change_set、message）都已持久化，为什么要多一张 decision 表？会不会是双写（再造一个 `supplemented_repos`）？
**查证**：源数据分属 4 个模块、schema 各异、缺链字段，跨模块查询违反 AGENTS.md（"不得直读他模块 schema"）。所以统一视图需要一张自己的表。
**结论**：需要，但**只存链不存 payload**——`decision` 表存 {id, step, upstream_ref, 源指针, 证据指针}，payload 留在源模块。凡是要把 payload 全拷进决策表的做法都是双写，否决。

### Q4. "requirement 实体化"到底要做什么？（对已拍板决策②的重新审视）
**追问**：用户已批准"requirement 实体化 id 随主流程补"。但 E1 显示 requirement = project_id **已经存在**。那决策②的真实内容是什么？
**结论**：决策②的真实内容是**字段贯通**，不是建实体：
- `PlanSnapshot(plan_version=1)` 就是需求实体，无需新表；
- 要补的是**下游环节携带 project_id**：confirmation（E6）、PR 观察（E4）、classification 记录；
- 若按原理解"新建 requirement 表"→ 制造第二个事实源，与 project_id 打架 → **否决，改为贯通**。

### Q5. 影响面时点快照的数据从哪来？（对已拍板决策③的落地检查）
**追问**：`affected_repository_ids` 决策发生时从哪定格？
**查证**：决策发生时数据已存在——分类/确认时 `final_repos = REQUIRED + MAYBE`（confirmation.py `final_repos` 属性）；集成时 `execution_batches` 在 plan_snapshot。
**结论**：时点快照**零新增采集成本**，只是把"决策当时已经算出的仓库集合"定格进决策单。决策③正确且便宜。

### Q6. L4 证据可靠吗？
**追问**：决策单的 evidence_ref 指向什么才可靠？
**查证**：红线 5 已定"指 RepoMesh 侧持久化消息"。E5 证实 `DECISION` 消息类型存在、`CollaborationMessageRecord` 镜像持久化；E8 证实房间可精确路由（DM vs 仓库房）。
**结论**：L4 已具备，**无需新增基础设施**。要补充的是把"过程证据（Room 消息）"与"结果证据（classification_evidence_version 指纹）"分开存——前者是"怎么讨论的"，后者是"结论依据什么"，混淆会导致审计说不清。

### Q7. RAG 是必需还是加分？顺序对不对？
**追问**：RAG 的价值依赖什么？
**推导**：相似检索的价值 = 检索到的"相似历史决策链"的质量。没有干净的链数据，embedding 检索的就是垃圾。
**结论**：**追溯先行，RAG 后置**——链数据未稳定前做 RAG 是空中楼阁。RAG 保持"加分项"定位，独立推进，不进 MVP。

### 第一遍审查结论
| 发现 | 类型 | 处置 |
|---|---|---|
| requirement 实体已存在（=project_id），无需新建 | 过度设计 | 改为字段贯通 |
| 决策单表只存链+指针，不拷 payload | 过度设计 | 落地方案固化此边界 |
| RAG 从 MVP 剥离，追溯先行 | 过度设计 | 阶段后置 |
| 锚点大部分已存在，工作量比观感小 | 事实遗漏 | 落地方案据此压缩规模 |
| 过程证据与结果证据需分开存 | 补充 | 决策单 schema 加 evidence 双指针 |

## 3. 第二遍审查：拷问"怎么不翻车"（实施视角）

### B1. 模块边界（AGENTS.md 硬约束）
**风险**：决策链横跨 4 个模块。若新建 `decision_chain` 模块直读 4 张表 → 违反"Never query or write another module's PostgreSQL schema directly"。
**对策**：决策链模块**只依赖生产者契约**，路线 = 事件投影：
- 各 producer 在关键动作处 emit `EventEnvelope`（E7 骨架已有；intake 已有先例）；
- `decision_chain` 订阅事件 → 投影进自己的表；
- 跨模块引用一律走 `repomesh.modules.<producer>.contracts`。
**先决条件**：给 task_orchestration / delivery 补事件发射点（契约先行，单 PR 单模块）。

### B2. 写入幂等与重放（AGENTS.md 硬约束）
**风险**：事件投影若重放/乱序，决策单会重复或错序。
**对策**：
- `decision_nodes.event_id` 唯一约束 → 重放幂等（参照 `(project_id, plan_version)` 唯一约束先例 E1）；
- 投影按 `recorded_at` 单调追加，business_time 与 recorded_at 分离（见 B4）；
- 同 step 多事件（改档多次）→ 版本化，不覆盖。

### B3. 回填（历史数据）
**风险**：存量 plan_snapshot/task/PR 中，confirmation 无 project_id（E6）、PR 无 project_id（E4），无法推导。
**对策（第一性原理：不猜）**：
- **可回填**：task（自带 project_id，E3）、PR（经 change_set 反查 project_id，E4）→ 回填 upstream_ref；
- **不可回填**：confirmation/classification 存量记录无 project_id 且不可推导 → **不回填**，标 `source=legacy`，只对 7 步修复后新产生的数据保证链完整；
- 伪造的链比没有链更危险（审计翻车），宁缺毋滥。

### B4. 双时态
**风险**：回填/重放的决策单时间线错乱 → 追溯顺序失真。
**对策**：`business_time`（决策发生时间，来自事件）+ `recorded_at`（投影落库时间）双字段。查询按 business_time 排序。

### B5. 并发写入
**风险**：确认流程是 ThreadPoolExecutor 4 并发（已实现），多条 confirmation 决策单并发投影。
**对策**：`(project_id, step, version)` 唯一约束 + 投影层串行化（单消费者/顺序处理）；与现有 `_confirm_parallel` 的 copy_context 模式不冲突。

### B6. 确认与改档的关系
**风险**：确认决策单和改档决策单若做成两个独立链节，会歧义（改档本身就是确认过程的一部分）。
**对策**：确认决策单内嵌 `adjustments` 子记录，或同一 step 的 v2 版本——**不引入独立"改档 step"**，链保持 6 个 step 与功能板块文档一致。

### B7. 读路径 join 成本
**风险**：若决策单只存"指针"，追溯查询要跨 4 个模块契约端口 join → 慢且脆弱。
**对策**：决策单存**链字段 + 轻量 payload 摘要 + 源指针**（三层）：
- 链字段：step/status/upstream_ref/时间；
- 摘要：决策结果值（三档结果、确认/驳回、task 标题、PR url）——够展示用；
- 指针：源记录 id，按需深查。
这修正了第一遍的"只存指针"，落到"摘要+指针"。

### B8. RAG embedding 时机
**风险**：embedding 调用（外部队列/API）进写入主路径 → 拖慢决策落库，违反"每笔写都快且稳"。
**对策**：embedding 生成走**批量异步**（独立表 `decision_embeddings`，按 recorded_at 分批），查询向量只在读取时生成。写入路径永不调用 embedding 服务。

### B9. 测试与验收
**行为测试**（按 AGENTS.md "tests for behavior"）：
- 贯通测试：intake→classification→confirmation→task→PR 各环节断言 project_id 存在且一致；
- 幂等测试：同一事件重放两次，决策单不重复；
- 链完整测试：trace 一个完整需求 → 6 个 step 齐全、顺序正确、每环有证据；
- 契约测试：decision_chain 与各 producer 的端口契约（对照现有 delivery-read-model 契约测试范式）。

### B10. 与 7 步修复的关系
**确认**：L1 锚点贯通必须随 7 步修复一起做——"上游引用只在数据产生的当下可知，事后补只能靠猜"（B3 已证）。**本落地方案的 Phase 1 与 7 步修复合并进同一批 PR**，不做两遍返工。

### 第二遍审查结论（5 项落地修正）
1. 事件投影路线，不直连他模块 schema（B1）；
2. event_id 唯一约束 + 版本化，幂等可重放（B2/B5）；
3. 回填只做可证明的部分，不可推导标 legacy（B3）；
4. 决策单 = 链字段 + 轻量摘要 + 源指针（B7）；
5. RAG 批量异步，不进写入主路径（B8）。

## 4. 落地方案

### 4.1 总原则（两遍审查收敛）
```
1. 决策链 = 字段贯通 + 统一只读视图，不是新造一套系统
2. 决策单只存"链 + 摘要 + 指针"，payload 留在源模块（唯一事实源，不双写）
3. 写入走事件投影，幂等可重放，跨模块只走契约
4. 追溯先行，RAG 后置，AGE 触发才上
5. 只对修复后的新数据保证链完整；历史数据能证明才回填
```

### 4.2 架构决策
| 决策 | 选择 | 理由 |
|---|---|---|
| 归属模块 | **新模块 `modules/decision_chain`**（读侧投影）+ 各 producer 补事件发射（写侧） | 不违反模块边界；单一 owner |
| 存储 | 决策链：PG 关系表（`decision_chain_nodes`）；向量：`decision_embeddings`（✅ 已落地，JSON/JSONB 列 + 应用层 cosine，不装 pgvector） | 线性链 2-3 跳，表足够；小规模向量应用层算即可 |
| 数据源 | `EventEnvelope` 事件流（intake 已有先例） | 跨模块唯一合法通路 |
| 事实源 | 各 producer 的源记录是事实源；决策链表是**统一只读投影** | 延续"同一事实单一拼写"红线 |
| 链根 | `project_id`（= requirement 实体，E1） | 无需新实体 |

### 4.3 数据模型（decision_chain 模块，自持 schema）
```
decision_chain_nodes
├─ decision_id      UUID  PK
├─ event_id         UUID  UNIQUE        -- 幂等：重放不重复
├─ project_id       UUID  FK(逻辑)      -- 链根 = requirement（E1）
├─ organization_id  UUID                -- L1 命名空间（E2：源表无此列，投影自持）
├─ step             enum                -- classification/confirmation/integration/task/pr
├─ version          int                 -- 同 step 多事件（改档）版本化，不覆盖
├─ status           enum                -- proposed/confirmed/rejected/adjusted
├─ actor            enum+id             -- llm / human(确认) / 哪个 agent
├─ upstream_ref     UUID | NULL         -- 链：父决策 id（requirement 根链在此串起）
├─ evidence_refs    jsonb               -- [结果证据: fingerprint/scan_artifact] + [过程证据: message_id]
├─ payload_summary  jsonb               -- 轻量结果（三档值/确认结论/task 标题/PR url）——够展示
├─ affected_repository_ids  jsonb       -- 时点快照（决策③）
├─ business_time    timestamptz         -- 决策发生时间（双时态，B4）
└─ recorded_at      timestamptz         -- 投影落库时间

decision_embeddings（✅ 已交付，L3）
├─ decision_id  UUID  PK/UNIQUE
├─ embedding    json/jsonb        -- 向量列表（双库兼容，应用层 cosine，不装 pgvector）
└─ recorded_at  timestamptz       -- 批量生成（B8），pending 判定依据
（org 隔离经 join decision_chain_nodes 实现，无冗余列；文本/时间取决策单原字段）
```

### 4.4 分阶段实施

**Phase 0 —— 契约先行（先于一切代码）**
- 产出：`docs/contracts/decision-chain-v0.1.md`，定义：step 枚举、`DecisionChainNode` 数据结构、事件类型表（`ClassificationDecided` / `ConfirmationDecided` / `IntegrationDecided` / `TasksPlanned` / `PullRequestObserved`）、`DecisionChainStore` 端口（append/trace/find_similar_structural）。
- 验收：契约评审通过；`decision_chain` 模块骨架（module.toml/README/ports）落盘。

**Phase 1 —— 锚点贯通（与 7 步修复合并，同一批 PR）**
- repository_intelligence：confirmation/classification 流程携带并持久化 `project_id`；补 `ClassificationDecided`、`ConfirmationDecided` 事件发射（含 org/project 字段、指纹、final_repos 时点快照）。
- task_orchestration：task 已带 project_id（E3）→ 仅补 `TasksPlanned` 事件发射（含 task_id + project_id + repository_id + upstream=confirmation）。
- delivery：PR 观察补 project_id（经 change_set 反查，E4）；补 `PullRequestObserved` 事件。
- 验收：贯通测试绿——新产生的数据五环节 project_id 一致。

**Phase 2 —— 决策链投影（decision_chain 模块主体）**
- 表 `decision_chain_nodes` 落库（4.3）；事件订阅 → 幂等投影（event_id 唯一约束）；
- `trace_decision_chain(project_id)` 端口实现：按 business_time 输出 6 step 链 + 摘要 + 证据指针；
- 验收：幂等测试、链完整测试绿。

**Phase 3 —— 追溯 API + 演示**（2026-08-28 已交付，见契约 §6.4）
- `GET /api/v1/decision-chains/{project_id}`（api 层只依赖 application 契约）；
- 前端可选（比赛演示可复用现有确认页面的样式）；
- 验收：审计场景走查——输入需求 id，展示完整链路与证据（`tests/test_decision_chain_trace_api.py` 走查测试绿）。

**Phase 4 —— 相似决策检索 + RAG（加分项，独立推进）**（2026-08-28 结构化检索已交付，见契约 §6.5）
- 结构化检索（SQL：同仓库/同模块/同依赖）先行——覆盖 80% 价值；✅ 已交付：`DecisionChainSimilarityService` + `GET /api/v1/decision-chains/{project_id}/similar`（`tests/test_decision_chain_similarity.py`、`tests/test_decision_chain_similar_api.py` 走查测试绿）；
- pgvector `decision_embeddings` 批量生成（B8）；新需求进 pipeline 时检索 Top-K → 注入 prompt；（Phase 4b，独立 PR——改动 repository_intelligence，与本次 decision_chain 模块闭环分开推进）
