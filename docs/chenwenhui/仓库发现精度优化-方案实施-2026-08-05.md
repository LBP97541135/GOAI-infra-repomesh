## 二、各阶段详情

### V4：组合优化（放宽确认 + 传递理由 + 三层分类）

**代码变更**：`confirmation.py` 修改

| 措施 | 改动 |
|------|------|
| 放宽确认标准 | prompt 从"需要证据才保留"改为"需要证据才排除"，默认 REQUIRED/MAYBE |
| 传递发现理由 | `confirm()` 新增 `discovery_evidence` 参数，把总 Manager 的 rationale 和 confidence 传给 Repository Manager |
| 三层分类 | 新增 MAYBE 状态；REQUIRED + MAYBE 都保留在最终列表中 |

**效果**：

| 指标 | V3 → V4 | 说明 |
|------|---------|------|
| Recall | 50.9% → **78.3%** | +27.4%，不再大量误排 |
| Precision | 93.3% → **80.4%** | -12.9%，仍远超 V1 |
| F1 | 61.7% → **76.4%** | +14.7%，找到最佳平衡 |

### P0：后过滤（分数 < 0.7 丢弃）

**代码变更**：`discovery.py` 添加 `_MIN_CONFIDENCE = 0.7` 常量和过滤逻辑

```python
evidence = [e for e in evidence if e.score >= _MIN_CONFIDENCE]
```

**效果**：对 V1 → V2 的影响很小（Recall +2.4%，Precision -0.4%），因为 LLM 在新 prompt 下仍倾向于给大多数仓库 ≥ 0.7 的分数。

### P1：Prompt 收紧

**代码变更**：`discovery.py` 的 system prompt 修改

| 修改点 | 旧 | 新 |
|--------|----|----|
| 核心措辞 | "likely to need changes" | "will need changes" |
| 低信号建议 | "if unsure, include them with confidence ≤ 0.5" | "Do NOT include these unless you have concrete evidence" |
| 新增规则 | — | "Only include repositories where you have POSITIVE EVIDENCE" |

### P2：Repository Manager 二次确认

**新增文件**：
- `application/confirmation.py`：`ConfirmationService` + `ConfirmationResult` + `ConfirmationSummary`
- `tests/test_confirmation.py`：17 个测试

**流程**：
```
发现阶段（总 Manager）→ 候选列表（平均 10 个）
         ↓
确认阶段（每个仓库的 Repository Manager）→ 逐个判断 REQUIRED/EXCLUDED
         ↓
最终列表（平均 2.1 个，Precision 93.3%）
```

**效果**：Precision 大幅提升至 93.3%，但 Recall 降至 50.9%——Repository Manager 过度排除了真正需要的仓库。

## 三、V3 逐用例分析

### 典型案例

| 用例 | 发现候选 | 确认后 | Ground Truth (direct) | 问题 |
|------|---------|--------|----------------------|------|
| TT-012 | 2 | 2 (user, auth) | user, auth | ✅ 完美 |
| TT-013 | 7 | 2 (order, order-other) | order, order-other | ✅ 精准 |
| TT-001 | 5 | 1 (notification) | preserve, preserve-other, cancel | ❌ 过度排除，3 个 direct 全漏 |
| TT-003 | 15 | 0 | 9 个 admin 服务 | ❌ 全被排除 |
| TT-010 | 5 | 2 (payment, inside-payment) | payment, preserve, preserve-other | ❌ 2 个 direct 被误排 |

### 根因分析：为什么 Recall 暴跌

1. **Repository Manager 信息不足**：每个 Manager 只看到自己仓库的 AutoCard（top_dirs + deps + recent_commits），但 AutoCard 的 commit 历史可能不含本次需求的关键信息。比如 TT-001 中 `ts-preserve-service` 的最近 commit 没有"email"关键词，Manager 就认为"无关"。

2. **Prompt 过于严格**："Be strict: only say REQUIRED if you have concrete evidence"——Manager 在没有明确证据时会倾向 EXCLUDED。

3. **缺少全局上下文**：Manager 不知道"总 Manager 已经选中了我"，它只看到自己的仓库信息和需求，容易做出保守判断。

## 四、优化方向

当前 V3 的主要问题是 **Recall 太低（50.9%）**。需要在 V3 的基础上提升 Recall，同时保持高 Precision。

| 方向 | 具体措施 | 预期效果 |
|------|---------|---------|
| **放宽确认标准** | 修改 prompt：从"concrete evidence"改为"reasonable evidence" | Recall +10~15% |
| **给 Manager 更多上下文** | 告诉 Manager"你被总 Manager 选中了，说明有一定相关性" | Recall +5~10% |
| **三层分类** | REQUIRED / MAYBE / EXCLUDED，MAYBE 的仓库保留但标注低置信 | Recall +15~20% |
| **提高分数阈值** | 发现阶段提高 limit，让更多候选进入确认阶段 | Recall +5% |
