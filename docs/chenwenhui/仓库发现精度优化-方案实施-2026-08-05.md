## 二、各版本详细变更与结果

### V1：原始基线

**改动原因**：建立基准线，了解当前系统表现。

**代码状态**：无后过滤，prompt 鼓励多报（"likely to need changes"、"if unsure, include them"）。

**结果**：Recall 87.2%（达标），Precision 50.5%（不达标），F1 60.5%。

**问题**：误报率 53.6%，平均每例多报 5.4 个仓库。频繁误报的"惯犯"：ts-order-other-service（6 次）、ts-rebook-service（5 次）、ts-route-service（5 次）。

---

### V2：P0 后过滤 + P1 Prompt 收紧

**改动原因**：V1 的 Precision 只有 50.5%，大量误报。根因是低分结果没有过滤 + prompt 鼓励多报。

**具体改动**：

P0 — `discovery.py` 新增后过滤：
```python
_MIN_CONFIDENCE = 0.7
evidence = [e for e in evidence if e.score >= _MIN_CONFIDENCE]
```

P1 — `discovery.py` 的 system prompt 修改：

| 修改点 | 旧 | 新 |
|--------|----|----|
| 核心措辞 | "likely to need changes" | "will need changes" |
| 低信号建议 | "if unsure, include them with confidence ≤ 0.5" | "Do NOT include these unless you have concrete evidence" |
| 新增规则 | — | "Only include repositories where you have POSITIVE EVIDENCE" |

**结果**：Recall 89.6%（+2.4%），Precision 50.1%（-0.4%），F1 61.2%（+0.7%）。

**分析**：P0+P1 几乎没效果。LLM 在收紧的 prompt 下仍倾向于给大多数仓库 ≥0.7 的分数，后过滤形同虚设。根因是 AutoCard 信息粒度不够，LLM 无法仅凭 top_dirs + deps 区分功能相似的仓库。

---

### V3：P2 Team Manager 严格确认（矫枉过正）

**改动原因**：P0+P1 无效，需要更强的过滤机制。引入二次确认——每个候选仓库由独立 LLM 判断是否真的需要修改。

**具体改动**：

新增 `confirmation.py`，实现 `ConfirmationService`：
- 输入：发现阶段的候选仓库列表 + 需求
- 处理：对每个候选仓库，LLM 扮演 Team Manager 做判断
- 输出：REQUIRED（保留）或 EXCLUDED（排除）

prompt 策略——**严格确认**：
```
Be strict: only say REQUIRED if you have concrete evidence.
Do NOT say REQUIRED just because the topic seems related.
If your repository handles a different concern, say EXCLUDED.
```

**结果**：Recall 暴跌至 50.9%（-38.7%），Precision 飙升至 93.3%（+43.2%），F1 61.7%。

**Recall 暴跌根因**：

| 因素 | 说明 |
|------|------|
| Prompt 过于严格 | "only say REQUIRED if you have concrete evidence" → 没有明确证据就排除 |
| AutoCard 信息不够 | Manager 看不到仓库间的调用关系。如 ts-preserve-service 调用了 ts-notification-service 这个事实不在 AutoCard 里 |
| 缺少全局上下文 | Manager 不知道"总 Manager 选中了我"，从零开始判断 |
| 二选一逼迫 | 只有 REQUIRED/EXCLUDED，不确定时被迫选 EXCLUDED |

典型案例：
- TT-003：发现阶段找到 5 个 admin 服务，确认阶段**全部排除**，最终预测 0 个
- TT-001：ts-preserve-service（订票服务）被排除，因为 AutoCard 里没有"email"关键词

---

### V4：组合优化（放宽 + 传理由 + 三层分类）

**改动原因**：V3 矫枉过正，Recall 从 89.6% 暴跌到 50.9%。需要恢复 Recall 同时保持 Precision。

**具体改动**：

`confirmation.py` 三项改进：

**措施 1 — 放宽确认标准**：
```
旧：Be strict: only say REQUIRED if you have concrete evidence
新：Default to REQUIRED or MAYBE unless you have CLEAR evidence
    that your repository is NOT affected.
```

**措施 2 — 传递发现理由**：

`confirm()` 方法新增 `discovery_evidence` 参数，把总 Manager 的 rationale 和 confidence 传给 Team Manager：
```
The Project Manager flagged your repository because:
"handles ticket reservation and has email-related commits" (confidence: 0.90)
Please verify whether this assessment is correct.
```

**措施 3 — 三层分类**：

新增 MAYBE 中间态：
- REQUIRED：有明确证据，直接进入最终列表
- MAYBE：间接相关，保留但标注低置信
- EXCLUDED：明确无关，排除

**结果**：Recall 78.3%（+27.4%），Precision 80.4%（-12.9%），F1 76.4%（+14.7%）。

**分析**：三项改进成功恢复了 Recall（从 V3 的 50.9% 回到 78.3%），同时 Precision 保持 80%+。F1 从 61% 跃升到 76.4%。

---

### V5：需求增强

**改动原因**：hard 用例的需求文本太短（平均 69 字），总 Manager 信息不足导致漏报。模拟真实用户-LLM 交互补充需求信息度。

**具体改动**：

新增 `enhance_requirements.py`：
1. `RequirementAnalyzer` 分析需求缺失维度
2. LLM 模拟 PM 追问 + 用户回答对话
3. 生成增强需求（平均从 69 字扩展到 253 字）

示例（TT-012）：
```
原始（62字）：修复用户信息修改功能的 bug。用户修改个人信息后，
认证服务没有同步更新。需要检查用户服务和认证服务之间的数据同步逻辑。

增强（187字）：修复用户信息修改功能中认证服务未同步更新的bug。
当用户（包括普通用户和管理员）修改个人信息（如手机号、邮箱、角色或权限等）后，
认证服务应立即同步更新，确保用户可以用新信息登录和操作...
```

**结果**：Recall 78.3%（持平），Precision 71.0%（-9.4%），F1 71.5%（-4.9%）。

**分析**：需求增强对 hard 用例有局部改善（TT-004 Recall +26%），但整体 F1 反而下降——增强需求给了 LLM 更多"联想空间"导致多报。

---

### V6：pom.xml 解析器修复（当前版本）

**改动原因**：调试中发现 AutoCard 的 deps 字段全部为空。排查后发现扫描器不支持 Java 项目的 pom.xml，导致全部 42 个仓库的依赖信息丢失。

**具体改动**：

`scan_remote.py` 新增 `_parse_pom_xml` 函数：
```python
def _parse_pom_xml(content: str) -> list[str]:
    """Parse a Maven pom.xml and return dependency artifact IDs."""
    import re
    deps = []
    for block in re.finditer(r"<dependency>(.*?)</dependency>", content, re.DOTALL):
        inner = block.group(1)
        m = re.search(r"<artifactId>\s*(.*?)\s*</artifactId>", inner)
        if m:
            deps.append(m.group(1).strip())
    return deps
```

修复后重新扫描全部仓库：**44/45 个仓库有 deps**（之前 0/45）。

示例：
```
ts-seat-service:           deps=[ts-common, jakarta.validation-api]
ts-preserve-service:       deps=[ts-common, spring-boot-starter-amqp, jakarta.validation-api]
ts-notification-service:   deps=[spring-boot-starter-mail, spring-boot-starter-freemarker, ts-common, ...]
```

**结果**：

| 指标 | V4（无 deps） | V6（有 deps） | 变化 |
|------|-------------|-------------|------|
| Recall | 78.3% | **90.8%** | **+12.5%** |
| Precision | 80.4% | 55.7% | -24.7% |
| F1 | 76.4% | 65.9% | -10.5% |

hard 用例大幅改善：

| 用例 | V4 Recall | V6 Recall | 变化 |
|------|-----------|-----------|------|
| TT-002（hard, cross-domain） | 46.7% | **73.3%** | +26.6% |
| TT-004（hard） | 88.0% | **94.0%** | +6.0% |

**分析**：pom.xml 修复是纯收益的 bug fix——deps 信息从无到有，让总 Manager 能基于依赖关系发现更多相关仓库。Recall 从 78.3% 跃升到 90.8%。Precision 下降是因为 deps 信息也给了 LLM 更多联想空间，但这是第一层可以接受的——精确化交给第二层。

### V7：Prompt 调优实验（已回退到 V6）

**改动原因**：V6 的确认阶段排除率只有 2%（几乎不过滤），尝试通过 prompt 调优在 V3(75%) 和 V4(2%) 之间找到中间点。

**具体改动**：

两个 prompt 全部改为中文。Team Manager 的判断标准从"默认保留"改为"基于证据判断"：
```
## 判断标准
- 仅共享 ts-common 等公共依赖不能作为 REQUIRED 的依据
- 如果你的 deps 中有和需求直接对应的依赖，倾向于 REQUIRED
- 如果你的仓库和需求描述的功能属于不同业务域，倾向于 EXCLUDED
- 如果不确定，选 MAYBE 而不是直接 EXCLUDED
```

**结果**：

| 指标 | 发现阶段 | 确认后 | 变化 |
|------|---------|--------|------|
| Recall | 80.2% | 63.7% | -16.5% |
| Precision | 54.5% | **69.0%** | +14.6% |
| 排除率 | — | **37.3%** | — |

**回退原因**：排除率 37% 偏高，Recall 损失 16.5% 太大。Team Manager 信息不足，无法准确判断"无关仓库"——它看不到调用链路，只能基于自己仓库的局部信息做判断。排除机制的精细化需要第二层图推理辅助。

## 三、关键设计决策

### Team Manager 的能力边界

通过 V3~V7 的迭代实验，得出了一个重要结论：

| Team Manager 能看到的 | Team Manager 看不到的 |
|---------------------|---------------------|
| ✅ 自己的依赖（pom.xml 中的 deps） | ❌ 谁调用了自己（反向依赖） |
| ✅ 自己的 API | ❌ 其他仓库的内部信息 |
| ✅ 自己的 commit 历史 | ❌ 仓库间的调用链路 |

**因此 Team Manager 不应该承担"判断仓库是否与需求相关"的职责。** 它的价值在于：
1. 确认涉及后，基于自己仓库的内部知识制定具体改动方案
2. 发现自己依赖了某个不在列表中的仓库时触发补充召回
3. 返回改动方案给总 Manager 做全局协调

真正的误报排除应交给第二层图推理（call_graph 确定性分析）。

### 确认阶段排除率的历史

```
V3（严格英文）:    75%  ← 太严格，Recall 暴跌
V4（宽松英文）:     1%  ← 太宽松，不起作用
V6（宽松+pom.xml）:  2%  ← 同上
V7（调优中文）:    37%  ← 终于在合理区间，但 Recall 损失太大
```

结论：靠 prompt 调优在 LLM 层面做排除，无法同时满足高 Recall 和高 Precision。需要第二层图推理的确定性分析。
