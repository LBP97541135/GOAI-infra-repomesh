## 二、各版本详细变更与结果

### V1：原始基线

**代码状态**：无后过滤，prompt 鼓励多报

**结果分析**：
- Recall 87.2%（达标），但 Precision 只有 50.5%
- 误报率 53.6%，平均每例多报 5.4 个仓库
- 被⼴频繁误报的"惯犯"：ts-order-other-service (6次)、ts-rebook-service (5次)、ts-route-service (5次)

### V2：P0 + P1（后过滤 + Prompt 收紧）

**具体改动**：

P0 — `discovery.py` 新增后过滤：
```python
# 新增常量
_MIN_CONFIDENCE = 0.7

# 在 discover() 方法末尾添加
evidence = [e for e in evidence if e.score >= _MIN_CONFIDENCE]
return evidence[:limit]
```

P1 — `discovery.py` 的 `build_discovery_prompt` 修改 system prompt：

| 修改点 | 旧 | 新 |
|--------|----|----|
| 核心措辞 | "likely to need changes" | "will need changes" |
| 低信号建议 | "if unsure, include them with confidence ≤ 0.5" | "Do NOT include these unless you have concrete evidence" |
| 新增规则 | — | "Only include repositories where you have POSITIVE EVIDENCE" |

**结果**：Recall 89.6%（+2.4%），Precision 50.1%（-0.4%），F1 61.2%（+0.7%）

**分析**：P0+P1 几乎没效果。LLM 在收紧的 prompt 下仍倾向于给大多数仓库 ≥0.7 的分数，后过滤形同虚设。根因是 AutoCard 信息粒度不够，LLM 无法仅凭 top_dirs + deps 区分功能相似的仓库。

### V3：P2 严格确认（矫枉过正）

**具体改动**：

新增 `confirmation.py`，实现 `ConfirmationService`：
- 输入：发现阶段的候选仓库列表 + 需求
- 处理：对每个候选仓库，LLM 扮演 Repository Manager 做判断
- 输出：REQUIRED（保留）或 EXCLUDED（排除）

V3 prompt 策略——**严格确认**：
```
Be strict: only say REQUIRED if you have concrete evidence.
Do NOT say REQUIRED just because the topic seems related.
If your repository handles a different concern, say EXCLUDED.
```

**结果**：Recall 暴跌至 50.9%（-38.7%），Precision 飙升至 93.3%（+43.2%），F1 61.7%（+0.5%）

**Recall 暴跌根因分析**：

| 因素 | 说明 | 占漏报比 |
|------|------|---------|
| Prompt 过于严格 | "only say REQUIRED if you have concrete evidence" → 没有明确证据就排除 | 主要 |
| AutoCard 信息不够 | Manager 看不到仓库间的调用关系。如 ts-preserve-service 调用了 ts-notification-service 这个事实不在 AutoCard 里 | 主要 |
| 缺少全局上下文 | Manager 不知道"总 Manager 选中了我"，从零开始判断 | 次要 |
| 二选一逼迫 | 只有 REQUIRED/EXCLUDED，不确定时被迫选 EXCLUDED | 次要 |

典型案例：
- TT-003：发现阶段找到 5 个 admin 服务，确认阶段**全部排除**，最终预测 0 个
- TT-001：ts-preserve-service（订票服务）被排除，因为 AutoCard 里没有"email"关键词

### V4：组合优化（放宽 + 传理由 + 三层分类）

**具体改动**：

`confirmation.py` 三项改进：

**措施 1 — 放宽确认标准**：
```
旧：Be strict: only say REQUIRED if you have concrete evidence
新：Default to REQUIRED or MAYBE unless you have CLEAR evidence
    that your repository is NOT affected.
```

**措施 2 — 传递发现理由**：
```python
# confirm() 方法新增 discovery_evidence 参数
def confirm(
    self,
    candidate_names: list[str],
    requirement: str,
    *,
    discovery_evidence: dict[str, tuple[str, float]] | None = None,
    # repo_name → (rationale, confidence)
)
```
prompt 中增加：
```
The Project Manager flagged your repository because:
"handles ticket reservation and has email-related commits" (confidence: 0.90)
Please verify whether this assessment is correct.
```

**措施 3 — 三层分类**：
```python
@dataclass(frozen=True, slots=True)
class ConfirmationSummary:
    required: list[ConfirmationResult]   # REQUIRED
    maybe: list[ConfirmationResult]      # MAYBE（新增中间态）
    excluded: list[ConfirmationResult]   # EXCLUDED

    @property
    def final_repos(self) -> list[str]:
        # REQUIRED + MAYBE 都保留
        return [r.repository for r in self.required] + [
            r.repository for r in self.maybe]
```

**结果**：Recall 78.3%（+27.4%），Precision 80.4%（-12.9%），F1 76.4%（+14.7%）

**效果**：三项改进成功恢复了 Recall（从 V3 的 50.9% 回到 78.3%），同时 Precision 仍保持在 80%+。F1 从 61% 跃升到 76.4%。

### V5：需求增强

**具体改动**：

新增 `enhance_requirements.py`，模拟 PM-用户交互：
1. `RequirementAnalyzer` 分析需求缺失维度
2. LLM 模拟 PM 追问 + 用户回答对话
3. 生成增强需求（平均从 69 字扩展到 253 字）

示例（TT-012）：
```
原始（62字）：修复用户信息修改功能的 bug。用户修改个人信息后，
认证服务没有同步更新。需要检查用户服务和认证服务之间的数据同步逻辑。

增强（187字）：修复用户信息修改功能中认证服务未同步更新的bug。
当用户（包括普通用户和管理员）修改个人信息（如手机号、邮箱、角色或权限等）后，
认证服务应立即同步更新，确保用户可以用新信息登录和操作...
```

**结果**：Recall 78.3%（持平），Precision 71.0%（-9.4%），F1 71.5%（-4.9%）

**分析**：需求增强对 hard 用例有局部改善（TT-004 Recall +26%），但整体 F1 反而下降——增强需求给了 LLM 更多"联想空间"导致多报。

### 漏报来源

| 来源 | 数量 | 占比 |

| 发现阶段漏报 | 34 | **100%** |
| 确认阶段误排 | 0 | **0%** |

### 误报来源

| 来源 | 数量 | 占比 |
|------|------|------|
| REQUIRED 误报 | 14 | 67% |

### 候选数变化

```
平均发现: 5.3 个 → 平均最终: 5.2 个
```

### 当前状态诊断

| 环节 | 状态 | 问题 |
|------|------|------|
| 发现阶段 | 正常 | 漏报全部来自这里（AutoCard 粒度限制） |
| 确认阶段 | 几乎无效 | 排除率 1%，V4 prompt 太宽松 |
| 整体 | 可用 | F1=76.4%，但不平衡（确认阶段没发挥作用） |
