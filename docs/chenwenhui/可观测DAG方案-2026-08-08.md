# 可观测 DAG 方案：计划快照持久化与可视化查询

> 创建时间：2026-08-08
> 模块：repository_intelligence
> 状态：方案设计（经两轮第一性原理对抗性审查）

---

## 一、问题定义

图推理引擎（DependencyGraphService）已经在 confirmation 和 integration 阶段提供确定性拓扑排序。但产出的 DAG 只存在于内存中——integrate() 返回 IntegratedPlan 后，如果调用方不保存它，图的结构就丢了。

需要回答三个问题：
1. **DAG 快照应该存什么？** 是存完整结构还是只存引用？
2. **存哪里？** PostgreSQL JSONB 还是图数据库？
3. **怎么查？** 需要什么 API 端点，前端怎么渲染？

---

## 二、第一遍对抗性审查：从第一性原理出发

### 原理零：DAG 快照的本质是什么？

DAG 快照不是一个实时变化的"活图"——它是一次规划产出的**不可变记录**。每次 PlanIntegrationService.integrate() 产出一份 IntegratedPlan，就是一个时间点的完整计划状态。

快照的核心价值：
- **可观测**：人类看到"这次规划产出了什么结构，谁先执行谁后执行"
- **可审计**：事后回溯"为什么是这个执行顺序"
- **可对比**：重规划后对比"v1 和 v2 有什么变化"
- **可关联**：把 DAG 节点和下游 ExecutionPlan、Task、Runner 事件关联起来

### 原理一：存完整结构还是只存引用？

**质疑**：ExecutionPlan 表已经存了 batches（JSONB），为什么还要再存一份？

**审查结论**：两者职责不同，不能合并。

| 维度 | ExecutionPlan（task_orchestration） | PlanSnapshot（repository_intelligence） |
|------|-------------------------------------|----------------------------------------|
| 关注点 | 执行状态——批次推进、任务完成 | 规划结构——为什么这么排、依赖图长什么样 |
| 数据 | batches（仓库ID列表 + task 信息） | nodes + edges + contracts + engineering_spec |
| 生命周期 | 随执行推进不断更新（current_batch_index 变化） | 不可变，一次规划一份快照 |
| 消费者 | AdvanceExecutionPlan（推进逻辑） | 人类 / 可视化前端 / 审计日志 |

ExecutionPlan 存的是"执行什么"，PlanSnapshot 存的是"为什么这么执行"。合并会导致执行层和规划层耦合。

**但需要建立关联**——PlanSnapshot 记录关联的 execution_plan_id，方便从 DAG 节点跳到执行状态。

### 原理二：PostgreSQL JSONB 够不够？

**质疑**：DAG 是图结构，用关系型数据库的 JSONB 存会不会查询能力不足？

**审查结论**：当前规模下够用。理由：

1. **节点量小**：当前 catalog 里 10-50 个仓库，一次规划的 DAG 节点 3-15 个。JSONB 读一个快照是一次行读取，没有性能问题。

2. **查询模式简单**：
   - "按 project_id 查最新快照" → `WHERE project_id = ? ORDER BY plan_version DESC LIMIT 1`
   - "查所有版本" → `WHERE project_id = ? ORDER BY plan_version`
   - "查某个状态的快照" → `WHERE project_id = ? AND status = ?`
   
   这些都是标准 SQL 查询，JSONB 内容只在应用层反序列化，不在 SQL 层做图遍历。

3. **不需要递归图遍历**：当前不需要"找出所有间接依赖 A 的仓库（多层递归）"这种查询。DependencyGraphService 在内存里做图遍历已经足够快。持久化是为了可观测和审计，不是为了图查询。

4. **引入图数据库的代价**：Neo4j 需要独立部署运维，需要学 Cypher 查询语言，需要处理跨库事务一致性。对于一个 10 节点级别的 DAG，投入产出比不合理。

**什么时候需要图数据库**：catalog 规模到 1000+ 仓库，且需要"找出所有间接依赖链路"这种多层递归查询。当前远未达到。

### 原理三：快照的不可变性

**质疑**：如果重规划了，旧快照怎么办？

**审查结论**：快照不可变。重规划产出新快照（version + 1），旧快照标记 `SUPERSEDED` 但不修改内容。这与 DAG 动态更新方案（中心化编排 + 版本号）完全一致。

快照状态转换：

```
CREATED → IN_PROGRESS → COMPLETED
                     ↘ FAILED
CREATED → SUPERSEDED（被新版本替代）
```

## 三、第二遍对抗性审查：实现边界与交互

### 质疑一：PlanSnapshot 存储应该放在哪个模块？

**选项 A**：repository_intelligence 模块（和 PlanIntegrationService 同模块）
**选项 B**：task_orchestration 模块（和 ExecutionPlan 同模块）
**选项 C**：新建 observability 模块

**审查结论**：选项 A。理由：

1. PlanSnapshot 是规划产出，归 repository_intelligence 管
2. 存储模式和同模块的 RepositoryRecord 一致（同 schema、同 Database 封装）
3. 不新建模块——避免过度拆分，一个表+一个 Store 够了

### 质疑二：快照什么时候写入？

**质疑**：在 integrate() 内部写，还是在 materialize() 时写？

**选项 A**：integrate() 返回前写入
- 优点：快照和规划严格绑定，即使 materialize 失败也有记录
- 缺点：integrate() 变成有副作用的（原来纯计算）

**选项 B**：materialize() 成功后写入
- 优点：只记录真正执行的规划
- 缺点：如果 materialize 失败，丢失规划记录

**审查结论**：选项 A，但通过 Store Protocol 解耦。integrate() 不直接写数据库——它返回 IntegratedPlan（已有行为不变），由调用方（router 或 bridge）决定是否持久化快照。这保持 integrate() 的纯计算语义。

实际写入点：在 PlanExecutionBridge.materialize() 成功创建 spec 和 execution plan 后，写入 PlanSnapshot。这样：
- 快照和执行记录在同一个事务上下文（可观测关联）
- integrate() 保持纯计算
- materialize 失败时不产生快照（合理——没执行的规划不值得存）

### 质疑三：快照的状态怎么更新？

PlanSnapshot 的 status 需要随 ExecutionPlan 的推进更新（CREATED → IN_PROGRESS → COMPLETED）。

**质疑**：谁来更新？如果由 AdvanceExecutionPlan 更新，task_orchestration 就要反向写 repository_intelligence 的表——跨模块写。

**审查结论**：不跨模块写。PlanSnapshot 的 status 更新通过**事件订阅**或**查询时关联**实现：

**方案一（推荐 MVP）**：查询时关联。API 端点在返回快照时，关联查询 ExecutionPlan 的 status，临时拼装。PlanSnapshot 本身只存规划时的静态结构，status 字段是可选的缓存。

**方案二（后续）**：事件驱动。ExecutionPlan 状态变更发出领域事件，repository_intelligence 订阅并更新快照 status。但这引入事件基础设施，MVP 不需要。

### 质疑四：IntegratedPlan.to_dict() 已经有了，为什么还需要专门的存储？

**质疑**：IntegratedPlan.to_dict() 返回 JSON，直接存 JSONB 不就行了？

**审查结论**：to_dict() 是序列化工具，不是持久化方案。需要存储层的理由：

1. **多版本管理**：需要按 project_id + plan_version 查询，纯 JSON 文件做不到
2. **状态关联**：需要关联 execution_plan_id，跟踪执行进度
3. **审计需求**：需要 created_at、created_by_agent_id 等元数据
4. **一致性**：和其他数据在同一 PostgreSQL 实例，ACID 事务保证

### 质疑五：graph edges 要不要单独存一张表？

**质疑**：edges 是图的核心结构，存 JSONB 会不会丧失查询能力？

**审查结论**：当前不需要单独表。理由：

1. edges 的查询场景是"展示某个快照的依赖图"——取出来全部展示，不做条件过滤
2. 如果未来需要"统计哪个仓库被依赖最多"这种聚合查询，可以从 JSONB 用 PostgreSQL 的 JSON 函数提取
3. 单独表增加 JOIN 复杂度，当前规模不值得

## 四、数据模型

### 4.1 表结构

```sql
-- schema: repository_intelligence
CREATE TABLE plan_snapshots (
    id                  UUID PRIMARY KEY,
    project_id          UUID NOT NULL,
    plan_version        INTEGER NOT NULL,
    created_at          TIMESTAMPTZ DEFAULT now(),
    created_by_agent_id UUID,
    
    -- 完整 DAG 结构（不可变）
    engineering_spec    TEXT NOT NULL,
    contracts           JSONB NOT NULL,    -- ContractSpec 列表
    task_dag            JSONB NOT NULL,    -- TaskNode 列表
    execution_batches   JSONB NOT NULL,    -- [["repo-a"], ["repo-b", "repo-c"]]
    graph_edges         JSONB NOT NULL DEFAULT '[]',  -- GraphEdge 列表（图推理产出）
    
    -- 执行关联（可选，materialize 后回填）
    execution_plan_id   UUID,              -- 关联 task_orchestration.execution_plans.id
    
    -- 元数据
    requirement_text    TEXT,              -- 原始需求文本（审计用）
    integration_method  VARCHAR(20),       -- "graph" | "llm_only"
    
    UNIQUE(project_id, plan_version)
);
```

### 4.2 索引

```sql
CREATE INDEX ix_plan_snapshots_project_id ON repository_intelligence.plan_snapshots(project_id);
CREATE INDEX ix_plan_snapshots_project_version ON repository_intelligence.plan_snapshots(project_id, plan_version DESC);
```

### 4.3 SQLAlchemy Model

```python
class PlanSnapshotRecord(Base):
```

## 五、存储层与 API

### 5.1 PlanSnapshotStore

```python
class PlanSnapshotStore:
    """PostgreSQL-backed store for immutable plan snapshots."""

    def __init__(self, database: Database) -> None:
        self._database = database

    async def save(self, snapshot: PlanSnapshotRecord) -> None:
        """Insert a new snapshot. Raises on (project_id, plan_version) conflict."""

    async def get_latest(self, project_id: UUID) -> PlanSnapshotRecord | None:
        """Get the highest-version snapshot for a project."""

    async def get_by_version(
        self, project_id: UUID, plan_version: int
    ) -> PlanSnapshotRecord | None:
        """Get a specific version."""

    async def list_all(self, project_id: UUID) -> list[PlanSnapshotRecord]:
        """List all snapshots for a project, ordered by version."""

    async def link_execution_plan(
        self, snapshot_id: UUID, execution_plan_id: UUID
    ) -> None:
        """Back-fill the execution_plan_id after materialize succeeds."""
```

### 5.2 写入时机

```
PlanExecutionBridge.materialize()
  ├── 创建 Engineering Spec
  ├── 创建 Contract Specs
  ├── 启动 ExecutionPlan（batches）
  ├── 写入 PlanSnapshot（关联 execution_plan_id）  ← 新增
  └── 返回 MaterializationResult
```

快照写入在 execution plan 启动成功之后——确保只有真正进入执行的规划才被记录。

### 5.3 API 端点

```
GET /api/v1/plans/{project_id}/latest
  → 最新 DAG 快照（nodes + edges + batches + contracts + spec）
  → 关联查询 execution_plan 的实时状态

GET /api/v1/plans/{project_id}/versions
  → 所有版本列表（简略：version + created_at + integration_method）

GET /api/v1/plans/{project_id}/versions/{version}
  → 指定版本的完整快照

GET /api/v1/dependency-graph
  → 当前 catalog 的依赖图（DependencyGraphService 的查询结果）
```

### 5.4 返回格式

`GET /api/v1/plans/{project_id}/latest` 返回：

## 六、前端可视化建议

### 6.1 渲染库选择

| 库 | 特点 | 适合度 |
|------|------|--------|
| **Cytoscape.js** | 专业图可视化，DAG 布局算法丰富，支持交互 | 推荐——DAG 场景最佳 |
| vis-network | 简单易用，物理引擎模拟 | 备选——简单场景够用 |
| D3.js | 最灵活但代码量大 | 过度——不需要自定义到这个程度 |
| React Flow | React 生态，节点可自定义 | 如果前端用 React 可选 |

### 6.2 DAG 渲染建议

- **分层布局**（hierarchical / dagre）：按 execution_batches 分层，Batch 1 在最上面
- **节点状态着色**：已完成绿色、进行中蓝色、待执行灰色
- **边置信度样式**：confirmed 实线、possible 虚线
- **批次分隔线**：用背景色带区分不同 batch

跨模块关系只有一个：PlanSnapshot.execution_plan_id → ExecutionPlan.id。这是只读引用（repository_intelligence 读 task_orchestration 的 plan status），不产生跨模块写。

## 九、对抗性审查总结

### 确认成立的判断

1. **PostgreSQL JSONB 够用**——10-50 节点级别，查询模式简单
2. **快照不可变**——重规划产出新版本，旧版本标记 SUPERSEDED
3. **PlanSnapshot 和 ExecutionPlan 职责分离**——规划结构 vs 执行状态
4. **写入时机在 materialize 成功后**——只记录真正执行的规划
5. **不跨模块写**——通过 execution_plan_id 只读关联

### 审查中修正的问题

| 问题 | 修正 |
|------|------|
| integrate() 有副作用？ | integrate() 保持纯计算，写入由 materialize 负责 |
| status 怎么更新？ | MVP 用查询时关联，不跨模块写 |
| edges 要不要单独表？ | 不需要，JSONB 够用 |
| 图数据库？ | 不需要，当前规模 PostgreSQL 远超够用 |
