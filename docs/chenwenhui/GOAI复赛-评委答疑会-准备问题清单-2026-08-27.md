## 一、优化方向一：多 Agent 协同 —— 逐条分析

### 1.1 全新环境冷启动 + 多项目多 Team

**评委原意**：证明系统能在全新环境里跑通多项目、多 Team 的冷启动和完整运行，减少对预置环境/人工调整的依赖。

**现状证据**：
- AgentTeams 是 K8s 原生：CRD（teams/managers/workers/humans）+ helm chart + controller 自动部署容器、沙箱、Matrix 通道、凭据注入；有 auto-sleep 生命周期管理。
- RepoMesh 有层级编排：Org Leader → Repository Leader → Worker，任务分配/上报沿 Leader 链幂等传递。
- 部署有一键脚本（hack/local-k8s-up.sh、helm）。

**真实差距**：没有"从一台空机器 → 起集群 → 建多 Team → 并行交付"的完整录屏/日志证据链；多项目并行时的资源调度（哪个 Team 用哪个 Worker）未见实现。

**可展示的已有能力**：helm 冷启动、CRD 声明式建 Team、任务层级链、幂等恢复。

**可问评委**：
- Q1-1：冷启动的证据形式，评委期待哪种——答辩现场 live demo（全新集群拉起+多 Team 并行），还是提交完整录屏+可复现脚本即可？现场时间是否有硬限制？
- Q1-2：多 Team 并行，评委关注的是"多个 Team 同时干活"（资源维度）还是"一个需求跨多个 Team 协作"（协作维度）？两者证明难度差一个量级。

### 1.2 动态加任务 / 仓库冲突 / Worker 故障重派 / 人工审批恢复

**评委原意**：展示 AgentTeams 根据上下文灵活调整协作关系：任务中途追加、多仓并发冲突、Worker 挂了自动重派、人工审批后恢复执行。

**现状证据**：
- 动态任务：task 状态机 + 乐观锁（`optimistic task version` 拒绝并发覆盖）——有。
- 仓库冲突：PostgreSQL 乐观锁 + delivery ChangeSet 幂等对账——有雏形。
- 故障重派：delivery README 说 "Runner failure without a confirmed native session creates a fresh retry action"；但 **task 层 lease（领取锁）/ 并行调度 / 重试策略 README 原文承认未实现**。
- 审批恢复：discovery_chain 有 approval gate（"approval is not advisory"）；console 有人工审批——有。

**真实差距**：每个场景都有"点"，但没有一个"故障→自动重派→恢复→继续交付"的端到端演示；Worker 崩溃的检测与重派主要依赖 AgentTeams controller（pod 级），任务级重派策略是空白。

**可问评委**：
- Q1-3：Worker 故障重派，评委期待的是 **Pod/容器级**（k8s controller 拉起新 worker）还是**任务级**（任务重新排队给其他 worker）？两者在 RepoMesh 里分别由 AgentTeams controller 和 RepoMesh task 层负责，后者目前是空白，直接影响我们要不要补 task-lease。
- Q1-4："多个仓库发生冲突"具体指什么冲突——同文件 Git 冲突、还是对同一服务的并发变更、还是两个 Worker 抢同一个任务？评委有无参考场景？
- Q1-5：审批恢复，评委希望看到"审批通过后**自动**继续执行"，还是"审批后**人工触发**继续"即可？恢复的自动化程度要求多高？

### 1.3 Skill Registry 从设计走向实际运行

**评委原意**：版本发布、评测、灰度、晋级失败、回滚，全生命周期要真跑起来。

**现状**：RepoMesh 侧无 Skill Registry；AgentTeams 有 remote skills 分发（STS 资源、`skill/alpha` 命名空间），但无版本/评测/灰度/回滚机制。这是三方向里 RepoMesh 最空白的一项。

**可问评委**（这是全场最值得问透的一块）：
- Q1-6：评委是否要求我们**自建**一套 Skill Registry 平台（含版本管理/灰度/回滚 UI），还是**复用现有机制证明"发布-回滚"闭环**即可（例如：skill 以 Git 仓库管理 → tag 即版本 → 按环境标签灰度 → 失败回退到上一 tag）？工程完备度 vs 机制演示，哪个权重更高？
- Q1-7："评测"环节，评委期待用什么标准评测 skill——离线数据集回测、线上 A/B、还是人工验收清单？有没有推荐的做法？
- Q1-8：灰度失败后的"晋级失败"和"回滚"，评委想看到的是 skill 版本回退不影响在跑任务，还是只要求演示回滚动作本身？

### 1.4 工程体系：Trace/Log/Metrics + 权限/超时/重试/降级/告警/SLO/容量/升级兼容/灾备

**评委原意**：工程上打通可观测三支柱，并补齐全套运维设计。

**现状**（比材料里展示的多，值得在复赛里重讲）：
- observability 模块：trace_ingest（OTel span 持久化）、log_recorder、usage_recorder（模型/tool 用量+成本）、alerting（窗口阈值规则：成功率<0.8 / 错误数>10 / P95 延迟，firing→resolved 生命周期）。
- 权限：ExecuteAuthorizedCodingRun + ExecutionContextGrant（过期/未授权工具/拒绝路径）。
- 重试：扫描层 get_with_retry（429/403 限流退避）。
- 空白：SLO 定义、容量规划、升级兼容（migration 策略）、灾备（备份/恢复）、降级（模型服务不可用时怎么办）。

**可问评委**：
- Q1-9：工程体系这么长一串（权限/超时/重试/降级/告警/SLO/容量/升级/灾备），评委期待**全部有设计文档**，还是**至少 2–3 项有真实实现+演示**？这决定我们时间分配。
- Q1-10：评委对"降级"的具体期待是什么——模型 API 故障时的降级（如 fallback 模型/离线队列）还是组件降级（可观测挂了不影响主流程）？

## 二、优化方向二：数据库 —— 逐条分析

### 2.1 控制面强化：并发领取 + 外部结果对账

**评委原意**：用数据库事务和约束保证"同一命令只被一个执行器有效处理"，结合幂等与对账避免重复合并/发布/状态不一致。

**现状**：
- PostgreSQL 已是控制面（计划/任务/审批/验证/审计）。
- 有乐观锁（task version 防并发覆盖）、幂等注册、delivery ChangeSet 周期对账（reconcile 失败自动重试）。
- **缺口**：SCM 命令/任务的"并发领取"没有数据库级锁——README 原文："Dependency-graph readiness, **leases**, parallel scheduling and **retry policy** remain the next layer"。

**可问评委**：
- Q2-1：评委建议的"同一命令只被一个执行器处理"，是否有偏好的实现路径——`SELECT … FOR UPDATE SKIP LOCKED` 抢占式领取、唯一约束（命令 id）原子插入、还是乐观版本号即可？评委是希望我们用**数据库原生机制**（如 SKIP LOCKED）还是应用层锁也接受？
- Q2-2："外部执行结果对账"目前我们有 delivery 周期 reconcile（拉取 ChangeSet 状态对比）。评委期待的对账粒度是**命令级**（每条 SCM 命令）还是**交付单元级**（ChangeSet/PR）？频次要求（秒级/分钟级）？
- Q2-3：评委提到"避免重复发布"——目前我们没有"发布"动作（只到 commit/PR 为止）。复赛是否需要把链路延伸到**真正的发布/部署**（比如触发 CI/CD 或部署清单变更）？还是交付到 PR/MR 即算完成？

### 2.2 PolarDB RAG 引擎 → 企业研发知识底座

**评委原意**：把企业代码、接口、Schema、研发规范、历史交付经验作为 Agent 可信上下文，减少幻觉；验证过的成功/失败案例直接服务相似需求。

**现状**：
- RepoMesh **无 RAG/向量检索**。
- 但扫描链路已采集的结构化数据就是现成的知识原料：dep_evidence（依赖关系）、identities（服务身份）、exposed_apis（接口路由）、deploy_identities（部署拓扑）、AutoCard（仓库事实卡）。还有 plan_snapshot（历史计划）与 delivery 记录（历史交付）可作为"历史经验"语料。
- 控制面数据（PostgreSQL）与知识底座天然同源。

**可问评委**：
- Q2-4：PolarDB RAG 引擎在复赛阶段如何获取——比赛是否提供云账号/免费额度？还是我们可用**开源自建对标实现**（pgvector / 其他向量库）证明"知识底座"机制即可，不影响评分？
- Q2-5：评委期待的 RAG 应用场景，优先级最高的是哪个——Planner 需求分析时的**跨仓影响范围判断**、Worker 修改时的**接口/Schema 依据检索**、还是**历史案例复用**（相似需求直接引用成功/失败经验）？我们想聚焦一个做到位。
- Q2-6：知识底座的数据来源，评委认为应优先接入哪类——仓库代码/接口（扫描产物）、研发规范文档、还是历史交付记录？

### 2.3 Polar Agentic Database Branch：数据库变更的隔离验证

**评委原意**：为数据库任务创建相互隔离、可并行试验的数据环境，验证 migration/回填/查询语义对**真实业务数据**的影响；空库测试发现不了的历史数据、约束冲突、新旧版本兼容问题要能在分支里暴露。交付物 = 代码 + 数据库变更 + 验证结果。

**现状**：RepoMesh 无任何数据库变更验证能力；验证机制停留在"跑 test_commands"（应用层测试）。

**可问评委**：
- Q2-7：Agentic DB Branch 的演示环境比赛是否提供？若自备，我们用 **PolarDB PostgreSQL 内核兼容的 PostgreSQL**（如云上 Pg 或本地实例）演示"branch 隔离 + 迁移回放 + 数据校验"机制，评委是否接受？
- Q2-8：Branch 中的"验证结果"作为交付物，评委期待的形态是什么——迁移回放日志 + 数据校验报告（如行数/约束/新旧值对比）、自动化测试通过、还是两者都要？
- Q2-9：这个闭环（建分支→跑 migration→验证→合并回主库）是否需要**端到端自动化**（Agent 全自动完成），还是 Agent 生成变更方案 + 人工确认关键步骤即可？数据库变更的生产安全红线，评委希望 RepoMesh 怎么处理（人工审批 gate）？
- Q2-10：评委说的"一次交付成功率"，有没有期望的度量方式——比如复赛现场用一组带历史数据/约束冲突的题目，看 RepoMesh 首次交付是否通过？

## 三、优化方向三：可观测 —— 逐条分析

### 3.1 OTel Trace 上报 AgentLoop + 监控告警实践

**评委原意**：把 OTel Trace 上报到 AgentLoop，用其数据加工/存储/可视化/告警能力，并给出 Token 异动、TTFT 耗时、Tool 调用错误的监控告警**实践**（不是架构图，是真实案例）。

**现状**：
- RepoMesh 已有 OTel 埋点（setup_tracing，otlp_endpoint 可配置）+ 自建 trace_ingest/alerting。
- alerting 已支持 estimated_cost / latency_p95 / success_rate / error_count 阈值规则。
- 无 TTFT 指标、无"异动检测"（相对基线漂移）实践、未接 AgentLoop。

**可问评委**：
- Q3-1：AgentLoop 接入方式——是否接受**标准 OTLP endpoint** 直报（我们改一个配置即可），还是必须用阿里云专有 SDK/协议？比赛账号如何开通 AgentLoop？（这是技术路径问题，直接影响改动量）
- Q3-2：评委点名的三类实践（Token 异动、TTFT 长、Tool 调用错误），希望我们提供"真实抓到的异常 + 告警 + 定位分析"的完整案例。RepoMesh 自建 observability 已有近似能力（成本/延迟/成功率告警），是否可以**同时展示自建告警 + AgentLoop 云端告警**双轨？还是评委更希望我们完全迁移到 AgentLoop？
- Q3-3：AgentLoop 的告警能否接入钉钉/飞书通知？我们已有 Matrix 通道，是否建议打通到 IM 告警？

### 3.2 评测与数据集回测、数据飞轮

**评委原意**：用 AgentLoop 建"观测→评估→数据集→优化实验回测"飞轮；科学度量任务完成度、执行效率。

**现状**：
- 已有验证集种子：TrainTicket 验证集（TT-001 多次 pipeline 运行记录）、备用数据集（Cerny-Zenodo）、仓库发现验证集。
- 无系统化评估框架（任务完成度/效率指标未定义）、无数据集版本管理、无回测流程。

**可问评委**：
- Q3-4：AgentLoop 的"Agent-as-a-Judge"评测，是否支持**导入我们自己的数据集**（如 TrainTicket 验证集）批量回测？评估维度（任务完成度、执行效率、工具使用正确性）能否导出结构化指标，用于复赛展示前后对比？
- Q3-5：评委期待"数据飞轮"的证据是什么——一个"发现问题→修→数据集回测→指标提升"的闭环案例？还是飞轮架构+一轮完整循环即可？

### 3.3 紧扣"解决什么痛点"

**评委原意**：观测评估是手段不是目的；要讲清楚 Agent 选题遇到什么真实的可靠性/成本/质量问题，观测评估如何解决它。

**现状**：RepoMesh 有真实痛点素材（TT-001 三次运行失败记录、图推理修复、token 上下文爆炸问题），但材料里没讲成"痛点→观测→解决"的故事线。

**可问评委**（这个最重要）：
- Q3-6：评委认为 RepoMesh 最应该证明解决的真实痛点，是哪一个——**多仓交付不可控**（拓扑盲猜、执行乱序）、**Agent 可靠性/稳定性**（失败重派、超时重试）、还是**成本**（token 上下文爆炸）？我们好把观测评估对准这个痛点讲。
- Q3-7：答辩时"痛点"讲法，评委更接受"过程故事"（我们观测到 X → 定位到 Y → 修好 Z，带真实数据）还是"结论故事"（系统具备 A/B/C 能力，用指标证明）？

## 附：产品背景速查（答疑会沟通用）

- **AgentLoop**：阿里云 Agent 观测与优化平台。基于 OTel 采集；内置数据加工/存储/可视化/告警；"Agent-as-a-Judge"评估（评估器本身是 Agent，基于 Trajectory 轨迹评估）；支持模型调用（token、延迟）、工具调用（参数/返回/耗时/状态）、异常行为检测。
- **PolarDB RAG 引擎**：PolarDB for PostgreSQL 内置向量引擎（pgvector 升级版，标量+向量+全文一体），支撑企业知识库/Agent 记忆/语义检索；PolarSearch 记忆容器可做长短期记忆。
- **Polar Agentic Database Branch**：数据库分支能力（API：CreateAgenticDBBranch；相关产品线 Polar Lakebase）——基于 WAL Timeline + Copy-on-Write 的秒级分支（约 3.6s 建分支），元数据级隔离、万级并发分支，与 PolarDB 同内核兼容；用于 Agent 在隔离数据环境验证 schema/migration/回填，不碰生产数据。
