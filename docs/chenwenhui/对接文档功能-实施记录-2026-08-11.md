## 一、需求背景

基于单仓库的调整方案，生成一份**对接文档**，交给各仓库负责人**人工确认**是否允许该修改进入：

1. **正常流程**：Leader 制定方案 → 集成出 IntegratedPlan → 物化（materialize）时，为计划中每个仓库生成一份对接文档 → 仓库负责人审阅 → 批准 / 拒绝。
2. **异常流程**：Team Manager 上报异常回 Leader → Leader 制定新方案（replan）→ **涉及的相关仓库**需要生成新版本对接文档，旧文档标记为 SUPERSEDED（被替代），防止旧批准被误当作新方案的批准。

对应对话中的原话：

> "加一个功能：那就是基于单仓库的调整方案，做一个生成对接文档的功能，用来各仓库人员人工确认是否允许此修改，在出现异常team manager上报回leader，leader制定出新方案的时候，涉及的相关仓库也需要生成文档"

---

## 二、设计决策（第一性原理）

### 1. 一份文档 = 一个仓库 × 一个计划版本

| 维度 | 决策 | 理由 |
|------|------|------|
| 粒度 | 每仓库一份 | 确认人是"各仓库人员"，粒度必须对齐仓库所有权 |
| 版本 | 绑定 plan_version | replan 出新版本后，旧文档必须失效，不能复用 |
| 状态 | PENDING → APPROVED / REJECTED；被替代时 SUPERSEDED | 人工确认是单向动作；替代是版本演进动作 |
| 内容 | 调整方案 + 生产/消费契约 + 批次 | 仓库负责人需要看到"改我什么、我依赖谁、谁依赖我" |

### 2. 为什么单独建表而不是挂在 plan_snapshot 里

plan_snapshot 是规划层的**不可变观测记录**（nodes/edges/contracts）；handoff_docs 是**可变的人工决策记录**（状态会从 PENDING 变 APPROVED）。两者生命周期不同：

```
plan_snapshots: 一次规划一份，不可变，随版本追加
handoff_docs:   一仓库一份，可变状态，随决策/替代流转
```

### 3. SUPERSEDED 的语义

replan 时对受影响仓库：

```
旧文档(PENDING/APPROVED/REJECTED) --supersede_for_repos--> SUPERSEDED(记录 superseded_by_version)
新文档(PENDING)  ← generate_for_plan(新 plan_version)
```

关键点：
- **APPROVED 的旧文档也被标记 SUPERSEDED**——新方案必须重新走人工确认，历史批准不自动迁移。
- `supersede_for_repos` 不触碰 `plan_version == 新版本` 的文档（幂等，防止同版本重复生成时误伤）。

### 4. 存储可移植性

用 `session.merge`（按主键 upsert）而不是 `ON CONFLICT DO UPDATE`——因为测试跑 SQLite、生产跑 PostgreSQL，merge 跨方言可移植。

## 四、领域模型

### HandoffDoc

```python
@dataclass(frozen=True, slots=True)
class HandoffDoc:
    id: UUID
    project_id: UUID
    plan_version: int
    repository: str
    status: HandoffDocStatus      # PENDING / APPROVED / REJECTED / SUPERSEDED
    content: dict[str, Any]
    created_at: datetime
    created_by_agent_id: UUID | None = None   # Leader
    decided_by_agent_id: UUID | None = None   # 仓库负责人
    decision_reason: str = ""
    superseded_by_version: int | None = None
```

### content 结构（build_doc_content）

```jsonc
{
  "repository": "ts-payment-service",
  "plan_version": 1,
  "requirement": "make payments retryable",
  "engineering_spec": "Unify the payment retry pipeline...",
  "adjustment": {
    "instruction": "add the retry endpoint",      // 来自 TaskNode
    "depends_on": ["ts-notification-service"],
    "parallelizable_with": [],
    "execution_batch": 2,                          // 来自 execution_batches
    // ——以下字段来自确认阶段的 per-repository 调整方案（可选）——
    "summary": "add the retry call with an idempotency key",
    "changed_apis": ["POST /payments/retry"],
    "changed_modules": ["payments"],
    "risk": "high"
  },
  "interfaces": {
    "produced": [{"interface": "POST /payments/retry", "consumer": "ts-order-service", "agreement": "..."}],
    "consumed": [{"interface": "POST /notifications/send", "producer": "ts-notification-service", "agreement": "..."}]
  },
  "related_repositories": ["ts-notification-service", "ts-order-service"]
}
```

这就是文档的核心——**单仓库视角的调整方案 + 它生产/消费的接口**，仓库负责人据此判断"是否允许此修改"。

## 五、Service 行为

### generate_for_plan（两条路径）

```
materialize 路径: repositories=None  → 计划内每个仓库各生成一份 PENDING 文档
replan 路径:     repositories=[受影响仓库] → 先 supersede 旧文档，再为受影响仓库生成 PENDING 文档
```

### decide

只允许 PENDING 文档被决策；已决策（APPROVED/REJECTED）或被替代（SUPERSEDED）的文档抛 `HandoffDocError`。

## 六、PlanExecutionBridge 集成

### materialize（新增 Step 5b，保存计划快照之后）

```python
docs = await handoff_docs.generate_for_plan(
    project_id=project_id,
    plan_version=plan_version or 1,
    plan=plan, requirement=requirement,
    created_by_agent_id=leader_agent_id,
    details=repo_details,          # 来自 /integration 的确认结果（changed_apis/changed_modules/risk）
)
result.handoff_doc_ids = [doc.id for doc in docs]
```

`handoff_docs` 未注入时静默跳过（保持 bridge 向后兼容，不破坏既有测试/调用方）。

### replan（新增 Step 3c）

```
new_plan is None（只失效，不重规划）:
    supersede_for_repos(project_id, affected_repos, superseded_by_version=new_plan_version)

new_plan 存在（Leader 制定出新方案）:
    generate_for_plan(plan_version=new_plan_version, plan=new_plan,
                      repositories=affected_repos,
                      details=_handoff_details_from_summary(confirmation_summary, affected_repos))
```

`_handoff_details_from_summary` 从 `ConfirmationSummary` 的 required/maybe 里提取每仓库的 `summary / changed_apis / changed_modules / risk`，只保留受影响仓库——**新方案的文档自动带上 Team Manager 上报后的最新调整细节**。

## 七、API 端点

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/handoff-docs?project_id=&plan_version=&repository=&status=` | 列表（可筛选） |
| GET | `/handoff-docs/{doc_id}` | 单个文档（JSON） |
| GET | `/handoff-docs/{doc_id}/markdown` | 单个文档（Markdown，`text/plain`，直接给人看/发给仓库负责人） |
| POST | `/handoff-docs/{doc_id}/decision` | 提交人工决策 `{approved, decided_by_agent_id, reason}` |

请求模型配套增强：
- `MaterializeRequest.repo_details: dict[str, RepositoryPlanView]` —— 把确认阶段的每仓库调整方案透传给文档生成。
- `ReplanRequest.confirmation: ConfirmationSummaryView | None` —— **提供时**：Leader 本地重集成受影响仓库 → 新计划 + 重生成文档；**省略时**：仅让旧任务作废 + 旧文档 SUPERSEDED。

## 八、测试

`tests/test_handoff_docs.py`，13 个测试全部通过，覆盖：

1. **内容构建**：角色（producer/consumer）拆分、批次索引、确认细节合并
2. **Markdown 渲染**：含"人工确认"区块、状态文本、接口列表
3. **服务生命周期**：每仓库一份 PENDING → 决策 APPROVED/REJECTED → 已决策/已替代不可再决策 → 范围重生成时 supersede
4. **Postgres 存储往返**（SQLite 测试库）：upsert、筛选、批量 supersede
5. **Bridge 集成**：materialize 生成文档 / replan 为受影响仓库重生成 / replan（无新方案）仅 supersede

### 调试中解决的问题

| 问题 | 根因 | 修复 |
|------|------|------|
| `AttributeError: 'str' object has no attribute 'name'` | 测试 StubCatalog 返回裸字符串，bridge 需要 `RepositoryProfile` | 改为返回带 name/id/url 的 `RepositoryProfile` |
| `ApplicationContainer.__init__() missing 6 required positional arguments` | **陈旧 pyc 缓存**：conftest.py 源码 mtime 早于 `__pycache__` 字节码，Python 加载旧版 fixture | 删除 tests/__pycache__ 下 conftest 相关 pyc |
| `'Database' object has no attribute 'session'` | Database 只有 `transaction()` / `sessions` 工厂，无 `session()` | 统一改用 `self._database.transaction()` |
| 存储测试 supersede 断言失败 | 测试取 `docs[0]`（notification），但 supersede 目标是 payment | 按 repository 过滤取目标文档 |
