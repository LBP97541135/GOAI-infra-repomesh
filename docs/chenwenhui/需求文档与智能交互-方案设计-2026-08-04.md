## 一、为什么改：一句话交互的根本矛盾

### 1.1 之前的设计

用户给一句话：`"在 https://gitlab.example.com/orders/order-service 里加微信支付"`

系统解析出 URL + 需求文本，直接扔给 LLM 分析。

### 1.2 问题

一句话能携带的信息量（通常 10~30 个汉字）远不足以让 LLM 精确判断哪些仓库需要改。具体表现：

| 场景 | 一句话 | 问题 |
|------|--------|------|
| "加微信支付" | 没说是哪种支付（扫码？H5？Native？） | LLM 不知道该找支付网关还是找订单服务 |
| "优化订票流程" | 完全没有功能点 | 所有服务都可能相关，Precision 趋近于 0 |
| "修复通知 bug" | 不知道是邮件通知还是站内通知 | LLM 只能猜，准确率不可控 |

**根本矛盾**：输入信息量 ≪ 输出精度要求。这不是 prompt 优化能解决的，是物理限制。

### 1.3 新设计

用户可以给两种形式的输入：

```
方式 A：需求文档（文件）
    repomesh run --requirement-file PRD.md https://gitlab.example.com/group

方式 B：文本描述（直接写在命令行里，比一句话丰富）
    repomesh run --requirement "修复订票流程中微信支付回调超时的问题" https://gitlab.example.com/group

方式 C：省略 URL，系统交互式提示
    repomesh run --requirement "修复支付回调超时"
    → ⚠ 未提供仓库或组织 URL。
    → URL > _
```

两种需求输入方式都会进入同一个流程：**如果信息足够就直接分析，不够就追问**。URL 可以省略，系统会提示用户输入。

## 二、整体流程

```
用户输入
  │
  ├── 需求：--requirement-file PRD.md  或  --requirement "一段文本"
  ├── URL：位置参数（可省略，省略则交互提示）
  │
  ▼
┌─────────────────────────────────┐
│  Step 0: URL 缺失检查            │
│  如果 URL 为空：                  │
│  - 交互模式 → 提示用户输入        │
│  - --no-interactive → 报错退出    │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────┐
│  Step 1: 信息充分度评估          │
│  manager 模型读取需求文本，判断：  │
│  - 业务信息是否足够清晰？         │
│  - 是否缺少关键上下文？           │
│  输出: { sufficient: true/false, │
│         missing: ["xxx"],        │
│         questions: ["..."] }     │
└──────────────┬──────────────────┘
               │
       ┌───────┴───────┐
       │               │
   sufficient=true  sufficient=false
       │               │
       ▼               ▼
┌──────────────┐  ┌──────────────────────────┐
│  Step 2A:    │  │  Step 2B: 智能交互        │
│  直接进入     │  │  系统向用户提问 1~3 个    │
│  仓库发现     │  │  问题，用户回答后追加     │
│  流程         │  │  到需求文本，重新评估      │
└──────────────┘  │  （最多 2 轮交互）         │
                  └───────────┬──────────────┘
                              │
                              ▼
                     ┌────────────────┐
                     │  进入仓库发现    │
                     │  流程（不变）    │
                     └────────────────┘
```

### 流程要点

1. **不管哪种输入方式，后续处理完全一样**。需求文档和文本描述在系统眼里没有区别，都是一个字符串。

2. **URL 可以省略**。如果用户忘记给 URL，系统在交互模式下会提示输入；在 `--no-interactive` 模式下直接报错退出。

3. **交互不是强制的**。如果需求已经足够详细（比如一份完整的 PRD），系统不会问任何问题，直接进入仓库发现。交互只在信息不足时触发。

4. **最多 2 轮交互**。每轮系统问 1~3 个问题，用户回答后系统重新判断。如果 2 轮后仍然信息不足，系统会带着已有信息直接分析，并在结果中标注哪些仓库是低置信度的。

## 三、信息充分度评估（Step 1）

### 3.1 模型选择：使用 manager 模型

需求充分度评估由 **manager 模型**（即系统主模型，当前为 DeepSeek）执行。原因：

- 判断"信息够不够"需要全局理解力，不是简单的分类任务
- manager 模型负责制定分析方案，评估需求充分度是方案制定的第一步
- 后续的仓库发现也由同一个模型执行，保证充分度判断和发现逻辑的一致性

代码中通过 `make_llm_client()` 创建的 `LLMClient` 实例同时用于充分度评估和仓库发现：

```python
llm_client = make_llm_client(api_key, base_url=base_url, model=model)

# 充分度评估（manager 模型）
analyzer = RequirementAnalyzer(llm_client)

# 仓库发现（同一个 manager 模型）
service = RepositoryDiscoveryService(catalog, llm_client=llm_client)
```

### 3.2 核心原则：评估的是业务信息量，不是技术信息量

**用户不需要知道涉及哪些仓库、哪些代码文件。** 评分标准检查的是"用户是否把业务场景和问题说清楚了"，不是"用户是否了解系统架构"。

举例：

| 需求文本 | 评估结果 | 原因 |
|---------|---------|------|
| "优化订票流程" | ❌ 不足 | 没说具体哪个环节、什么问题、期望什么效果 |
| "下单后微信支付回调经常超时，导致订单状态卡在待支付，需要排查支付链路" | ✅ 充足 | 业务场景明确（支付回调超时）、问题现象清楚（订单卡在待支付）、涉及的业务链路有线索（支付链路） |

第二句话里用户**没有提到任何仓库名或技术组件**，但信息完全够用——系统可以从 AutoCard 中读到的仓库功能描述来匹配"支付""订单状态"这些业务概念。

### 3.3 评估维度

| 维度 | 充足的表现 | 不足的表现 | 是否必须 |
|------|-----------|-----------|---------|
| **业务场景** | 描述了具体的功能场景和问题现象（如"支付回调超时""订单状态不同步"） | 只说了模糊的方向（"优化""重构""改进"） | ✅ 必须 |
| **行为描述** | 说了期望改什么行为（如"加一个退款入口""改成分页查询"） | 只有一个动词没有宾语（"改一下""修一下"） | ✅ 必须 |
| **变更类型** | 能判断是新增功能 / 修复 bug / 重构 / 接口变更 | 不清楚是改什么 | ✅ 必须 |
| **技术约束** | 有性能要求、兼容性要求等（如"响应时间 < 200ms""兼容旧版本"） | 无约束 | ⚪ 可选，缺少不影响充分性 |

### 3.4 LLM Prompt 设计

```
系统角色：你是一个需求分析助手。判断一份需求描述是否包含足够的业务信息，
让仓库发现系统能准确地找到需要修改的仓库。

重要原则：用户是业务人员，不需要知道涉及哪些仓库或代码文件。
你只需要检查用户是否把『要做什么』和『什么问题』说清楚了。

检查以下维度：
1. 业务场景：是否描述了具体的功能场景和问题现象？
2. 行为描述：是否说了期望改成什么行为？
3. 变更类型：是否能判断是新增功能、修复 bug、还是重构？
4. 技术约束：有无性能或兼容性要求？（可选，缺少不算不足）

返回 ONLY 一个 JSON 对象（不要 markdown fence，不要额外文字）：
{
  "sufficient": true 或 false,
  "confidence": 0.0 到 1.0 的浮点数,
  "missing_dimensions": ["缺失的维度名称"],
  "questions": ["用业务语言提问的追问，最多3个"],
  "extracted_keywords": ["从需求中提取的关键业务词"]
}
```

### 3.5 交互问题示例

| 需求文本 | 判断 | 追问 |
|---------|------|------|
| "加微信支付" | 不足 | "请问是哪种支付方式？（扫码支付 / H5 支付 / 退款）涉及哪些业务流程？" |
| "优化订票流程" | 不足 | "请具体说明是哪个环节需要优化？（查询车次 / 选座 / 下单 / 支付）期望的改进效果是什么？" |
| "修复订票流程中微信支付回调超时的问题，需要检查支付服务和订单状态同步逻辑" | 充足 | 无追问，直接进入分析 |
| PRD.md（一份完整的需求文档） | 充足 | 无追问 |

**交互问题的设计原则**：全部用业务语言提问，不问"你知道这个功能涉及哪些服务吗"。用户只需要回答业务层面的问题。

## 四、对现有架构的影响

### 4.1 不需要改的部分

| 模块 | 原因 |
|------|------|
| PlatformFetcher / GitLabFetcher / GitHubFetcher | 平台获取与需求输入无关 |
| AutoCard 构建（scan_repo / scan_org） | 仓库扫描与需求输入无关 |
| OrgCache | 缓存机制不变 |
| parse_llm_response / 评分逻辑 | 响应解析和评分逻辑不变 |
| call_graph.json / 调用图提取 | 底层数据不变 |

### 4.2 需要改的部分

| 改动 | 文件 | 说明 |
|------|------|------|
| CLI 参数解析 | `repomesh_cli.py` | `--requirement` / `--requirement-file` 二选一 + URL 可选 |
| URL 缺失提示 | `repomesh_cli.py` | 交互模式下提示输入 URL；`--no-interactive` 下报错退出 |
| 需求加载 | `scan_remote.py` | 新增 `load_requirement()`，替代从一句话中拆分 URL |
| 信息充分度评估（新增） | `requirement_analysis.py` | `RequirementAnalyzer` 类 + `RequirementAnalysis` 数据结构 |
| 交互循环 | `repomesh_cli.py` | 充分度评估 → 追问 → 追加到需求文本，最多 2 轮 |
| Prompt 微调 | `discovery.py` | `build_discovery_prompt` 注入提取的关键词 |

### 4.3 架构边界不变

改动全部在应用层（CLI + application service），不触及 domain 层和 infrastructure 层。符合 AGENTS.md 中"Application services depend on ports"的约束。

## 五、验证集适配

验证集需要从"一句话需求"改为"需求文本描述"，每个用例的 requirement 字段扩展为 2~5 句话。

### 5.1 格式变化

```json
{
  "id": "TT-001",
  "requirement": "修复订票和取消订单流程中发送通知邮件的异常。\n用户反馈下单后收不到确认邮件，取消订单后也收不到通知。\n经排查是邮件发送接口调用异常，需要检查相关服务的通知调用逻辑。",
  "requirement_type": "text",
  ...
}
```

### 5.2 新增"信息充分度"测试用例

| 用例 | 输入 | 期望行为 |
|------|------|---------|
| MIN-001 | "优化订票流程" | sufficient=false，追问具体环节 |
| MIN-002 | "改一下支付" | sufficient=false，追问支付方式和场景 |
| MIN-003 | "修复订票流程中微信支付回调超时的问题..." | sufficient=true，不追问 |
| MIN-004 | PRD.md 完整文档 | sufficient=true，不追问 |
