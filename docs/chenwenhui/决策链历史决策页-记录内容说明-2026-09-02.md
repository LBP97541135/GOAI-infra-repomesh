# 历史决策页记录内容说明

> 日期：2026-09-02
> 对应页面：控制台「历史决策」（`#/decision-chains`）
> 对应实现：`frontend/src/pages/DecisionChainPage.tsx`（v3 定稿实装，见 `docs/design/decision-chain-v3-mockup.html`）

## 一、这页记录的是什么

**每一个需求从提出到落地之间，所有关键节点上「谁、在什么时候、做了什么决定、为什么」的完整台账。**

数据不是手写的，而是系统后台真实流转时产生的决策事件（event），逐条落库后由投影器串成一条链。一条链 = 一个需求的完整决策过程。页面本身只做两件事：找到链、如实展示链。

## 二、五步决策模型

一条链固定五个步骤，每步一张卡：

| 步骤 | 系统名 | 记录的内容 | 回答的问题 |
|---|---|---|---|
| 1. 圈定范围 | `classification` | 模型把需求拆成**必改 / 待定 / 不做**三档清单（必改默认展开，待定/不做折叠） | 为什么这么做、边界在哪 |
| 2. 人工确认 | `confirmation` | 谁批准的、批准理由、批准时附加的条件；**改过口风会留版本** | 谁拍板的、中途改过什么 |
| 3. 排执行顺序 | `integration` | 多仓库之间谁先谁后、接口由谁定义谁消费（如 `IPriceChangeReason`） | 跨仓库怎么协作的 |
| 4. 拆成任务 | `task` | 拆出了哪几个具体任务（任务 id 逐行列出，不去重） | 最终落成了几个活 |
| 5. 提交代码 | `pr` | PR 状态（已合入 / 待合入）+ 可点击的 PR 链接 | 结论是什么、落地没有 |

### 版本聚合（人工确认的版本记录）

圈定范围 / 人工确认 / 排执行顺序三个步骤是**版本化**的：同一步拍板多次时，页面只展示最新生效版，旧版本收进卡内「版本记录」时间线。每条时间线标注：

- 旧版：`已被取代` + 可展开完整原文；
- 新版：`当前生效` + 差异说明（如 `补录批准理由`）。

例：人工确认 v1「批准 · 未留理由 · 已被取代」→ v2「批准 · 补录批准理由 · 当前生效」。这样两张确认卡分不清"哪个是哪个时候的"的问题从结构上消除。

### 缺口与未到达

- **缺口**：前后步骤都有记录、唯独这一步没有 → 虚线幽灵卡 + 「数据如此，非展示缺漏」，进度条上打 ⚠；
- **未到达**：链还没走到这一步 → 虚线空心卡 + 「这条链还没走到这一步」。

页面对缺失数据只如实占位、不编造叙事。

## 三、每张卡的溯源层

每张卡底部有「溯源 · 原始事件与证据」折叠层（默认收起），存原始凭据：

- `decision_id` / `event_id`
- 业务时间、入库时间（UTC）
- 事件类型（如 `ConfirmationDecided`、`TasksPlanned`、`PullRequestObserved`）
- 上游决策单指针、关联任务、change_set
- 证据引用（evidence_refs）

**用途：出事时拿原始凭据对账，页面展示层与库里存的永远能对上。**

## 四、页面的两种找法与附加板块

| 入口 | 用法 |
|---|---|
| 语义检索 | 用自然语言描述要找的历史决策，向量匹配每个项目的最新决策单（余弦相似度）；embedding 未配置时如实报错，不回退 |
| 需求定位 | 输 issue 列表里能看到的信息（标题关键词 / `#短id` / 完整 UUID），唯一命中直接追溯，多条列出候选 |

链下方还有「相似历史」板块，推荐语义相近的旧需求，供跨项目复用决策上下文。

## 五、链头卡与进度条

- **链头卡**：需求原文 + 终态徽章（已落地 · PR #N / 未提交代码 / 未通过人工确认 / 等待按要求修改）+ 全量审计 id 行（项目 id、需求快照 id、计划版本）；
- **五步进度条**：实心 ✓ = 有记录 / ⚠ = 缺口 / 空心 = 未到达，可点击跳转到对应卡片。
