# 决策链与历史上下文 —— 功能板块文档（2026-08-28）

> **状态**：方案已确认（四层绑定结构 + 三项设计决策已拍板）。
> **定位**：让 RepoMesh 从"会写代码"到"懂业务历史"——每次决策可追溯，每个新需求站在历史肩膀上。

---

## 1. 功能介绍

### 1.1 功能总览

给 RepoMesh 装上"组织记忆"，沉淀开发过程中每个决策（为什么这么改、依据是什么、谁批准的），提供三个能力：

| 功能 | 做什么 | 类比 | 触发时机 |
|---|---|---|---|
| **决策沉淀** | 每个决策点自动产出一条"决策单"，串成决策链 | 老开发的工作笔记 | 分类/确认/改档/task/PR 发生时，自动落 |
| **决策链追溯** | 输入需求 id → 输出完整链路（需求→分类→确认→task→PR），每环带证据 | 快递全链路查询 | 审计、复盘、新人理解 |
| **相似决策推荐** | 新需求 → 语义检索相似历史决策链 → 注入 LLM prompt | 医生查既往病历 | 新需求进入 pipeline 时 |

### 1.2 功能价值

- **对 AI 系统**：从"无状态推理"到"有记忆推理"——不重复历史错误，前后决策一致；
- **对企业**：知识不随人走（核心开发离职，决策依据仍在）；决策可审计（内审/合规）；变更风险可控；
- **对比赛**：落地评委"历史上下文深度理解"建议，RAG 加分项天然载体。

## 2. 我们存储了什么（核心）

### 2.1 概念：决策链 + 决策单

- **决策链（Decision Chain）**：一次需求从分析到交付的完整决策序列（需求→分类→确认→集成→task→PR）。
- **决策单（Decision Node）**：链上的每个决策点，带完整元信息。

### 2.2 绑定模型（四层，已确认）

```
org_url（入口）→ organization_id（归属组织 / 命名空间）
  └─ requirement_id（决策链根，跨仓决策的自然单位）
      ├─ 影响面：affected_repository_ids（决策时点的仓库集合）
      ├─ 决策单：分类 / 确认 / 集成 / 改档（绑决策链根，不绑单仓库）
      ├─ task → repository_id（仓库级执行锚点）
      │      └─ 证据：Room 消息（单仓库 Room / Leader DM）
      └─ PR / 交付（关联 task）
```

| 层 | 对象 | 回答的问题 | 定位 |
|---|---|---|---|
| L1 | organization_id（org_url 规范化） | 这个决策属于哪个组织 | 户口本：命名空间/归属/数据隔离 |
| L2 | requirement_id | 这次决策是什么 | 身份证：决策链根，跨仓单位 |
| L3 | task_id + repository_id | 每个仓库分别做了什么 | 行动记录：仓库级执行锚点 |
| L4 | Room 消息 / run event / evidence_version | 依据是什么、谁批准的 | 证据：决策单的 evidence_ref |

### 2.3 存储的上下文（Context）

| 上下文 | 内容 | 来源 |
|---|---|---|
| **需求原文** | 进入 pipeline 的需求文本 | 需求摄入（需实体化，见 2.6-②） |
| **Room 对话消息** | 单仓库 Room + Leader DM 的消息镜像（决策讨论、确认、驳回的原始过程） | collaboration 模块（已有 `CollaborationMessageRecord`） |
| **执行轨迹** | run events（每次 coding run 的事件序列） | agent_runtime（已有 `RunnerEventRecord`） |
| **证据对象** | 扫描产物、`classification_evidence_version` 指纹、确认对话记录 | repository_intelligence（已有） |

### 2.4 存储的信息（每条决策单的元信息）

| 信息 | 说明 |
|---|---|
| 归属 | `organization_id`（org_url 规范化后的 UUID，已确认） |
| 决策链根 | `requirement_id`（实体化需求 id，已确认） |
| 决策单标识 | `decision_id` + `step`（环节：分类/确认/改档/集成/task/PR） |
| 时间 | 业务时间 + 记录时间（双时态） |
| 决策者 | `actor`（LLM / 人工，哪个环节） |
| 状态 | proposed / confirmed / rejected / adjusted |
| 上游引用 | 指向决策链根 / 父决策（链的串联） |
| **影响面** | `affected_repository_ids` 集合（决策时点快照，已确认，不事后改写） |
| 证据引用 | Room 消息 id / run event id / evidence_version |

### 2.5 存储的决策（六类决策点）

| 决策点 | 存什么 | 例子 |
|---|---|---|
| **分类决策** | 三档结果 + 依据 + 证据指纹 | `checkout → required（证据: 直接依赖 5 处）` |
| **确认决策** | 确认/驳回 + 图预扩充清单 + 冲突 + 观察名单 | `payment → confirmed（预扩充自图）` |
| **改档决策** | 谁、把哪个档改成哪个档、理由 | `ledger: excluded → maybe（人工，理由: 记账依赖）` |
| **集成方案决策** | 执行批次 + 契约 | `批次1: {checkout, payment}，契约 C1` |
| **任务拆分决策** | task + 依赖 + 上游引用（requirement_id） | `task-1: 重构 checkout 结账模块` |
| **PR 决策** | 变更集 + 关联 task + PR url + 合入理由 | `PR #42: 合入结账重构（task-1）` |

### 2.6 已确认的三项设计决策

1. **org_url 只做入口，内部用 `organization_id`（UUID）**——避免 URL 变体（斜杠/大小写/协议）导致同一组织数据分裂；
2. **requirement 实体化 id，随主流程补**——需求进入 pipeline 时落一条带 id 的记录（"决策链种子"），后续所有决策挂此 id；id 只在产生当下可知，事后补只能靠猜；
3. **影响面用时点快照**——决策发生时定格涉及仓库集合，依赖图后续变化不回溯改写历史决策（历史是照片不是直播）。

## 3. 企业真实使用场景

### 场景一：新需求评估（技术负责人）
> 新需求"优化结账流程"进入系统，自动带出半年前的相似需求决策链：
> "当时 checkout 被分为 required，payment 在确认时被图预扩充纳入，ledger 被人工从 excluded 改为 maybe（理由：记账依赖），最终影响 3 个仓库。"
> 负责人基于历史经验 5 分钟拍板，不用重新调研。

### 场景二：变更合规审计（审计/合规部门）
> 内审问："生产环境支付模块为什么被改？"
> 系统展示完整决策链：需求 → 分类（带证据指纹）→ 人工确认（Room 消息）→ 任务 → PR（合入理由），
> 每环有证据、有批准人、有时间。审计从"翻日志猜"变成"查链"。

### 场景三：知识传承（新入职开发者）
> 新人接手陌生模块，查该仓库的历史决策链：
> "这个模块为什么这么设计、改过几次、为什么改、当时谁拍的板"。
> 不需要到处找人问，老人离职也不怕知识断层。

### 场景四：架构治理与变更风险控制（架构师）
> "checkout 改一个接口，会波及哪些下游？"
> 依赖图影响分析秒出：`payment → ledger → analytics`（多跳）。
> 架构师在动手前评估风险，避免"改一个 API 炸了 30 个下游"。

### 场景五：跨团队协作（多团队开发）
> A 团队要改公共库接口，先查该仓库历史决策链：
> "谁依赖它、之前有什么接口约定、为什么这么设计"。
> 避免误伤其他团队的既有约定。

## 4. 技术路线与边界

| 关注对象 | 技术 | 说明 |
|---|---|---|
| 决策链（沉淀/追溯/推荐） | **PG 关系表 + 外键 + pgvector** | 线性 2-3 跳路径查询，**不需要图数据库** |
| 代码依赖图（影响分析） | 现状 **JSON 快照**（单一事实源）；规模上来可升级 **AGE** | 图的价值锚点在依赖图，不在决策链 |
| 相似决策推荐（RAG） | **pgvector**（决策文本 embedding） | 独立于图，RAG 加分项 |

**边界**：只有当跨仓影响分析需要多跳遍历/中心性（依赖图规模上千节点几万边）时，才考虑 AGE——那是依赖图的升级，决策链存储不受影响。

---

## 5. 设计红线（含原因）

1. **决策链不存图数据库**——决策链是线（2-3 跳路径），线的查询用表；图是给网（多跳遍历、图算法）用的，用图存线是杀鸡用牛刀；
2. **不引入 semantica 重量级模块**（ontology/SPARQL/推理引擎）——决策数据是我们自己生成的结构化数据，不需要机器自动推理，引入只有成本没有收益；
3. **决策记录是唯一事实源，图谱（若建）只读投影**——一份真值，复印件可随时重印，绝不双写（避免两份数据打架）；
4. **影响面是时点快照**——历史是照片不是直播，事后改写导致追溯失真、审计翻车；
5. **证据指 RepoMesh 侧持久化消息**——指自己手里握得住的那份（collaboration 镜像），不依赖外部 Matrix 可用性。
