# 决策链与历史上下文 —— 功能定义（v2，2026-08-28）

> 一句话定位：**让 RepoMesh 从"会写代码"到"懂业务历史"——每次决策可追溯，每个新需求站在历史肩膀上。**
>
> v2 变更：确认绑定模型为四层结构（org_url 归属 → requirement 决策链根 → task/repository 执行锚点 → Room 消息证据）；
> 对抗性审查后给出 7 条调整建议（见 §7）。

---

## 1. 核心概念模型

**决策链（Decision Chain）**：一次需求从分析到交付的完整决策序列。
**决策单（Decision Node）**：链上的每个决策点（分类、确认、改档、任务拆分、PR）。

**四层绑定模型**（决策记录怎么挂、挂在哪）：

```
org_url（归属组织 / 命名空间）
  └─ 决策链根：requirement_id（跨仓决策的自然单位）
      ├─ 影响面：affected_repository_ids（决策时点的依赖图子图，跨仓表达）
      ├─ 决策单：分类 / 确认 / 集成 / 改档（跨仓，绑决策链根）
      ├─ task → repository_id（仓库级执行）
      │      └─ 证据：Room 消息（单仓库 Room / Leader DM）
      └─ PR / 交付（关联 task）
```

| 层 | 对象 | 回答的问题 | 定位 |
|---|---|---|---|
| L1 | org_url | 这个决策属于哪个组织 | 户口本（命名空间 / 归属） |
| L2 | requirement_id | 这次决策是什么 | 身份证（决策链根，跨仓单位） |
| L3 | task_id + repository_id | 每个仓库分别做了什么 | 行动记录（仓库级执行锚点） |
| L4 | Room 消息 / run event / evidence_version | 依据是什么、谁批准的 | 证据（决策单的 evidence_ref） |

**跨仓场景示例**：需求"优化结账流程"
> 决策链根 = `issue-42`（L2）；分类/确认/集成全绑 `issue-42`，不绑单仓库；
> 影响面 = `{payment, checkout, ledger}`（依赖图子图）；三个仓库各一个 task（L3），各自 Room 消息为证据（L4）。

## 2. 功能清单

| 功能 | 做什么 | 触发时机 |
|---|---|---|
| **决策沉淀** | 每个决策点自动产出一条决策单（id、时间、actor、依据、状态、上游引用） | 分类/确认/改档/task/PR 发生时 |
| **决策链追溯** | 输入 requirement_id → 输出完整链路（需求→分类→确认→task→PR），每环带证据 | 审计、复盘、新人理解 |
| **相似决策推荐（RAG）** | 新需求 → 语义检索相似历史决策链 → 注入 LLM prompt | 新需求进入 pipeline 时 |

## 3. 存什么（数据维度）

- **决策单**：decision_id / chain_id(requirement) / step / created_at / actor / status / evidence_ref / upstream_ref / payload
- **证据**：指向 RepoMesh 侧的 collaboration 消息 id（Room 消息镜像）、run event、evidence_version
- **影响面**：affected_repository_ids 集合（决策时点的仓库集合，快照式）
- **归属**：organization_id（org_url 规范化后的内部标识）

## 4. 技术路线（决策链 vs 图的最终判断）

**结论：决策信息走"决策链"（PG 关系表 + 外键），不需要图数据库。** 理由：

1. 决策链是**线性 2-3 跳**（requirement → task → PR），路径查询，SQL 足够；
2. 决策间的直接引用稀疏（外键可表达），不存在"多跳决策推理"的查询需求；
3. 跨仓影响**通过 repository 维度交给代码依赖图**，不塞进决策存储。

| 关注对象 | 技术 | 说明 |
|---|---|---|
| 决策链（沉淀/追溯/推荐） | **PG 关系表 + 外键 + pgvector** | 决策链 + 语义检索，不需要图 |
| 代码依赖图（影响分析） | **现状 JSON 快照**；规模上来可升级 **AGE** | 图的价值锚点在这里，不在决策链 |
| 相似决策推荐（RAG） | **pgvector**（决策文本 embedding） | 独立于图，RAG 加分项 |

**边界**：只有当"跨仓影响分析"要跑多跳遍历/中心性（依赖图规模到上千节点几万边）时，才考虑 AGE——那是**依赖图的升级**，决策链存储不受影响。

## 5. 企业实际应用场景

| 角色 | 场景 |
|---|---|
| 技术负责人 | 新需求自动带出相似历史决策链，基于历史快速拍板 |
| 审计/合规 | 输入需求 id 展示完整决策链，每环有证据有批准人 |
| 新入职开发者 | 查历史决策链理解"为什么这么设计"，不用找人问 |
| 架构师 | 改核心仓前看影响面（依赖图子图）：会不会炸 30 个下游 |
| 跨团队 | 改公共库前查历史决策与接口约定，避免误伤 |

## 6. 红线（不做什么）

1. 决策链**不存图数据库**（关系表够用，不为技术而技术）；
2. 不引入 semantica 的 ontology/SPARQL/推理引擎等重量级模块；
3. 决策记录是**唯一事实源**，任何图谱（若建）是只读投影，绝不双写；
4. 影响面记录**决策时点**的仓库集合，不事后用最新依赖图改写（bi-temporal 原则）；
5. 证据引用 **RepoMesh 侧持久化消息 id**，不直接依赖外部 Matrix 事件 id。

## 7. 对抗性审查调整建议（v1 → v2 修正）

1. **org_url 不能直接当存储键**：URL 有变体（大小写/末尾斜杠/协议），同一组织会产生数据分裂。→ 内部统一用 `organization_id`（UUID），org_url 只是入口输入。
2. **requirement 当前无稳定 id**（`RequirementAnalysis` 是纯文本分析）→ 决策链根需要一个实体化的 `issue/requirement` 稳定 id（这属于决策链种子，必须随主流程补）。
3. **区分"决策链"与"决策单"**：链是根的聚合，单是链上节点。概念上先分清，避免实现时混为一谈。
4. **证据引用 RepoMesh 侧消息 id**：Room 消息在 AgentTeams 侧（Matrix），RepoMesh 的 collaboration 模块有镜像（`CollaborationMessageRecord`）→ 证据指向镜像 id，不依赖外部系统可达性。
5. **影响面是"时点快照"**：决策发生时认定的涉及仓库集合，事后依赖图变化不回溯改写历史决策。
6. **跨仓决策不复制到各仓库**：决策单绑决策链根（requirement），仓库维度只出现在 L3 的 task 上——这就是"不绑单仓库"的落地方式。
7. **决策间稀疏引用用外键**：决策 A → 决策 B 的直接引用（如"改档原因"）用外键表达，不需要图遍历能力。
