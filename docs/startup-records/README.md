# 启动记录（startup-records）

这个目录记录**每一次从零（或接近从零）启动项目**以及启动后端到端验证（如 issue→提交链）的实走过程：每一步执行了什么命令、
预期是什么、实际发生了什么、卡在哪里、怎么绕过的。目的不是写教程，而是留下
「README 承诺的启动路径在真实机器上到底走不走得通」的证据，供修 README、修脚本时对照。

## 文件约定

- 一次启动一个文件：`YYYY-MM-DD-<场景>.md`，例如 `2026-09-02-from-zero-windows.md`。
- 每一步一个小节，固定字段：
  - **命令**：原样粘贴（含工作目录、用哪个 shell）。
  - **预期**：README/脚本注释里承诺的结果。
  - **实际**：真实输出摘录（长输出落到同名 `.log` 文件，正文只引关键行）。
  - **状态**：`PASS` / `BLOCKED`（卡死，需要人工干预） / `WORKAROUND`（绕过了，写清怎么绕的） / `SKIP`（跳过及原因）。
  - **耗时**：粗略即可。
- 原始控制台输出放在同名 `*.log` 文件里，正文引用行号或关键片段。
- 结尾必须有「问题清单」小节，按严重度列出本次暴露的缺陷，每条指向 README 段落或脚本行号。

## 状态字段的判定

- README 写的命令原样跑通 = PASS。
- 需要改命令、改脚本、手工补文件才能过 = WORKAROUND，即使最后过了也不算 PASS。
- 环境原因（网络、Docker 引擎故障）导致失败，要单列出来，不算项目缺陷但要记。
- 多份记录的问题需要合看时，另写 `YYYY-MM-DD-defect-summary.md` 做分级汇总（设计问题 / 实现 bug / 支持缺口 / 环境文档），例：`2026-09-02-defect-summary.md`。
- 交给下一个会话继续时，写 `YYYY-MM-DD-handoff-<主题>.md`，含环境实况、要读的文件、待裁决项。
