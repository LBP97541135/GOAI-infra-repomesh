# TT-001：订票与取消流程通知邮件修复需求

## 1. 需求概述

修复订票成功和取消订单后的通知邮件发送异常。当前所有用户都无法收到相关邮件，初步排查表明通知服务的邮件发送接口调用存在异常，问题跨越通知服务与订单业务服务之间的调用链。

修复后，订票成功应发送包含订单号、车次和座位信息的确认邮件；订单取消成功应发送包含取消结果和退款信息（如有）的确认邮件。邮件发送失败不得阻断订票或取消订单主流程。

## 3. 用户场景

### 3.1 订票成功

用户完成选座并成功下单后，系统应异步或同步触发订票确认邮件。邮件至少包含：

- 订单号
- 车次
- 座位信息
- 可识别的订票成功状态

### 3.2 取消订单成功

用户成功取消订单后，系统应触发取消确认邮件。邮件至少包含：

- 订单号或可关联订单的标识
- 订单已取消状态
- 退款信息（适用时）

## 4. 功能要求

### 4.1 通知服务

- 检查并修复邮件发送实现。
- 检查邮件接口的请求参数校验、响应状态和异常处理。
- 确保邮件发送成功返回明确的成功响应。
- 非法请求返回明确的客户端错误，不产生不完整或错误邮件。
- 邮件服务商或 SMTP 调用失败时，支持有限次数重试。
- 重试仍失败时记录足够的日志，包括操作类型、订单标识、收件人脱敏信息和失败原因；不得记录密码、访问令牌或完整敏感凭据。

### 4.2 业务调用方

- `ts-preserve-service` 在订票成功后调用通知服务。
- `ts-cancel-service` 在取消成功后调用通知服务。
- `ts-preserve-other-service` 检查订票和取消相关通知调用。
- 各调用方使用通知服务约定的请求字段，不自行拼接另一套邮件协议。
- 通知调用失败不得回滚已经成功的订票或取消操作。
- 调用失败必须记录可关联的业务日志，并遵循统一的超时与重试策略。

## 5. 接口契约

### 5.1 通用邮件接口

```text
POST /api/v1/notifications/email
```

请求至少包含：

```json
{
  "recipient": "user@example.com",
  "subject": "订票成功",
  "body": "..."
}
```

行为约定：

- 邮件成功发送：返回 `200 OK` 或项目既有的等价成功响应。
- 请求字段缺失或格式非法：返回 `400`，并给出可定位的字段错误。
- 邮件服务商失败：返回明确的服务端错误；调用方记录错误并继续主业务流程。
- 请求应携带业务幂等标识，避免网络重试造成重复发送。

### 5.2 订单通知接口

```text
POST /api/v1/notifications/order
```

该接口负责根据订单事件生成合适的邮件内容，覆盖订票成功和取消成功场景。若项目最终统一使用通用邮件接口，应由通知服务内部完成模板选择，调用方不得重复实现模板规则。

## 6. 非功能要求

- 可靠性：邮件调用失败时有限重试，重试策略应有最大次数和退避时间。
- 隔离性：邮件发送失败不能影响订单创建、订票确认或取消事务的成功结果。
- 可观测性：每次发送、重试和最终失败都可通过订单标识或请求幂等键关联查询。
- 安全性：日志中的邮箱、订单和用户信息应按现有脱敏规范处理。
- 一致性：所有调用方使用同一套请求字段、状态码语义和错误处理约定。

## 7. 实施批次

### 批次 A：通知服务

负责仓库：`ts-notification-service`

- 复现邮件发送失败。
- 修复邮件接口和订单通知接口。
- 增加参数校验、异常处理、重试和失败日志。
- 增加成功、非法请求、服务商失败和重试耗尽测试。

以下仓库可在批次 A 的接口契约确认后并行处理：

- `ts-preserve-service`

- `ts-preserve-other-service`

每个仓库需要核对调用路径、请求载荷、超时、错误隔离和测试覆盖。

## 8. 验收标准

- 订票成功后，通知服务收到正确的确认邮件请求。
- 取消成功后，通知服务收到正确的取消邮件请求。
- 确认邮件包含订单号、车次和座位信息。
- 取消邮件包含取消状态和适用的退款信息。
- 邮件发送失败时按策略重试，重试耗尽后有可查询日志。
- 邮件服务不可用时，订票和取消主流程仍能正常完成。
- 非法邮件请求返回 `400`，不调用外部邮件服务。
- 所有受影响仓库的相关测试通过，且接口字段和错误语义保持一致。
- 重复投递同一业务幂等键不会产生重复邮件。

## 9. 风险与待确认项

- 需要确认当前邮件服务使用 SMTP、第三方邮件 API，还是项目内置适配器。
- 需要确认通知发送是同步调用还是消息队列异步调用；无论采用哪种方式，都必须保留主流程隔离和失败可追踪性。
- 需要确认订单取消退款信息的真实字段来源，避免通知服务自行猜测金额或状态。
- 需要在测试环境提供可控的邮件服务替身，禁止验收测试直接向真实用户邮箱发送邮件。
